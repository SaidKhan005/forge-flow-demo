# Lane B Catalog Follow-Up Proposal

Status: proposed
Owner: permission catalog owner
Source slice: B5 - Admin access-control + permission-key completeness sweep

## Purpose

B5 intentionally does not amend the frozen permission catalog. This note
captures the scoped follow-up work needed to reconcile permission-key gaps
without drifting the three mirrors:

1. `docs/contracts/auth_permission_key_catalog.md`
2. `lib/auth/permission_keys.dart`
3. additive permission-key seed migration under `db/migrations/`

## Catalog Gaps To Reconcile

| Key | Current finding | Proposed disposition |
|---|---|---|
| `account.configure` | Already flagged in the catalog pending-additions section; `lib/screens/account_screen.dart` hand-types the key. | Add an `account.*` category or place in the owner-approved account settings namespace, seed grants for the operator roles that own My Account edits, then replace the string literal with `PermissionKeys.*`. |
| `business_timing.configure` | Already flagged in the catalog pending-additions section; `lib/screens/business_setup_screen.dart` and `lib/screens/business_timing_editor_screen.dart` hand-type the key. | Add a business-timing settings key in the owner-approved namespace, seed grants for operator owner/admin or manager-tier roles per product decision, then replace the string literals with `PermissionKeys.*`. |
| `admin.roles.catalog_publish` | B2 can reuse `admin.roles.edit_seeded` while catalog publish remains super_admin-only. A distinct key is only needed if catalog publishing opens beyond that role. | Prefer no new key for launch. Add only if B2's final implementation needs a separable grant from seeded-role editing. |
| `admin.vendor_applicability.edit` | B10 can stay super_admin-role gated at launch. A distinct key is only needed if vendor-applicability editing opens beyond super_admin. | Prefer no new key for launch. Add if B10 expands to a broader F&F admin tier or needs permission-cache/MFA semantics independent of the role claim. |

## Follow-Up Slice

Recommended slice name: **Catalog tri-mirror amendment for account and timing
settings keys**.

Allowed files for that slice:

- `docs/contracts/auth_permission_key_catalog.md`
- `lib/auth/permission_keys.dart`
- a new additive migration under `db/migrations/`
- the three screens that currently hand-type the operator settings keys

Non-goals:

- Do not change admin route guards.
- Do not change seeded role meaning beyond the explicit key grants.
- Do not add B2/B10 admin keys unless their implementation has landed and the
  catalog owner confirms the new key is required.

## Acceptance Checks

- `PermissionKeys.all` contains every new key exactly once.
- The catalog table documents each new key, its grant intent, and MFA posture.
- The migration inserts each new key and role grant idempotently.
- Tests that compare catalog constants to seed data pass.
- No screen keeps hand-typed `account.configure` or
  `business_timing.configure` after constants exist.
