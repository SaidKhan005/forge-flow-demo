# 11A.13 Walkthrough - Roles + Hierarchy + Sessions inspect (cross-operator admin)

**Slice:** 11A.13 (Phase 11A - F&F Operations Console)
**Mode:** `-DemoMode` (admin Flutter Web client + in-memory roles /
hierarchy / sessions admin gateway, no live proxy required)
**Date:** 2026-05-05

This walkthrough covers the admin click path for the new
`Roles, hierarchy, and sessions` route mounted at
`/admin/roles-hierarchy-sessions` in `lib/admin/admin_routes.dart`.
The slice ships the cross-operator inspect surface that gives F&F
support escalations one screen with three tabs (Roles, Hierarchy,
Sessions) scoped to the picked operator. F&F super_admin can pick
an operator, tab through the role catalog, audit-edit org-unit
hierarchy, and force-logout active sessions. ff_support lands on
the read-only branch.

  § Roles + Permission Explainer (`11W.2` + `11A.13` Roles tab),

  route mounted after the operator picker, the
  `_buildRolesHierarchySessions` builder + the
  `_RolesHierarchySessionsRouteShell` host that runs the picker
  before the inspect surface, the
  `rolesHierarchySessionsAdminGateway` field on
  `AdminConsoleServicesScope`, the
  `rolesHierarchySessionsAdminGatewayOf(context)` accessor, and the

  from `kDemoRolesByOperator` / `kDemoOrgUnitsByOperator` /
  `kDemoHierarchyLocationsByOperator` / `kDemoSessionsByOperator`.

- `lib/main_admin.dart` - resolves
  `HttpRolesHierarchySessionsAdminGateway` (mirrors the members
  resolver) and feeds it into
  `AdminConsoleServicesScope.rolesHierarchySessionsAdminGateway`.
  Live builds bind the proxy-backed gateway; the in-memory
  walkthrough fixtures only reach the screen in
  `--dart-define=ADMIN_DEMO_AUTH=true` runs or when the proxy URI
  is missing - never on a live deploy.
- `lib/admin/screens/roles_hierarchy_sessions_admin_screen.dart` -
  new `RolesHierarchySessionsAdminScreen` widget. Three tabs in a
  `TabBar` + `TabBarView`: Roles (seeded view-only by default;
  edit gated on `canEditSeededRoles` which mirrors
  `admin.roles.edit_seeded`; custom-role create + delete via
  `admin.roles.create_custom` / `admin.roles.delete_custom`),
  Hierarchy (org-unit tree + location leaves with audit-logged
  Move actions), Sessions (every active session for every user in
  the operator with `Force logout` per `admin.session.force_logout`,
  disabled on the admin's own session). Every write surfaces an
  admin reason dialog before forwarding the call.
- `lib/admin/services/roles_hierarchy_sessions_admin_gateway.dart` -
  new `RolesHierarchySessionsAdminGateway` interface +
  `HttpRolesHierarchySessionsAdminGateway` carrying the bearer
  token to the proxy `/v1/admin/auth/roles`,
  `/v1/admin/auth/org-units`, and `/v1/admin/auth/sessions`
  paths; idempotency key forwarded verbatim; non-forge-admin
  callers throw `RolesHierarchySessionsForbiddenException` before
  any HTTP call lands. Audit `action` strings live in the locked
  `team.*` / `admin.session.*` family
  (`team.roles.edit_seeded`, `team.roles.create_custom`,
  `team.roles.delete_custom`, `team.org_unit.move`,
  `team.location.move`, `admin.session.force_logout`) so admin-path
  and operator-self-service writes produce identical canonical fact
  rows differing only in `actor_kind`.
- `lib/admin/services/demo_roles_hierarchy_sessions_admin_gateway.dart`
  - new `InMemoryRolesHierarchySessionsAdminGateway` plus the demo
  seed reusing `kDemoDinerOperatorId` / `kDemoSunsetOperatorId`
  from `kDemoMembersByOperator` so the walkthrough can hop
  straight from the Members surface into Roles / Hierarchy /
  Sessions for the same operator. Captures audit events with
  `actor_kind = forge_admin` + the calling admin's UID + a
  non-empty `admin_reason`.
- `lib/admin/screens/operator_picker_screen.dart` - reused
  verbatim. The new route opens this picker on first paint and
  remembers the last-picked operator per admin UID.

## Click path (text trace)

### Step 1 - Sign in as super_admin and open the route

Launch the admin console with `-DemoMode -Device chrome`, sign in
as `super.admin@forgeflow.test`, click `Roles, hierarchy, and
sessions` in the side nav.

**Expected:**

- The route mounts the operator-picker screen first
  (`Key('admin_operator_picker_screen')`) - the inspect surface is
  scoped to one operator at a time.
- The picker dialog renders with an operator dropdown.

### Step 2 - Pick Demo Diner Co.

Choose `Demo Diner Co.` in the operator dropdown, leave Toronto
Yorkville selected, tap `Use selection`.

**Expected:**

- The inspect surface mounts
  (`Key('admin_roles_hierarchy_sessions_screen')`) with the picked
  operator named in the page header subtitle ("Inspect and
  audit-edit the role catalog, org-unit hierarchy, and active
  sessions for Demo Diner Co. ...").
- The `TabBar` (`Key('admin_rhs_tab_bar')`) renders three tabs:
  `Roles`, `Hierarchy`, `Sessions`. The Roles tab is selected by
  default.

### Step 3 - Tab through Roles

Stay on the `Roles` tab.

**Expected:**

- The Permission Explainer card
  (`Key('admin_rhs_permission_explainer')`) renders at the top of
  the tab. Per the parity contract § "Roles + Permission
  Explainer" line 102, it lists every key in the frozen
  `PermissionKeys.all` catalog grouped into the nine locked
  categories in the locked order: `product` → `forgeflow` →
  `barrio` → `admin` → `team` → `billing` → `integration` →
  `integrations` → `workflow`. Each section header carries a
  testable key (`admin_rhs_permission_category_<prefix>`).
- Permission keys flagged in `PermissionKeys.requiresMfa` (e.g.
  `admin.users.erase_pii`, `admin.roles.edit_seeded`,
  `admin.pricing_tier.edit`) render with a lock icon plus the
  literal "MFA" text and the contract-pinned tooltip "Requires
  multi-factor authentication." (line 110). No emoji-only
  signals.
- The seeded roles card (`Key('admin_rhs_roles_seeded')`) lists 4
  rows: Operator owner, Operator manager, Operator supervisor,
  Operator staff. Each row carries the `Seeded` chip and renders
  view-only. The `Edit permissions` button is hidden by default;
  it lights up only when `canEditSeededRoles == true` is passed
  by the route shell. The route shell defaults `false` even for
  super_admin until production plumbs the MFA-asserted claim
  (`admin.roles.edit_seeded` is MFA-required per the parity
  contract § "Seeded roles" line 104; the proxy stays
  authoritative regardless and rejects the call without an
  MFA-fresh token).
- The custom roles card (`Key('admin_rhs_roles_custom')`) lists 1
  row (`Floor Captain`, key `custom.floor_captain`) with a
  `Delete` button.
- The `New custom role` button
  (`Key('admin_rhs_roles_create_custom')`) is visible in the
  custom-roles card header.

### Step 4 - Tab through Hierarchy

Tap the `Hierarchy` tab (`Key('admin_rhs_tab_hierarchy')`).

**Expected:**

- The hierarchy card mounts (`Key('admin_rhs_hierarchy_tab')`)
  with the org-unit tree:
  - `Demo Diner Co.` (root)

- Each non-root org-unit and location row shows a `Move` button.
  The root org-unit has no `Move` button (the root cannot be
  reparented).

### Step 5 - Tab through Sessions

Tap the `Sessions` tab (`Key('admin_rhs_tab_sessions')`).

**Expected:**

- The sessions card mounts (`Key('admin_rhs_sessions_tab')`) with
  three rows:
  - `Dana Owner / owner@demo-diner.test` - iOS Safari on iPhone -
    Toronto, ON - active 15m ago
  - `Dana Owner / owner@demo-diner.test` - Chrome on macOS -
    Toronto, ON - active 2h ago
  - `Mira Manager / manager@demo-diner.test` - Android Chrome on

- Each row exposes a `Force logout` outlined button.
- The page-level explainer reads "Every session for every member

### Step 6 - Force-logout a fixture session

Tap `Force logout` on the `Dana Owner / Chrome on macOS` row
(`Key('admin_rhs_session_force_logout_session-diner-owner-web')`).

**Expected:**

- The reason dialog (`Key('admin_rhs_reason_dialog')`) opens with
  the title `Force logout Dana Owner`.

Submit empty.

**Expected:**

- The error label reads `Add a reason before continuing.`.

Type `walkthrough verification`, tap `Confirm`.

**Expected:**

- The dialog dismisses.
- A snackbar reads `Signed out Dana Owner`.
- The row disappears from the sessions table.
- The audit log captures the contract-locked
  `admin.session.force_logout` action with
  `actor_kind = forge_admin`, `actor_user_id = demo-super-admin`,
  `target_kind = auth_session`, `target_id = session-diner-owner-web`,
  `admin_reason = walkthrough verification`, and the payload
  `{ user_id: demo-user-diner-owner }`. The `business_date` field
  carries the restaurant-local date; the `row_hash` field is null
  on the demo gateway (the live proxy populates it).

### Step 7 - Cannot revoke own admin session (test pin)

The screen layer disables the `Force logout` button on any session
whose `userId` equals the actor's UID; the gateway also throws
`RolesHierarchySessionsGatewayError(errorCode:
'cannot_revoke_self')` if a programmatic call ever fires. Both
defences are pinned by the widget test "force-logout button is
disabled for a session belonging to the actor" + the gateway test
"forceLogoutSession throws cannot_revoke_self when targeted user
is the admin".

### Step 8 - Sign in as ff_support, verify view-only posture

Sign out, sign in as `support@forgeflow.test`. Open `Roles,
hierarchy, and sessions`, pick the same operator.

**Expected:**

- The view-only banner (`Key('admin_rhs_readonly_banner')`)
  renders.
- The `New custom role` button is absent.
- Every row's mutate-action buttons are absent (`Delete` on
  custom roles, `Move` on org-units / locations, `Force logout`
  on sessions). The three tabs still render so support can read
  state.

## Permission gating evidence

- Client side (admin console): the route is only reachable when
  the auth gate admits the caller (`super_admin` or `ff_support`).
  The `_buildRolesHierarchySessions` builder reads
  `state.session.roles` and computes
  `canEdit = roles.contains('super_admin')`; the screen consumes
  `editingEnabled` to drive the read-only banner and the
  visibility of every mutate affordance. `canEditSeededRoles` is
  conservatively false; production wires the MFA-required claim.
- Defence in depth at the gateway seam:
  `RolesHierarchySessionsAdminGateway.{editSeededRole,
  createCustomRole, deleteCustomRole, moveOrgUnit, moveLocation,
  forceLogoutSession}` each throws
  `RolesHierarchySessionsForbiddenException` when
  `actorIsForgeAdmin == false`. Asserted by "every mutation throws
  Forbidden when actorIsForgeAdmin is false".
- Defence in depth on `admin_reason`: every gateway write throws
  `RolesHierarchySessionsGatewayError(errorCode:
  'admin_reason_required')` on empty reason.
- Cannot-revoke-self pinning: gateway throws
  `cannot_revoke_self`; screen disables the affordance on the
  actor's own session.

## Boundary checks

  `11W.2` / `11W.3` / `11W.4` own operator-web and are
  intentionally scoped out.

  live in `/v1/admin/auth/{roles,org-units,sessions}` and the

  `admin.roles.*` and `admin.session.force_logout` keys the
  catalog already ships.

## UX writing posture

(per `docs/frameworks/UX_ADJUSTMENT_FRAMEWORK.md` and the user's writing
standard). The page header subtitle and the per-tab explainer
text both name the audited nature of every action so the F&F
admin sees their accountability up front.

ZERO em dashes appear in any operator-facing literal in the new
files (test pin: `roles_hierarchy_sessions_admin_screen_test.dart`
"rendered text never contains an em dash" + the gateway test "no
operator-facing literal contains an em dash"). Hierarchy
validation copy mirrors the parity contract's
"Validation copy (locked)" block verbatim
(`Cannot move into a child of itself.`).
