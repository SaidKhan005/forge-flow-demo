# 8.demo-mode-banner Walkthrough — Runtime per-(operator, location, category) demo banner

**Slice:** 8.demo-mode-banner (Phase 8 P1 audit follow-up — closes the
unfulfilled architecture promise in
`lib/services/integration/demo_mode_state.dart` lines 12-15).
**Mode:** Production / staging build (`kDemoMode = false`). The banner
is a runtime read of `demo_mode_state.is_demo`, NOT a build-time flag.
**Date:** 2026-05-08
**Demo start condition:**
- Operator: "Demo Diner Co.", Location: "Toronto Yorkville".
- Operator has just signed in for the first time.
- No vendor connections yet for the active location.
- `demo_mode_state` rows for `(operator, location)`:
  | category    | is_demo |
  |-------------|---------|
  | pos         | true    |
  | labor       | true    |
  | reservation | true    |

This walkthrough is a numbered click-path per the
`docs/CODEX_PROMPT_GENERATION_STANDARD.md` Walkthrough Specificity
section. Every step names the user action, the expected visual state,
and the runtime-state surface that drives each render.

The slice realizes two Hard Promises:
2. **Demo mode persists post-launch.** The banner is driven by the
   per-(operator, location, category) `demo_mode_state.is_demo` row;
   the banner clears WITHOUT a redeploy once
   `DemoModeFlipPolicy.evaluateFlip` flips the row after the first
   vendor backfill commit.
10. **Every backend phase ships operator-facing UX before phase
    close.** Phase 8.0 wired the write side and the proxy read route
    in 2026-05-04; this slice closes the read-side UX gap the audit
    flagged on 2026-05-08.

## Click-path

### 1. Cold start — three demo banners visible

- Operator signs in on a fresh device. AppShell mounts.
- `_AppShellState._bindDemoModeNotifier` resolves
  `Provider<SyncProxyClient?>` (production wires
  `HttpSyncProxyClient`) and the `DemoModeStateNotifier` instance from
  `ForgeFlowScope`.
- `_syncDemoModeScope` pushes `(operatorId = op-demo,
  locationId = loc-yorkville)` into the notifier; the notifier calls
  `client.fetchDemoModeStates(operatorId: ..., locationId: ...)` which
  hits proxy route
  `/v1/operators/op-demo/locations/loc-yorkville/demo_mode_states`.
- The proxy returns three rows (POS, Labor, Reservation; all
  `is_demo = true`).

Expected render — directly under the standalone app bar, above the
Shift / Variance / Plan / Benchmark IndexedStack:

```
┌──────────────────────────────────────────────────────────────────┐
│ ◢ Demo POS data — connect a POS to go live.                     │
├──────────────────────────────────────────────────────────────────┤
│ ◢ Demo labor data — connect a labor system to go live.          │
├──────────────────────────────────────────────────────────────────┤
│ ◢ Demo reservation data — connect a reservation system to go    │
│   live.                                                          │
└──────────────────────────────────────────────────────────────────┘
```

Named widgets under test:
- `DemoModeBanner` (`lib/widgets/demo_mode_banner.dart`).
- Per-row keys: `demo_mode_banner_pos`, `demo_mode_banner_labor`,
  `demo_mode_banner_reservation`.
- Stack key: `demo_mode_banner` (root `Material`).

### 2. Operator connects a POS — POS row clears, others remain

- Operator navigates to **Settings → Setup → Vendor connections**
  (admin/operator-web path; a mobile-side route lands as a
  follow-up).
- Operator completes the Toast OAuth flow. Vendor sink
  `toast_pos_postgres_sink.dart` commits the first backfill batch
  (>=1 record).
- `DemoModeFlipPolicy.evaluateFlip(category: pos, ...)` flips
  `demo_mode_state.is_demo = false` for `(op-demo, loc-yorkville,
  pos)` and stamps `flipped_to_live_at` / `flipped_by_connection_id`.
- A realtime frame on an `integrations.*` topic for the active
  operator arrives via the `RealtimeEventBus`. AppShell's
  `_handleBusinessScopeRealtimeEvent` calls
  `notifier.refresh()`; the notifier re-pulls and sees POS now
  `is_demo = false`.

Expected render — POS row collapses; Labor and Reservation rows stay:

```
┌──────────────────────────────────────────────────────────────────┐
│ ◢ Demo labor data — connect a labor system to go live.          │
├──────────────────────────────────────────────────────────────────┤
│ ◢ Demo reservation data — connect a reservation system to go    │
│   live.                                                          │
└──────────────────────────────────────────────────────────────────┘
```

Belt-and-braces: even if the realtime frame is not delivered, the
banner re-pulls on the next foreground resume
(`_AppShellState.didChangeAppLifecycleState`) and on the next
business-scope flip — the POS row drops out of the next snapshot,
the banner rebuilds with two children.

### 3. Operator connects labor + reservation — banner stack hides entirely

- Operator finishes the 7shifts OAuth + Tock manual webhook paste.
  Each vendor sink commits its first backfill; flip policy fires
  twice more.
- `demo_mode_state` for the scope:

  | category    | is_demo | flipped_to_live_at |
  |-------------|---------|--------------------|
  | pos         | false   | 2026-05-08T14:32Z  |
  | labor       | false   | 2026-05-08T15:08Z  |
  | reservation | false   | 2026-05-08T15:41Z  |

- Notifier refresh returns three `is_demo = false` rows.
  `DemoModeStateSnapshot.hasDemoCategories` is `false`.

Expected render — `DemoModeBanner` collapses to
`SizedBox.shrink`; the Shift / Variance / Plan / Benchmark tabs sit
flush against the app bar exactly as in the post-onboard production
state. Disconnect later does NOT re-show the banner — the flip is
one-way per `DemoModeFlipPolicy` (`docs/contracts/demo_mode_contract.md`).

### 4. Multi-location operator switching scopes

- Operator opens the **Business** drawer and selects a second
  location ("Montréal Mile End") that has no connections yet.
- `RestaurantScopeNotifier.activateBusinessScope` flips the active
  scope; AppShell's scope listener calls `_syncDemoModeScope`.
- The notifier's `setScope` sees the new key, clears the prior
  snapshot, and pulls fresh rows for the Mile End location — all
  three categories return `is_demo = true`.

Expected render — banner stack returns with three rows (Mile End is
fresh demo data); flipping back to Yorkville hides the banner again.

### 5. Hidden cases (do NOT render)

- **No proxy client wired** (demo / no-Firebase shells, widget tests
  that bypass `bootstrapAndRunApp`): `Provider<SyncProxyClient?>` is
  null, the notifier never refreshes, the banner stays hidden.
- **Signed out**: `_demoModeAuthListenedTo.session == null`,
  `_syncDemoModeScope` calls `notifier.clear()`, banner hides.
- **Notifier provider absent** (some standalone widget tests): the
  banner falls through to `SizedBox.shrink` instead of throwing.

## Manual verification on a build

1. Build `flutter run --release --dart-define=FORGE_FLOW_USE_FIREBASE_AUTH=true
   --dart-define=FORGE_FLOW_PROXY_BASE_URI=https://<staging-proxy>` against
   a staging Postgres seeded with three `demo_mode_state` rows for
   the test operator/location, all `is_demo = true`.
2. Sign in. Confirm three banner rows appear under the app bar.
3. From the admin console (or via direct SQL) flip the POS row to
   `is_demo = false`. Background and foreground the mobile app.
4. Confirm the POS row clears and the other two remain.
5. Flip the remaining rows; foreground the app. Confirm the banner
   disappears entirely and the tab body sits flush with the app bar.

## Known follow-ups

- **Mobile-side vendor connections route**: the banner's contract
  says "Tap CTA: deep-link to vendor connections screen", but mobile
  has no such route today (vendor connections live on operator web /
  admin console). The banner ships informational-only this slice;
  the deep-link CTA lands as part of the mobile-side connections
  surface follow-up.
- **Dedicated `integrations.demo_mode_flip` realtime topic**: the
  refresh trigger uses a permissive `integrations.*` /
  `first_backfill.*` topic-prefix match. Tightening this to a
  dedicated topic that the proxy publishes when
  `DemoModeFlipPolicy` writes is a low-cost follow-up that would
  remove the redundant proxy round-trip on unrelated integrations
  events.
