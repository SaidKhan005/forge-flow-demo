# 8.TS Walkthrough — Toast POS adapter (engineering, lifecycle = `documented`)

**Slice:** 8.TS (Phase 8 — Toast POS adapter, engineered against the
documented Standard / Partner API surface; live HTTP deferred to
`8.TS.live.sandbox` / `8.TS.live.prod`)
**Mode:** `kDemoMode = true` (operator app, deterministic seed). No
live HTTP runs from this slice.
**Date:** 2026-05-04
**Demo start condition:**
- Business date `2026-W18 Mon` (Monday of ISO week 18, 2026).
- Operator: "Demo Diner Co.", Location: "Toronto Yorkville".
- Shift dashboard scope: whole-day.
- All vendor connections empty. `demo_mode_state.is_demo = true` for
  `pos`, `labor`, `reservation`.
- Toast `lifecycle = VendorLifecycle.documented` per
  `lib/integrations/pos/toast_pos_adapter.dart`. Vendor picker shows
  "Coming soon" pill, no Connect button.

This walkthrough is a numbered click-path per the
`docs/CODEX_PROMPT_GENERATION_STANDARD.md` Walkthrough Specificity
section. It anchors on two phases:

- **Steps 1-3 — Picker chrome at lifecycle = `documented`.** The
  operator sees Toast in the picker, sees the "Coming soon" pill,
  taps "Notify me when ready", and lands on a name-the-chrome state
  this lane does NOT wire (the dialog tap behavior ships with
  `11W.8`).
- **Steps 4-9 — Engineering anchor scenarios.** Forged signature →
  403; malformed payload → drop; future-dated event → sanity drop;
  OAuth near-expiry → cron refresh. These exercise the framework
  binding the engineering tests prove.

The slice realizes Hard Promises:
1. **Phase 8 = pure transport swap.** Toast vendor connector writes
   existing canonical fact tables only.
4. **Per-operator isolation is non-negotiable.** Every fact write
   flows through `OperatorScopedRepository.withTenant`.
7. **F&F holds all provider keys server-side.** Toast partner
   credentials live in Cloud Run env / KMS at the framework layer;
   the adapter consumes opaque `ToastCredentialHandle` values.
8. **AI infrastructure is general-purpose.** This adapter binds to
   the existing `PosAdapter` interface; no framework changes.

### 4. Adversarial: forged Toast webhook signature

- A bad actor sends a forged Toast webhook to
  `/v1/webhooks/toast/<operator_id>/<location_id>`.
- The proxy invokes `InboundWebhookHandler.dispatch`. The
  `ToastWebhookSignatureVerifier.verify` call returns
  `valid = false`, `failureReason = 'HMAC mismatch on Toast-Signature
  header'`.
- Expected outcome:
  - **Widget under test:** none (server-side flow).
  - HTTP status `403`.
  - `WebhookOutcome.signatureInvalid`.
  - `inbound_webhook_idempotency.attempt_count` increments to 1.
  - No canonical fact written.
- After three forged retries: `inbound_webhook_dead_letter` row
  with `failure_kind = 'signature_invalid'`. No DLQ tile in
  observability admin (V1 lean cut 2 trim); the row stays for
  forensic read by support via the proxy debug console.

### 5. Adversarial: malformed Toast payload

- Toast (or a forged source) sends a payload with the expected
  signature but an unexpected field shape (e.g., `numberOfGuests` is
  a JSON object instead of an int).
- Expected outcome:
  - **Widget under test:** none.
  - The adapter's `_canonicalize` produces a `covers` field of the
    wrong type; `factSink.upsertOrderFact` throws when the production
    sink validates against the canonical fact schema.
  - `WebhookOutcome.adapterError`.
  - HTTP status `500` so Toast retries.
  - `inbound_webhook_idempotency.attempt_count` increments;
    after three failures the event lands in
    `inbound_webhook_dead_letter` with `failure_kind =
    'adapter_error'`.
  - Queue is NOT poisoned. **No `parse_warnings` or `parse_partial`
    is recorded** (V1 lean cut 2 removed those columns).

### 6. Adversarial: future-dated Toast event

- Toast sends a webhook with `openedDate = now() + 5 days`.
- The handler runs steps 1-3 (signature, binding, idempotency) all
  green. Step 4 — vendor timestamp sanity guard — fires.
- Expected outcome:
  - **Widget under test:** none.
  - `VendorTimestampSanity.evaluate` returns `failed = true`,
    `rule = SanityRule.openedInFuture`,
    `rule!.sqlValue = 'opened_in_future'`.
  - `WebhookOutcome.sanityDropped`.
  - HTTP status `200` (we accept the request from Toast's
    perspective; we just never write a canonical fact).
  - `sanity_log` row written with `rule = 'opened_in_future'`,
    `payload_summary` carrying `opened_at` + `now`.
  - `connector_sync_log` row written with
    `event_kind = 'sanity_drop'`.
  - No canonical fact written. The dashboard's
    business-date-2026-W18-Mon view stays clean.

### 7. Adversarial: closed_at < opened_at

- Toast sends a webhook with `closedDate` an hour BEFORE
  `openedDate`.
- Expected outcome:
  - `VendorTimestampSanity.evaluate` returns `failed = true`,
    `rule = SanityRule.closedBeforeOpened`,
    `rule!.sqlValue = 'closed_before_opened'`.
  - `WebhookOutcome.sanityDropped`.
  - `sanity_log` row written with `rule = 'closed_before_opened'`.
  - `connector_sync_log` row written with `event_kind =
    'sanity_drop'`.
  - No canonical fact written.

### 8. OAuth near-expiry refresh

- Time-travel the test clock so an existing
  `vendor_credentials.token_expires_at` is `now() + 30 minutes`
  (within the 24-hour `kRefreshExpiryHorizon`).
- The `pg_cron` job invokes
  `OAuthRefreshCronRunner.runOnce`. The Toast partner re-issues a
  fresh access token via the documented `client_credentials`
  exchange.
- Expected outcome:
  - `connector_sync_log` row written with `event_kind =
    'auth_refresh'`.
  - `vendor_credentials.consecutive_refresh_failures = 0`.
  - Connection stays `connected`.
  - **No `pg_advisory_lock` involved at V1 (lean cut 2 trim).**
