# 9.UX.grant-payload — Team-users gateway carries authoritative per-grant payload

Date: 2026-04-30
Lane: `gracious-yalow-da6aeb`

## Slice scope

Closes the data-half of the gap left by the
[9.UX.inheritance-hint slice](9.UX.inheritance-hint.0.md). The
role-change dialog already renders an `Active grants` block with
authoritative inheritance hints when `TeamUserListItem.grants` is
populated; until now, the production path left `grants` at its
`const []` default because the gateway's `TeamUserListEntry` shape
projected `coalesce(ur.location_id, u.primary_location_id)` into
`entry.locationId` — ambiguous between a `location`-scoped grant and
an `operator_wide` grant whose owner has a primary-display location.

This slice extends the gateway with an additive `grants` field
carrying the full per-grant scope payload from `user_roles` +
`user_effective_locations`, and wires the production
`_teamUserFromEntry` mapping (now factored into the public
`teamUserListItemFromEntry`) to populate `TeamUserListItem.grants`
end-to-end. The existing 8 widget tests for the rendering branches
stay green; one new production-path integration test pins the live
gateway-shape -> mapper -> dialog flow.

## What landed

**Repository layer** (`lib/infrastructure/persistence/postgres/repositories/users_repository.dart`)
- Extended `selectTeamUsersByOperator` SQL with a per-user `grants`
  jsonb subselect over `user_roles` joined to `roles` (for
  `role_label`) and to a per-grant `user_effective_locations`
  aggregate. One row per user, all active grants nested with
  `(user_role_id, role_id, role_label, scope_type, org_unit_id,
  location_id, source_org_unit_id, effective_location_ids,
  valid_from, valid_until, revoked_at)`.
- The `role_label` join means per-grant labels are resolved
  server-side. The dialog never depends on the section's role-catalog
  load completing before the user list — eliminating the race where
  secondary grant rows could freeze to raw role UUIDs if `listUsers`
  returned before `listRoles`.
- Added `TeamUserGrantRepositoryRow` DTO (carries `roleLabel`) +
  `_projectTeamUserGrants` helper that handles both the live driver's
  `List<Map<...>>` shape and the JSON-string fallback the postgres
  `::text` cast can return. Falls back to `roleId` if a snapshot is
  missing the label (defense-in-depth).
- Existing `locationId` projection (`coalesce(ur.location_id,
  u.primary_location_id)`) is preserved verbatim for backward compat;
  no field renamed, no field removed.

**Gateway DTO** (`lib/services/auth/auth_operations_gateway.dart`)
- New `TeamGrantSnapshot` value type (additive, mirrors the repo row
  shape) with an optional `roleLabel`. Optional so older proxies
  that haven't rolled out the additive label still deserialize
  cleanly — clients fall back through their own resolver chain when
  the field is absent.
- `TeamUserListEntry` gains an additive `grants:
  List<TeamGrantSnapshot>` field defaulting to `const []`. Existing
  callers see no breaking change.

**HTTP transport** (`lib/services/auth/proxy_auth_operations_gateway.dart`)
- `_teamUserFromJson` deserializes the new `grants` array via a new
  `_teamGrantFromJson` helper, including the optional `role_label`.
  Missing field → empty list (backward compat); malformed shape →
  narrow `ProxyAuthOperationsError`.

**Proxy route** (`tool/advisor_proxy/advisor_proxy.dart`)
- `_teamUserToJson` adds `grants: user.grants.map(_teamGrantSnapshotToJson)`.
  Per-grant JSON includes `role_label` when the snapshot carries one
  (it always will from the repository gateway); omits `valid_*` /
  `revoked_at` keys when null to keep the payload tight. No other
  route handler touched (audit-log seam owned by 9.UX.6 is untouched).

**Repository gateway** (`lib/services/auth/repository_auth_operations_gateway.dart`)
- `listUsers` builds `TeamGrantSnapshot` entries from the new
  repository rows, forwarding `roleLabel` straight through. Static
  helper `_teamGrantSnapshotsFromRepositoryRows` is the only
  addition; nothing else in the gateway changed.

**Production mapper** (`lib/forge_flow_app.dart`)
- `_teamUserFromEntry` now delegates to a new public top-level
  `teamUserListItemFromEntry(entry, roleOptions: ...)` so the mapping
  is testable without booting the AppShell widget tree.
- The const-empty-default comment block from the inheritance-hint
  slice is removed (its limitation is now resolved). Per-grant
  `roleLabel` resolves in this order:
  1. `grant.roleLabel` (gateway-supplied, the live source of truth);
  2. `entry.roleLabel` if the grant's `roleId` matches the user's
     primary role (last-resort match);
  3. `roleOptions` lookup (legacy fallback for stale proxies);
  4. raw `roleId` (defense-in-depth — should not happen in
     production because the gateway always supplies a label).
- This means `_teamUsers` never has to be remapped when the role
  catalog publishes — labels are decided server-side, eliminating
  the load-order race where `listUsers` returning before `listRoles`
  would freeze secondary grants to raw role UUIDs.

## Operator walkthrough (kDemoMode = true)

The walkthrough below was verified through the production-path
integration assertion in
`test/team_settings_inheritance_hint_test.dart`:
`production path: TeamUserListEntry.grants flow through
teamUserListItemFromEntry and render inheritance hints`. This test
drives the same `_RoleGrantDialog` that mounts in `Settings → Team →
user-action menu → Change role` under `kDemoMode`, but the input is
the gateway-side `TeamUserListEntry` shape — exactly what the live
`gateway.listUsers` returns to `_AppShellState._loadTeamDataIfNeeded`.

1. **Open Settings → Team.** `TeamSettingsSection` mounts with the
   actor permissioned for `team.users.view` + `team.roles.assign`.
   `_AppShellState._loadTeamDataIfNeeded` calls
   `gateway.listUsers(...)`. The proxy serializes
   `TeamUserListEntry.grants` into the JSON response; the
   `ProxyAuthOperationsGateway` deserializes the array back into
   `List<TeamGrantSnapshot>`; `_teamUserFromEntry` (now thin wrapper
   around `teamUserListItemFromEntry`) maps each snapshot into a
   `TeamUserRoleGrant` on `TeamUserListItem.grants`.
2. **Tap the user-actions menu** for a multi-grant user
   (`team_user_actions_user-prod` in the production-path test). The
   popup lists `Change role` because `team.roles.assign` is held.
3. **Tap `Change role`.** The `_RoleGrantDialog` opens. Its
   `_ActiveGrantsList` reads `widget.user.grants` directly (no demo
   override; no in-section seeding). Three rows render:

   | Grant id              | Role label  | Inheritance hint                          |
   | --------------------- | ----------- | ----------------------------------------- |
   | `grant-prod-op-wide`  | Owner       | `Applies operator-wide`                   |
   | `grant-prod-org-east` | Manager     | `Inherited via East Region (3 locations)` |
   | `grant-prod-loc-1`    | Supervisor  | `Direct at Vancouver Robson`              |

   Asserted via `find.text(...)` in the production-path test.
4. **Singular case (separate fixture):** the existing
   `org_unit grant with 1 effective location renders singular "1 location"`
   test still passes the same dialog with
   `effective_location_ids = ['loc-vancouver']` and the hint reads
   `Inherited via East Region (1 location)`. The same singular-vs-plural
   logic engages on the production path because the gateway emits the
   full `effective_location_ids` array unchanged.
5. **Stale-label case (separate fixture):** the existing
   `org_unit grant whose unit is missing from the loaded options falls back to "org_unit (unknown)"`
   test still passes — the section's lookup-miss fallback never sees a
   crash because the grant object always carries the raw scope ids
   even when the section's option lists no longer carry the label.
6. **Cross-tenant RLS sweep:** the new SQL projection runs inside
   `runInTenantContext` bound to the verified actor's
   `(operator_id, location_id)`. Switching operators in the
   demo gateway returns only that operator's users with their grants;
   no cross-tenant rows leak (the existing 38-test
   `auth_live_binding_test.dart` suite still passes, confirming
   tenant-context behavior is unchanged).

## Role-label race-fix (P2 review feedback)

A reviewer flagged that an earlier draft of this slice could let
secondary grant labels freeze to raw role UUIDs. The original
`teamUserListItemFromEntry` resolved per-grant labels by looking up
`roleOptions` (the in-section role catalog), but Settings starts role
loading and user loading concurrently. If `gateway.listUsers` returns
before `gateway.listRoles`, the mapper runs against the empty default
catalog and falls back to the raw role-id; later role-catalog updates
do not remap the cached `_teamUsers`, so the dialog can keep showing
UUIDs until a forced reload.

Fix: carry `role_label` per grant in the gateway payload, joined
server-side from `roles.display_name` inside the `selectTeamUsersByOperator`
projection. The mapper now reads `grant.roleLabel` first, so labels
are resolved before the user list ever leaves the proxy. The
`roleOptions` argument is kept as a fallback for forward-compat with
older proxies that haven't rolled out the additive field yet — but
on the live path, the gateway-supplied label is the authoritative
source. Two new pinning tests in
`test/forge_flow_app_team_user_grants_test.dart`
(`role-label race: gateway-supplied label wins even when the
role-catalog is empty (no UUID freeze)` and `gateway-supplied label
takes precedence over a stale roleOptions entry`) lock the behavior
in.
