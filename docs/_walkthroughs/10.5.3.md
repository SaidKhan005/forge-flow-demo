# 10.5.3 Walkthrough — Daypart-live primary driver

**Slice:** 10.5.3 (Phase 10.5 — Shift daypart-aware service period view + primary driver)
**Mode:** `kDemoMode = true` (operator app, deterministic seed)
**Date:** 2026-05-03

This walkthrough closes the daypart-live primary-driver teaching that
10.5.2 left queued. The accumulator from 10.5.2 already carries every
input the engine needs (per-period covers, sales, FOH/BOH minutes,
wage dollars, derived CPLH/SPLH/PPA/blended-wage). 10.5.3 extends the
read service to mint the per-period driver via the canonical
`LaborModel.determineLever` and surfaces it as a chip on both the
Shift daypart cards and the Variance daypart lens.

The Hard Promise this slice keeps:

> Shift's whole-day view is authoritative; 10.5 adds daypart
> alongside, never replacing.

Whole-day Shift's primary driver and the Variance whole-week PRIMARY
DRIVER section are byte-identical. The new chip is additive, sits
inside each daypart card, and degrades cleanly when the engine has
no signal.

The 7.58 / 7.61 contracts the chip honors:

- **7.58 Single Source of Truth.** Every minted id flows through
  `LaborModel.determineLever`. The read service never re-derives a
  key from a different formula.
- **7.58 F-2 / F-1 (no `'covers_down'` overclaim).** When no axis
  exceeds its threshold the read service returns null instead of the
  legacy empty-candidate `'covers_down'` fallback. The chip surface
  resolves null through `LeverCards.lookup` and renders the
  `"NO PATTERN YET"` degraded state, not a real lever.
- **7.61 R-STOR-1 / R-PROD-5.** Per-period ids carry the lowercase
  canonical form on the wire (`'covers_down'`, `'ppa_up'`). No
  upper-snake leaks into the notifier's API or the chip text.
- **7.61 R-STOR-7 + R-CONS-1.** Renderers go through
  `LeverCards.lookup`; null returns degrade explicitly instead of
  falling through to a real card.

## Click path (text trace)

### Step 1 — Launch the operator app in demo mode

Run `lib/main_forgeflow.dart` (kDemoMode is pinned in
`lib/data/app_defaults.dart`). The app boots into the operator
shell with the seeded mock replay data source attached and the
active target profile bootstrapped.

**Expected:** Shift dashboard renders with whole-day metrics already
on screen. The scope toggle defaults to **Whole Day**. The Whole
Day surface (SHIFT OUTPUTS / SHIFT INPUTS / FOH PRODUCTIVITY) is
byte-identical to 10.5.2.

### Step 2 — Switch to the daypart lens during simulated Lunch

Set the simulated clock to a Lunch-active instant (Tuesday 12:30,
Lunch 11:00–15:00). Tap the **Daypart** pill above the Shift
content.

**Expected:**

- Time-into-service header strip appears: `● Lunch · 1h 30m in`.
- SERVICE PERIODS sticky group renders one card per defined service
  period.
- **Lunch card**:
  - Carries the `ACTIVE NOW` chip on the right of its header row.
  - Renders the per-period metric grid (covers, sales, PPA, CPLH,
    SPLH, hours, blended wage) reading from
    `ShiftServicePeriodNotifier.buckets['lunch']`.
  - Below the grid, a new chip renders the per-period driver:
    ```
    PRIMARY DRIVER · COVERS ↓
    ```
    The chip text is the short label from
    `LeverCards.lookup(notifier.primaryLeverIdFor('lunch'))` plus a
    direction arrow from `LeverCards.metricDirectionGlyph` (suffix
    `_up` / `_over` → `↑`; `_down` / `_under` → `↓`). **Arrow tracks
    raw metric direction; color tracks favorability** — so when
    covers run below forecast by more than 2 %, the chip is red
    (unfavorable) with `↓` (covers moved down). When wage runs
    below target, the chip is green (favorable) with `↓` (wage
    moved down). The two are independent.
- **Dinner / Late Night cards**: their snapshots are still
  `projected` in the seed, so the buckets are empty. Cards render
  `"No data yet for this period."` placeholder; no driver chip is
  rendered (the chip lives inside the metric-grid branch — empty
  buckets surface no chip at all).

### Step 3 — On-target shift renders the degraded chip

Re-seed (or pick a moment in) a Lunch shift where the bucket is
non-empty but every axis sits within its threshold (covers within
±2 % of forecast, PPA within ±3 %, CPLH within ±5 %).

**Expected:**

- Lunch card still renders the metric grid (the bucket has data).
- The driver chip renders the degraded copy:
  ```
  PRIMARY DRIVER · NO PATTERN YET
  ```
  colored muted gray. **The legacy `'covers_down'` fallback is not
  surfaced** — the read service returned null because no axis
  exceeded its threshold (per 7.58 F-2). The chip routes through
  `LeverCards.lookup`, which returns null for any id outside the 16
  catalog ids; the chip renders `"NO PATTERN YET"` rather than
  falling through to a real card.

### Step 4 — Switch back to whole-day

Tap **Whole Day**.

**Expected:** SERVICE PERIODS, the time-into-service header, the
per-period cards, and their driver chips disappear. SHIFT OUTPUTS,
SHIFT INPUTS, and FOH PRODUCTIVITY return — byte-identical to the
pre-10.5.3 view. The whole-day primary lever (rendered by
`ShiftDashboardReadModel`) is unchanged.

### Step 5 — Open Variance → daypart lens

Navigate to the Variance tab → This Week. Tap the **Daypart** pill
in the `Whole Week | Daypart` segmented control.

**Expected:**

- WTD vs PLAN, DOLLAR IMPACT, PRIMARY DRIVER, and FULL WEEK
  PROJECTION collapse.
- `SERVICE PERIODS · TODAY` sticky group appears.
- Each per-period card renders the same metric block 10.5.2 shipped,
  followed by the same driver chip the Shift surface shows. The two
  surfaces read from the same `ShiftServicePeriodNotifier` — the
  drivers reconcile by construction.
- Empty periods render `"No data yet for this period."` and no
  chip.

Tap **Whole Week** to restore the authoritative WTD view.

**Expected:** the four whole-week sections come back unchanged and
the whole-week PRIMARY DRIVER section reads from `WeekData`,
unaffected by the daypart driver work.

### Edge — Restaurant has no usable IANA timezone

Same posture as 10.5.2: `missingTimezone = true`, the buckets map is
populated with empty accumulators, and the daypart cards render the
explicit "Timezone not configured" copy. Because every bucket is
empty, no driver chip renders (the chip only appears inside the
`hasData` branch). The notifier's
`primaryLeverIdFor('<period>')` returns null for every period in
this state because (a) the buckets are empty, and (b) the read
service short-circuits to null when `bucket.hasAnyData == false`.

## Trace summary

```
OpenShiftSnapshot[s] (per business date)
  ├── synthesizeCanonicalFactsFromSnapshots →  POS lines + labor punches
  │     └── ShiftServicePeriodReadService.build
  │           └── Map<ServicePeriodId, ServicePeriodAccumulator>
  └── forecastCoversByPeriodFromSnapshots →  Map<periodId, forecastCovers>

ActiveTargetProfile (WageStandardContextService.loadOrBootstrap…)
  └── targetCPLH / targetSPLH / targetPPA / fohWage / bohWage

ShiftServicePeriodReadService.computePrimaryLevers
  ├── per period:
  │     ├── pre-check: profile present, hasAnyData, forecastCovers > 0
  │     ├── threshold scan: any axis above threshold?
  │     │     covers ±2%, ppa ±3%, cplh ±5%, splh ±5%, foh/boh wage ±3%
  │     ├── if no axis fires → null            (7.58 F-2 — no covers_down overclaim)
  │     └── else → LaborModel.determineLever(…) (7.58 single source of truth)
  └── Map<periodId, String?>  (lowercase canonical or null)

ShiftServicePeriodNotifier
  ├── _primaryLeverIds (the map above)
  ├── primaryLeverIdFor(periodId)         →  String?
  └── primaryLeverCardFor(periodId)        →  LeverCardData?  (via LeverCards.lookup)

Shift daypart card / Variance daypart card
  └── _DaypartDriverChip / _DaypartVarianceDriverChip
        ├── card present → "PRIMARY DRIVER · {SHORT} {↑|↓}" colored by isFavorable
        └── null         → "PRIMARY DRIVER · NO PATTERN YET" muted
```

## Permission gating

No new permission keys. The Shift daypart card and the Variance
daypart lens are read-only operator views; the chip surfaces a
recommendation, not a command (Hard Promise #6). The chip respects
the same auth gates as the surfaces it sits inside (`Shift` /
`Variance > This Week`); per-permission-key changes belong to
`Phase 9`, not 10.5.

## Boundary checks

- **Whole-day Shift surface is byte-identical when scope = Whole
  Day.** The chip lives inside `_DaypartScaffoldCard`, only used
  when scope = Daypart. The whole-day primary lever continues to
  flow through `ShiftDashboardReadModel.primaryLeverId` /
  `primaryLeverCard` — untouched.
- **Variance whole-week PRIMARY DRIVER section is byte-identical
  when scope = Whole Week.** `WeekData.primaryLeverId` and the
  PRIMARY DRIVER sliver are untouched.
- **Driver computation respects 7.58 F-2.** Empty-candidate fallback
  is intercepted before the engine: if no axis exceeds its
  threshold, the read service returns null directly; the engine's
  legacy `'covers_down'` literal cannot reach the notifier or the
  chip. The pre-call gate replicates only the threshold checks
  (it does not re-derive the id) so 7.61 R-PROD-1 / 7.58 Single
  Source of Truth remain intact.
- **Lowercase canonical only.** Every id minted by the read service
  is lowercase snake_case (R-STOR-1). `_DaypartDriverChip` reads
  the resolved `LeverCardData.shortLabel` rather than the id, so
  the chip text is the canonical operator-facing copy and never
  leaks the storage form.
- **Renderer null-safety.** Both chips use
  `notifier.primaryLeverCardFor(periodId)` (which itself routes
  through `LeverCards.lookup`). Null surfaces as
  `"PRIMARY DRIVER · NO PATTERN YET"` — never falls through to
  `LeverCards.coversDown` (the pre-7.58.UX.5 silent overclaim
  pattern).
- **No new schema, no migration drift.** The notifier reads from
  the same SQLite tables 10.5.2 already consumed; no
  `db/migrations/*.sql` was edited.
- **Per-period plan targets remain a known limitation.**
  `ActiveTargetProfile` is restaurant-level, so every period uses
  the same target rates today. The chip's accuracy will improve
  once per-period plan targets ship (tracked in the Phase 10.5
  doc's Placeholder Notes); the API surface (`primaryLeverIdFor`)
  does not change.
- **Hours-flex levers are intentionally skipped.** Per-period
  scheduled hours are not tracked at this slice; the read service
  passes null to the optional `*_hours_*` parameters so those
  axes never fire spuriously.
- **SPLH axis is BOH-only.** Per 7.58, SPLH is the BOH productivity
  axis. The engine consumes `bucket.bohSplh` (sales / BOH hours)
  rather than `bucket.splh` (sales / total minutes), and the axis
  is skipped when `bohMinutes == 0`. Without that gate, a FOH-only
  period would mint `splh_up` / `splh_down` off the FOH-blended
  ratio — pinned in
  `test/services/shift_service_period_primary_driver_test.dart`.
- **Chip arrow tracks metric direction, color tracks favorability.**
  The chip uses `LeverCards.metricDirectionGlyph` (id-suffix
  derived) for `↑` / `↓` and `LeverCardData.isFavorable` for the
  green/red accent. The two are independent: `foh_wage_down` is
  favorable (green) but its arrow is `↓`; `foh_wage_up` is
  unfavorable (red) but its arrow is `↑`. Both Shift and Variance
  chips share the helper, so they cannot drift.
- **Demo synthesis path unchanged.** The new wiring uses the same
  `OpenShiftSnapshot` records the 10.5.2 synthesizer already
  consumes; no new fact source. The Phase 8 path will replace the
  forecast-covers helper with a real fact loader without changing
  the read service or the chip.
