# 9.UX.5 - Settings Account Active Sessions

Date: 2026-04-30

## Scope

Add a self-service Active Sessions viewer to Settings -> Account. The
operator sees their own `auth_sessions` ledger rows with device /
network metadata, can revoke a single non-current session, and can
sign out of all devices. Reads and writes flow through
`AuthOperationsGateway` -> proxy -> Postgres so the Flutter client
never touches the database directly and per-user RLS still gates
cross-user reads server-side.

## Operator Walkthrough (`kDemoMode = true`)

1. Launch ForgeFlow in demo mode (`flutter run -t lib/main_forgeflow.dart`)
   and sign in as the demo operator
   (`demo.operator@forgeflow.test` / `forge-flow-demo`).
2. Open Settings -> Account.
3. Confirm the **Active sessions** section header renders below the
   **Account** card (text trace:
   `find.text('Active sessions')` resolves and the
   `active_sessions_row_demo-session-current` widget key is present).
4. Verify three demo devices render in last-seen order with device
   labels, approximate location (CA + IPv4), and last-active timing:
   - "Forge & Flow app · iOS" tagged with the green `THIS DEVICE`
     pill (`active_sessions_current_badge`); revoke action is
     suppressed and replaced by a `Current` label.
   - "Safari · iPad" with a Revoke button.
   - "Chrome · Windows" with a Revoke button.
5. Tap **Revoke** on the iPad row
   (`active_sessions_revoke_demo-session-tablet`). Confirm the row
   disappears from the list and a snackbar reads
   "Sign-out request sent to Safari · iPad."
6. Tap **Sign out of all devices**
   (`active_sessions_sign_out_everywhere`). Confirm the
   "Sign out everywhere?" dialog renders, tap **Sign out everywhere**
   to confirm, and verify:
   - the session list collapses to empty,
   - `AuthSessionNotifier.signOutAllSessions()` runs (the demo shell
     forwards the existing notifier callback so the local device is
     signed out and refresh-token revocation kicks in for the live
     stack), and
   - the Settings route pops back to the sign-in screen on the next
     frame.

## Contract Notes

- Reads route through `AuthOperationsGateway.listActiveSessions` ->
  `GET /v1/auth/sessions` (auth-gated; the proxy resolves
  `(operator_id, location_id, user_id)` from the verified Firebase
  bearer token before delegating to the gateway). The Flutter
  `_authOperationsGateway` reads `device_label`, `user_agent`, `ip`,
  `geo_country`, `created_at`, `last_seen_at`, and the optional
  `revoked_*` fields off the projection.
- Single revokes go through `AuthOperationsGateway.revokeSession` ->
  `POST /v1/auth/session/revoke` (existing B6 route; reused so the
  ledger mutation contract stays consistent).
- Sign-out-all goes through `AuthOperationsGateway.signOutAll` ->
  `POST /v1/auth/session/revoke-all` (existing B6 route). After the
  proxy returns, the section invokes the
  `onSignOutAllDevices` callback the Account tab passes from
  `AuthSessionNotifier.signOutAllSessions()`, which clears local
  storage, fires Firebase refresh-token revocation, and transitions
  the notifier to `AuthSessionUnauthenticated` so the Flutter client
  is not stranded in a stale signed-in state.
- Per-user RLS on `auth_sessions` is the authoritative gate. Reads
  bind `(operator_id, location_id, user_id)` via
  `runInTenantContext`; the WHERE clause already pins
  `user_id = @user_id::uuid`, and the policy refuses cross-user rows
  even if a future caller accidentally widens the predicate.
- Demo mode (`kDemoMode = true` or no live gateway): the section
  installs `DemoActiveSessionsGateway` (in-memory) seeded with three
  stable rows from `DemoAuthSessionsFixtures` so the walkthrough can
  exercise the click path without staging.

## Notes

- No new permission keys: the surface is self-service so the actor's
  verified Firebase bearer token alone authorizes the read / revoke.
- Acceptance for cross-user isolation: the proxy ignores any
  client-supplied `user_id`; only the JWT-resolved scope reaches
  `listActiveSessions`. Future surfaces that need to view another
  user's sessions belong on the admin path
  (`/v1/admin/auth/users/<id>/sessions`) and are out of scope here.
