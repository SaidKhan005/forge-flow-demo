# 10.5.0 Walkthrough — Shift daypart toggle scaffold

**Slice:** 10.5.0 (Phase 10.5 — Shift daypart-aware service period view + primary driver)
**Mode:** `kDemoMode = true` (operator app, deterministic seed)
**Date:** 2026-05-02

This walkthrough exercises the surface-only seam that opens the
daypart lens on the Shift dashboard. The slice ships a segmented
"Whole Day | Daypart" toggle plus a SERVICE PERIODS scaffold that
renders one card per restaurant-scoped service-period definition
(Lunch, Dinner, Late Night from `demoDefinitions`) with a live
ACTIVE NOW chip on the period containing the wall clock. The live
bucketing engine, per-period covers/sales/CPLH metrics, primary-
driver teaching, time-into-service header, and Settings → service
periods editor land in subsequent 10.5 slices.

The Hard Promise this slice realizes:

> Shift's whole-day view is authoritative; 10.5 adds daypart
> alongside, never replacing.

Whole-day stays the default scope on first paint and stays the
source of truth — the toggle is additive. Switching scopes is a
local UI preference; the read model and notifier are unchanged.

## Time-source contract

The ACTIVE NOW chip on each scaffold card is the only piece of this
slice that touches the live clock. Its time-source rule mirrors
`current_state_boundary_monitor.dart` and the time-boundary
contract:

1. **Restaurant-local now, not device clock.** When the
   `RestaurantScopeNotifier` exposes a `RestaurantLocation` with a
   non-empty IANA `businessTimezone`, the scaffold reads `now` via
   `tz.TZDateTime.now(loc)`. When the timezone is missing or
   unrecognized, the scaffold returns null and renders zero ACTIVE
   chips — no fallback to `DateTime.now()`. Tests inject
   restaurant-local time through `ShiftDashboard.clockOverride`.
2. **Business-date weekday, not wall-clock weekday.** The active-
   period resolver runs `BusinessDateResolver.resolve` against the
   restaurant-local `now` plus a `businessDayStartLocalTime`
   cutoff (default `04:00` until the
   `RestaurantTimingConfigReadService` wiring lands in this widget
   tree — explicitly noted in the constant declaration). The
   business date's weekday — not `now.weekday` — is the value
   compared against `ServicePeriodDefinition.applicableDays`. This
   is what makes Sunday 01:30 calendar still count as Saturday's
   business day for a `Fri/Sat`-only Late Night period.
3. **Boundary tie-break.** The scaffold honors the same
   `[startLocalTime, endLocalTime]` inclusive-end / inclusive-start
   rule the phase doc locks (event at exact `endLocalTime` belongs
   to the ending period; event at exact `startLocalTime` belongs to
   the starting period).
4. **Live ticking.** `_DaypartScaffoldSectionState` runs a
   `Timer.periodic(Duration(seconds: 30), ...)` (matches the
   header live clock cadence) that calls `setState` on every tick.
   The chip therefore stays accurate while the operator parks on
   the daypart view across `15:00`, `17:00`, `23:00`, or `02:00`
   without any other notifier firing. The timer is cancelled in
   `dispose`.

## Demo seed shape (relevant for this walkthrough)

`MockReplayDataSeed.generateForDate(<today>)` produces the same 14
current-week shifts the existing Shift visual tests use; this slice
does not read or change the seed. The daypart scaffold reads
exclusively from `ServicePeriodDefinitionResolver.demoDefinitions`,
which today carries:

- **Lunch** — `11:00`–`15:00`, weekdays Mon–Fri.
- **Dinner** — `17:00`–`23:00`, every day.
- **Late Night** — `23:00`–`02:00`, Fri & Sat only,
  `rollsPastMidnight: true`.

Persisted timing config and a Settings editor for these definitions
are part of the 10.5 foundation pre-requisite list and remain
deferred to a later slice.

  Lunch (`L`), Dinner (`D`), Late Night (`LN`). Each card shows the

  (e.g. `11:00 – 15:00`), and a muted "Daypart bucketing not yet
  wired." subline.
- If the wall clock falls inside a period that's applicable today,
  that one card carries an `ACTIVE NOW` chip on the right of its
  header row. With the demo seed's default Friday business date and
  a real-time clock landing in Dinner (17:00–23:00), Dinner is the
  active card.

The scope toggle stays visible at the top of the scroll area; the
"Daypart" pill now carries the highlighted accent.

### Step 4 — Restore the authoritative whole-day view

Tap the "Whole Day" pill.

**Expected:** SERVICE PERIODS disappears and the SHIFT OUTPUTS,
SHIFT INPUTS, and FOH PRODUCTIVITY sections come back exactly as
they were in Step 2. The whole-day notifier is unchanged across
the round trip — no refresh fires.

### Step 5 — Pull-to-refresh works in either scope

In either scope, drag down to trigger the `RefreshIndicator`.

**Expected:** `ShiftDashboardNotifier.refresh()` fires (same as
before this slice). The local scope state is preserved across the
refresh — switching scope is a UI preference, not a data fetch.

### Edge — clock between periods

If the wall clock falls outside every applicable period (e.g.
Tuesday at 16:00, after Lunch ends and before Dinner starts), no
card carries an `ACTIVE NOW` chip. All three cards still render
with their windows. This case is covered by
`test/shift_dashboard_daypart_toggle_widget_test.dart` →
`'no ACTIVE NOW chip when the clock is between periods'`.

### Edge — Late Night across midnight (business-date wrap)

Late Night's `rollsPastMidnight: true` flag plus the business-day
rollover means `01:30` on a Saturday morning still falls inside
Friday's business day, and `01:30` on Sunday morning still falls
inside Saturday's business day. The scaffold's
`_resolveActivePeriodId` runs `BusinessDateResolver.resolve` to
project to the right business date first, then uses **that
date's weekday** for the `applicableDays.contains` check. The
clock-window check returns the period when
`minutes >= start || minutes <= end`. This case is covered by two
tests in `test/shift_dashboard_daypart_toggle_widget_test.dart`:

- `'Late Night ACTIVE NOW surfaces post-midnight on rolls-past-midnight days'`
  — Sat 01:30 calendar = Fri business day (weekday 5),
  applicable = `[5, 6]`, ACTIVE.
- `'ACTIVE chip uses business-date weekday, not wall-clock weekday'`
  — Sun 01:30 calendar = Sat business day (weekday 6),
  applicable = `[5, 6]`, ACTIVE. This is the regression test for
  the device-clock-as-truth bug; pre-fix the chip would have
  silently disappeared at the calendar rollover.

### Edge — chip stays in sync without external rebuilds

Park on the daypart view at `14:55`. At `15:01` Lunch ends; at
`17:00` Dinner starts. The chip must follow the live clock without
the operator toggling scope or pull-to-refreshing. The scaffold's
30-second `Timer.periodic` re-runs the active-period resolver on
each tick, so the chip vacates Lunch shortly after `15:00:00` and
re-anchors on Dinner shortly after `17:00:00`. This case is
covered by
`test/shift_dashboard_daypart_toggle_widget_test.dart` →
`'ACTIVE chip refreshes on the periodic ticker when the clock crosses a service-period boundary'`.

### Edge — restaurant has no usable IANA timezone

If `RestaurantLocation.businessTimezone` is empty or not present
in the timezone DB, the scaffold returns null `localNow` and zero
cards carry an `ACTIVE NOW` chip. The cards still render with
their windows — the operator sees the lens; they do not see a
chip computed from the device clock. This matches the boundary
monitor's `MissingTimezoneError` posture (refuse to fall back).
Covered by
`test/shift_dashboard_daypart_toggle_widget_test.dart` →
`'no ACTIVE chip when restaurant scope has no usable IANA timezone and clockOverride is unset'`.

## Boundary checks

- **Whole-day surface is byte-identical when `_scope ==
  ShiftScope.wholeDay`.** The three `SliverMainAxisGroup`s now live
  inside `_ShiftDashboardState._wholeDaySlivers(rm)`; the bodies
  are the same widgets in the same order with the same inputs. The
  pre-existing `shift_visual_widget_test.dart` smoke test still
  passes verbatim.
- **No data-layer change.** `ShiftDashboardNotifier`,
  `ShiftDashboardReadModel`, `OpenShiftSnapshot`,
  `ShiftServiceAdapter`, the `ShiftService` close-shift path —
  none touched. This slice introduces zero new fields on the read
  model and zero new methods on the notifier.
- **No bucketing engine.** Cards do not display covers, sales,
  CPLH, or hours per period. The "Daypart bucketing not yet wired."
  subline makes the placeholder state explicit. Future slices will
  swap the placeholder out for live numbers using a
  `ShiftServicePeriodReadService` per the phase-10.5 plan; this
  slice does not pre-bake any of that surface.
- **No persisted timing config dependency.** The scaffold reads
  `ServicePeriodDefinitionResolver.demoDefinitions` directly
  (the same fallback every other consumer uses today). The phase
  doc's "close the deferred time-boundary foundation" prerequisite
  remains a prerequisite for live bucketing; it is not a
  prerequisite for opening the surface seam.
- **Settings editor untouched.** `lib/screens/settings_screen.dart`
  is not modified by this slice. The Frontend Exposure entry for
  the editable Settings → Service periods controls remains a later
  10.5 slice.
- **Test seam unchanged in shape.** The existing
  `ShiftDashboard.clockOverride` static is reused as the test-only
  source for the scaffold's restaurant-local clock, matching the
  live clock's seam. The override returns a `DateTime` already
  treated as restaurant-local. Tests keep using the same
  `tearDown(() { ShiftDashboard.clockOverride = null; })` pattern.
  Production code never reaches the override path — it always
  reads `tz.TZDateTime.now(loc)`.
- **No raw `DateTime.now()` in the active-period path.** The only
  uncached `DateTime` reads in the scaffold are guarded: the
  override path (test-only), and the `tz.TZDateTime.now(loc)`
  branch (real timezone). The "no usable IANA timezone" branch
  returns null and renders no chip rather than falling back. This
  matches `current_state_boundary_monitor.dart`'s
  `MissingTimezoneError` posture.
- **No new tracker writes by this commit.** Tracker movement
  (10.5 from queued to active) is part of the slice handoff, not a
  separate downstream task.
