# 8R.TC Walkthrough — Tock reservation adapter (engineering, lifecycle = `documented`)

**Slice:** 8R.TC (Phase 8R — Tock reservation adapter, engineered
against the documented Tock reservation API surface; live HTTP
deferred to `8R.TC.live.sandbox` / `8R.TC.live.prod`)
**Mode:** `kDemoMode = true` (operator app, deterministic seed). No
live HTTP runs from this slice.
**Date:** 2026-05-04
**Demo start condition:**

- Business date `2026-W18 Mon` (Monday of ISO week 18, 2026).
- Operator: "Demo Diner Co.", Location: "Toronto Yorkville".
- Shift dashboard scope: whole-day.
- All vendor connections empty. `demo_mode_state.is_demo = true` for
  `pos`, `labor`, `reservation`.
- Tock `lifecycle = VendorLifecycle.documented` per
  [lib/integrations/reservation/tock_reservation_adapter.dart](../../lib/integrations/reservation/tock_reservation_adapter.dart).
  Vendor picker shows "Coming soon" pill, no Connect button.

This walkthrough is a numbered click-path per the
`docs/CODEX_PROMPT_GENERATION_STANDARD.md` Walkthrough Specificity
section. It anchors on three phases:

- **Steps 1-3 — Picker chrome at lifecycle = `documented`.** The
  operator sees Tock in the Reservations picker, sees the "Coming
  soon" pill with a Premium-tier tooltip, and taps "Notify me when
  ready" (chrome only at this slice; the dialog tap behavior ships
  with `11W.8`).
- **Steps 4-7 — manualPaste + Premium-tier connect anchor.** Connect
  flow → webhook URL + signing-secret display → operator-facing
  paste instructions → "Connecting (webhook pending)" → first signed
  webhook arrives → "Connected".
- **Steps 8-12 — Engineering anchor scenarios.** Forged signature →
  403; malformed payload → drop; future-dated event → sanity drop;
  disconnect / reconnect watermark.

The slice realizes Hard Promises:

1. **Phase 8 = pure transport swap.** Tock vendor connector writes
   the existing reservation canonical fact tables only.
4. **Per-operator isolation is non-negotiable.** Every fact write
   flows through `OperatorScopedRepository.withTenant`.
7. **F&F holds all provider keys server-side.** Tock API keys live
   in `vendor_credentials` at the framework layer; the adapter
   consumes opaque `TockCredentialHandle` values.
8. **AI infrastructure is general-purpose.** This adapter binds to
   the existing `ReservationAdapter` interface; no framework
   changes.

### 4. (Engineering only — Connect path on lifecycle = `production_credentialed`) Connect flow

> Lifecycle = `documented` hides the Connect button; the connect
> flow is exercised only after `8R.TC.live.prod` promotes the
> lifecycle. Documenting it here lets the engineering tests prove
> the manualPaste contract end-to-end.

- Operator (with Tock Premium-tier API key in hand) taps **Connect**
  on the Tock row.
- F&F admin shows a key-paste form:
  - **Field:** Tock API key (received from `integrate@tockhq.com`).
  - **Field:** Tock business id.
- Operator pastes both and taps **Verify and connect**.
- Adapter calls `TockApiClient.verifyApiKey`. On success, F&F renders:
  - **Widget under test:** `Key('vendor_picker_tock_connect_paste')`.
  - **Status pill:** **"Connecting (webhook pending)"** (read from
    `connector_connection.metadata.webhook_pending`).
  - **Webhook URL** display + Copy button.
  - **Signing secret** display + Copy button (one-time reveal —
    F&F never shows the secret again; the framework persists it in
    `vendor_credentials`).
  - **Numbered paste instructions** matching
    [docs/integrations/tock/webhook_signature.md](../integrations/tock/webhook_signature.md)
    "Manual paste instructions" section.

### 5. Operator pastes webhook URL + signing secret in Tock dashboard

- Operator follows the on-screen steps:
  1. Sign in to Tock dashboard.
  2. Settings → Integrations → Webhooks → Add webhook.
  3. Paste F&F's webhook URL into Tock's URL field.
  4. Paste F&F's signing secret into Tock's signing-secret field.
  5. Subscribe to **Reservation updates** events.
  6. Save webhook in Tock.
- Operator returns to F&F and taps **I've pasted both — verify**.
- F&F begins waiting for the first signed webhook from Tock.
- **Widget under test:** `Key('vendor_picker_tock_paste_verify')`.
- **Expected status pill:** still **"Connecting (webhook pending)"**.

### 6. First signed webhook arrives → status flips to Connected

- Tock sends a `reservation.updated` event signed with the same
  secret the operator pasted. The framework's
  `InboundWebhookHandler.dispatch` runs steps 1-3 (signature,
  binding, idempotency); `TockWebhookSignatureVerifier` returns
  `valid = true`. The adapter's `handleWebhook` writes the canonical
  fact.
- F&F admin chrome flips:
  - `connector_connection.metadata.webhook_pending = false`.
  - Status pill: **"Connected"**.
  - **Widget under test:** `Key('vendor_picker_tock_status')`.
  - The "In the Books" aggregate count on Shift gains a
    freshness indicator pulled from connector status.

### 7. 60-day backfill commits in the background

- The framework enqueues a 60-day backfill on connect
  (`firstBackfillStarted: true`). The Cloud Run Job invokes
  `TockReservationAdapter.backfill` with the documented
  `windowStart = now - 60d`, `windowEnd = now` window.
- For each page returned by `reservations/search`, the adapter
  invokes the framework's sanity hook BEFORE each canonical fact
  write (mandatory framework call #1).
- Watermark persists per batch (mandatory framework call #3).
- **Expected named values** (smoke fixture
  `tockBackfillPage1Reservations()`):
  - 3 reservations committed; one each for `EXPECTED`, `SEATED`,
    `LEFT`.
  - `result.recordsWritten` = 3.
  - `sink.watermarks.length` = 1 (single batch).

### 8. Adversarial: forged Tock webhook signature

- A bad actor sends a forged Tock webhook to
  `/v1/webhooks/tock/<operator_id>/<location_id>`.
- The proxy invokes `InboundWebhookHandler.dispatch`. The
  `TockWebhookSignatureVerifier.verify` call returns
  `valid = false`, `failureReason = 'HMAC mismatch on X-Tock-Signature
  header'`.
- Expected outcome:
  - **Widget under test:** none (server-side flow).
  - HTTP status `403`.
  - `WebhookOutcome.signatureInvalid`.
  - `inbound_webhook_idempotency.attempt_count` increments to 1.
  - No canonical fact written.
- After three forged retries: `inbound_webhook_dead_letter` row with
  `failure_kind = 'signature_invalid'`. No DLQ tile in observability
  admin (V1 lean cut 2 trim); the row stays for forensic read by
  support via the proxy debug console.

### 9. Adversarial: malformed Tock payload

- Tock (or a forged source with the right secret) sends a payload
  with the expected signature but an unexpected field shape (e.g.,
  `partySize` is a JSON object instead of an int).
- Expected outcome:
  - **Widget under test:** none.
  - The adapter's `_canonicalize` produces a `party_size` field of
    the wrong type; `factSink.upsertReservationFact` throws when the
    production sink validates against the canonical fact schema.
  - `WebhookOutcome.adapterError`.
  - HTTP status `500` so Tock retries.
  - `inbound_webhook_idempotency.attempt_count` increments; after
    three failures the event lands in `inbound_webhook_dead_letter`
    with `failure_kind = 'adapter_error'`.
  - Queue is NOT poisoned. **No `parse_warnings` or `parse_partial`
    is recorded** (V1 lean cut 2 removed those columns).

### 10. Adversarial: future-dated Tock reservation event

- Tock sends a webhook with `serviceDateTimestamp = now() + 5 days`.
- The handler runs steps 1-3 (signature, binding, idempotency) all
  green. Step 4 — vendor timestamp sanity guard — fires.
- Expected outcome:
  - **Widget under test:** none.
  - `VendorTimestampSanity.evaluate` returns `failed = true`,
    `rule = SanityRule.openedInFuture` (the reservation analog —
    sanity rule applies to `serviceDateTimestamp` per the
    framework's reservation policy entry).
  - `WebhookOutcome.sanityDropped`.
  - HTTP status `200` (we accept the request from Tock's
    perspective; we just never write a canonical fact).
  - `sanity_log` row written; `connector_sync_log` row written with
    `event_kind = 'sanity_drop'`.
  - No canonical fact written.

### 11. Disconnect → reconnect watermark preserved

- Operator taps **Disconnect** on the Tock row.
- `TockReservationAdapter.disconnect` returns
  `credentialsWiped: true`, `webhookUnregistered: false`,
  `watermarkPreserved: true`. F&F admin shows a follow-up pill:
  - **Copy:**
    > **One last step in Tock**
    > Tock asks you to remove the webhook from your dashboard
    > yourself; we can't do it for you. Sign in to Tock → Settings →
    > Integrations → Webhooks → delete the F&F entry. We've already
    > stopped trusting it on our side, so leaving it briefly is
    > harmless — just neater to remove.
- Operator reconnects later (same API key + business id). The
  framework's `connector_sync_watermark.cursor_token` from the prior
  connection is preserved; the new connect resumes from that cursor
  with no rewind and no skip.
- **Widget under test:** `Key('vendor_picker_tock_disconnect_chrome')`.
