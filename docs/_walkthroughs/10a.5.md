# 10a.5 Walkthrough — last_event_id replay on reconnect

**Slice:** 10a.5 (Phase 10a — Shared Multi-Device State V1)
**Mode:** Real WebSocket against the proxy + in-process publisher's per-(operator, topic) ring buffer + per-device SQLite watermark
**Date:** 2026-05-05

This walkthrough exercises the reconnect-resume seam: a connected
client picks up missed events the next time the WebSocket opens
(across either an in-process disconnect OR a fresh process start),
bounded by the 5-minute backlog window. Beyond that window the
server signals `replay_truncated` and the client falls back to a
one-shot Postgres refresh.

The Hard Promise this slice realizes:

> Per-operator isolation is non-negotiable. RLS-ready schema from day
> one; Phase 9 enforces.

Every replay query is scoped to the connecting JWT's operator id; the
publisher's ring is keyed `(operator_id, topic)` so a query for
operator A never inspects operator B's slice; the route applies a
defense-in-depth check on every replayed frame; the per-device
SQLite watermark is keyed `(operator_id, topic)` so a different
operator signing in on the same device cannot inherit the previous
operator's cursor.

## Demo walkthrough (4 steps)

1. **Connect with no watermark.**
   * Sign in fresh on the operator app (`main_forgeflow.dart`,
     `FORGE_FLOW_USE_FIREBASE_AUTH=true`).
   * The shell's `RealtimeAuthBridge` calls `setTenantContext`. The
     watermark store has no row yet, so the in-memory cursor stays
     null and the WebSocket upgrade omits `?last_event_id=...`.
   * Confirm the proxy log line `realtime.subscribed` carries the
     operator id and `auth_carrier`. No `realtime.replay_*` lines
     fire — first-connect path.

2. **Live event arrives + watermark advances.**
   * Trigger a producer that enqueues into `event_outbox` for the
     operator (e.g. close a shift to fire
     `rollup.invalidate.variance_week`).
   * The bridge claims the row, the in-process publisher fans the
     event out, the route forwards the JSON frame.
   * In SQLite, the row in `realtime_subscription_watermark` for
     `(operator_id, 'rollup.invalidate.variance_week')` now carries
     the new `event_id` and `occurred_at`.

3. **Simulate WebSocket disconnect.**
   * Kill the app process (cold restart) OR drop the network
     interface for ~10 seconds and let the back-off curve fire.
   * No additional events are produced during the disconnect window.

4. **Reconnect with watermark — 3 missed events replay before live.**
   * While the client is offline, fire 3 producer events with
     monotonically increasing `occurred_at` for the same operator.
   * Bring the client back online. `setTenantContext` (or the
     reconnect timer's `_connect`) hydrates the in-memory cursor
     from the SQLite watermark and forwards it as
     `?last_event_id=<uuid>` on the upgrade URI.
   * The route's `realtimeReplayFetcher` closure runs the resolver
     per-topic, accumulates the 3 missed events, sorts by
     `occurred_at`, and writes them to the wire BEFORE any live
     frames flow.
   * Confirm log lines: `realtime.replay_delivered` with
     `event_count: 3`, then live frames continue normally.

## Stale-watermark fallback (operator-walkthrough variant)

If the disconnect lasts longer than 5 minutes (the contract floor in
`kRealtimeReplayWindow` / `kRealtimeReplayBacklogWindow`), the
resolver returns `RealtimeReplayStaleSentinel.instance` and the
route emits `{"control":"replay_truncated"}`. The client clears its
in-memory cursor on receipt; the UI consumer (today: notifiers wired
to the `replayTruncated` stream) issues a one-shot Postgres refresh
on the affected tables. Live frames continue on the same socket
without a reconnect.
