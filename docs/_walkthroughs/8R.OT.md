# 8R.OT Walkthrough — OpenTable reservation adapter (lifecycle = documented)

**Slice:** 8R.OT (Phase 8R — engineer-all-17 Wave B; OpenTable reservation adapter; partnership-only)
**Mode:** `kDemoMode = true` (operator app, deterministic seed)
**Date:** 2026-05-04
**Lifecycle target at slice close:** `VendorLifecycle.documented`

This slice ships the OpenTable reservation adapter at lifecycle =
`documented` per the engineer-all-17 doctrine
(`memory/project_phase_8_engineer_all_17_doctrine.md`). OpenTable is
**partnership-only** at the documentation level — no public developer
portal exists. Engineering proceeds against the published
reservation-data field shape (the industry-standard reservation
envelope) so the moment OpenTable issues the partner doc + sandbox
credentials, only the small `8R.OT.live.sandbox` slice remains. EVERY
field-mapping assumption is captured as a `verify_in_live_sandbox:
true` row in `documentedPerOpentableV1FieldMapping` so the live
diff is bounded. Live HTTP is deferred to `8R.OT.live.sandbox` /
`8R.OT.live.prod` (Wave D, partnership-gated).

The slice respects every Hard Promise from `CLAUDE.md`:

1. Pure transport — the adapter writes existing canonical reservation
   tables only; no business logic in `lib/services/*` is touched.
2. Demo-mode persists — the same vendor-picker chrome renders in
   `kDemoMode = true` and `kDemoMode = false`, and the connect flow
   tells the operator the connection will flip them out of demo (when
   the lifecycle promotes to `production_credentialed`).
3. No app-logic changes before `7.58` — this slice adds a vendor
   adapter; metric formulas are untouched.
4. Per-operator isolation — every gateway call routes through
   `OperatorScopedRepository.withTenant(operatorId, locationId, ...)`.
5. Modular Adaptive Agentic RAG — n/a for this surface.
6. Recommendations not commands — n/a (reservation data inflow only).
7. F&F holds provider keys server-side — the partner-issued OAuth
   client_id / client_secret will live in Cloud Run env / KMS at
   `8R.OT.live.prod`; the documented slice runs entirely against the
   test transport.
8. AI infra is general-purpose — n/a (reservation adapter, not AI).
9. AI cost metering — n/a.
10. Backend phase ships operator-facing UX before phase close — the
    Vendor Connections widget already renders the "Coming soon" pill
    for `documented`-lifecycle vendors; this slice plugs OpenTable
    into that surface and adds the partner-app tooltip copy
    ("Partner API access in progress; we'll email you when it's
    ready") on top of the existing "Notify me when ready" capture.

## What changed

### `lib/integrations/reservation/opentable_reservation_adapter.dart` (NEW)

- `class OpenTableReservationAdapter implements ReservationAdapter` —
  all 7 framework methods (`connect`, `testConnection`, `backfill`,
  `pollIncremental`, `handleWebhook`, `disconnect`, plus the
  capability-profile getter and `vendorId` / `displayName` getters).
- `VendorCapabilityProfile`: `vendorId: 'opentable'`,
  `category: reservation`, `authMode: oauth`, `grantScope: perLocation`,
  `webhookSupport: autoRegister`, `coversFieldExposed: false` (covers
  classification = `not_applicable` per `field_mapping.md`),
  `lifecycle: VendorLifecycle.documented`, `modules: <String>[]`,
  `timestampPolicyDocId: 'docs/integrations/opentable/field_mapping.md'`.
- `documentedPerOpentableV1FieldMapping` constant Map — every
  field-mapping assumption captured with vendor field path + canonical
  field + doc URL + retrieval date + `verify_in_live_sandbox: true`
  flag. Mirrored in
  `test/integrations/reservation/fixtures/opentable_reservations_fixture.dart`
  (`documentedPerOpentableV1FieldMappingFixture`). The test
  "field-mapping constant mirrors fixture" pins the two in sync;
  `8R.OT.live.sandbox` diffs observed responses against this
  constant.
- `openTableTimestampPolicy` constant —
  `AmbiguousTimestampConvention.refuse` (assumed UTC ISO-8601 with
  explicit `Z`; the adapter refuses ambiguous shapes until
  `*.live.sandbox` confirms). Local declaration; deferred-merged into
  `vendorTimestampPolicy` catalog at the integration commit.
- `OpenTableTransport` abstract surface — production wires HTTP via
  the `*.live.*` slices when partner credentials arrive; tests inject
  `_FakeOpenTableTransport`. Methods cover:
  `exchangeAuthorizationCode` (OAuth callback completion), `refresh`
  (rotating refresh token), `revoke` (best-effort revoke on
  disconnect), `listReservations` (paginated backfill / poll),
  `fetchReservation` (webhook fall-through), `registerWebhook` /
  `unregisterWebhook` (auto-register on connect; tear down on
  disconnect), `sampleReservation` (test-connection probe).
- `OpenTableGateway` abstract surface — production wires
  `OperatorScopedRepository`-backed implementation; tests inject
  `_FakeOpenTableGateway`. Adapter NEVER opens its own database
  connection or imports `package:postgres` (banned-items test pins
  this).

### `lib/integrations/reservation/opentable_webhook_signature_verifier.dart` (NEW)

- `class OpenTableWebhookSignatureVerifier implements VendorWebhookSignatureVerifier`
  — HMAC-SHA256 over the raw body, lowercase hex,
  `X-OpenTable-Signature` header (every behavior assumed; flagged for
  verification in `*.live.sandbox`). Constant-time compare via the
  framework's `constantTimeBytesEquals`.
- Optional `X-OpenTable-Timestamp` (Unix epoch seconds) populates
  `WebhookSignatureVerification.timestamp` so the framework's 24h
  replay ceiling enforces against it; when the vendor does not bind a
  timestamp into the signed payload the verifier returns null and the
  idempotency UNIQUE on `(vendor_id, operator_id, vendor_event_id)`
  is the duplicate-write defense for legitimate retries.

### Step 4 — Engineering anchor: forged signature → 403

```
verify({rawBody=openTableReservationModifiedRawBody,
        headers={x-opentable-signature: 'beefcafe...' x64}})
  → WebhookSignatureVerification(valid=false,
                                 failureReason='X-OpenTable-Signature HMAC mismatch')

InboundWebhookHandler.dispatch(...) with the same tampered headers
  → WebhookOutcome.signatureInvalid (statusCode 403)
  → gateway.failedAttempts['evt-opentable-tampered'] == 1
  → adapter.handleWebhook NOT called
  → no canonical-fact write
```

**Expected:** Pinned in the test "Test 4 (framework end-to-end) —
tampered HMAC dispatched through InboundWebhookHandler returns 403 +
audit row + no canonical write".

### Step 5 — Engineering anchor: malformed payload drop

If a webhook arrives whose `command.payload['reservation']` is
missing or not a Map, `handleWebhook` returns
`HandleWebhookResult(recordsWritten: 0)`. The framework's
`appendSyncLog` records the drop; no canonical fact is written.

**Expected:** No partial-write flag (banned per V1 lean cut 2). The
adapter either writes a clean canonical fact or refuses.

### Step 6 — Engineering anchor: future-dated event drop (sanity guard)

`openTableFutureDatedReservation` has `reserved_at:
'2026-07-15T12:00:00Z'`, which is 60+ days after the test's
`nowFixed`. When this row flows through `pollIncremental` with the
framework's `sanityHook`:

```
sanityHook(vendorEventId='OT-9999',
           payload={'opened_at': '2026-07-15T12:00:00Z', 'closed_at': '2026-07-15T12:00:00Z'},
           isDeliberateBackfill: false)
  → false  (rule: opened_in_future)
adapter.pollIncremental skips writeReservationFact for this row
```

**Expected:** `result.sanityDropped >= 1`, no canonical fact for
reservation `OT-9999`. Pinned in "Test 1 (reject) — sanity hook
returning false skips canonical write".

### Step 7 — Engineering anchor: OAuth near-expiry → cron refresh

OpenTable's OAuth refresh shape is **assumed** at this slice
(see `oauth_shape.md` — rotating refresh tokens, 1h access TTL, 90d
refresh TTL). Live exercise of the refresh cron is deferred to
`8R.OT.live.sandbox`. The documented slice exercises the transport
seam (`OpenTableTransport.refresh`) so the production wiring slots
in without an adapter change. The framework's
`OAuthRefreshCronRunner` will pick up OpenTable expiring tokens once
the per-vendor refresher binding lands as part of the
`8R.OT.live.sandbox` integration commit.

**Expected:** `OpenTableTransport.refresh` exists and the test-double
returns a valid `OpenTableTokenResponse`. No assertion on cron
behavior at this slice; that lands at `*.live.sandbox`.

### Step 8 — Engineering anchor: disconnect / reconnect watermark preservation

```
backfill → recordsWritten = 3, watermark commits per batch
poll (empty page) → records = 0, watermark advances lastModifiedSeen
disconnect → credentials wiped (best-effort revoke + unregisterWebhook),
             watermark preserved
reconnect → fresh OAuth callback, same watermark visible to next poll
```

**Expected:** `postReconnectWatermark.lastModifiedSeen ==
preDisconnectWatermark.lastModifiedSeen`. Pinned in "Test 5 — full
lifecycle preserves watermark across disconnect/reconnect".

## Permission gating evidence

The adapter does not register routes; it implements
[ReservationAdapter] which is invoked by the proxy's webhook +
sync-worker surfaces. The permission gate
(`integrations.configure` per
`docs/contracts/auth_permission_key_catalog.md`) lives on the proxy
admin route that wires the connect / disconnect calls; this slice
neither adds nor changes those routes. Live verification of the gate
is in `live_verification_checklist.md` row "Permission gate" (filled
in at `8R.OT.live.sandbox`).
