# 8.business_date_denorm Walkthrough

**Slice:** 8.business_date_denorm (Phase 8). Denormalized `business_date` `DATE` column on the three Phase 8 integration framework tables that carry fact-bearing time data.
**Mode:** Migration-only. No Dart code changes, no operator-facing UX. F&F engineer at staging psql.
**Date:** 2026-05-05

This slice extends the
`docs/contracts/phase_7_55_time_boundary_contract.md` Rule 11
discipline ("denormalized `business_date` `DATE` column lives
alongside the source-truth `TIMESTAMPTZ` ... write-once, never
recomputed at read") to the Phase 8 integration framework tables
that originally shipped with bare `TIMESTAMPTZ` columns and no
`business_date` denorm.

Three framework tables carry fact-bearing time data and gain a
`business_date DATE NOT NULL` column plus an operator-leading B-tree
index plus a BEFORE INSERT trigger:

| Table                              | Source-truth timestamp |
| public.connector_sync_log          | occurred_at TIMESTAMPTZ |
| public.inbound_webhook_dead_letter | occurred_at TIMESTAMPTZ |
| public.sanity_log                  | detected_at TIMESTAMPTZ |

Five framework tables stay business_date-free because none of them
carries a fact-bearing instant that maps to a restaurant business
date: credential metadata (`vendor_credentials`), config
(`connector_connection`), sync state markers
(`connector_sync_watermark`), TTL-only dedupe
(`inbound_webhook_idempotency`), and the singleton
(`demo_mode_state`).

The trigger is the defense-in-depth seam. The existing Wave-1 sinks
(`lib/infrastructure/persistence/postgres/{libro,oracle_micros_simphony,quickbooks_time}_postgres_sink.dart`)
insert into `connector_sync_log` without setting `business_date`,
and the trigger backstops them. Future spine-bridge sink fanout
slices can compute `business_date` Dart-side and pass it on the
INSERT; the trigger fires only when `NEW.business_date IS NULL`.

## Authority files exercised

- `docs/contracts/phase_7_55_time_boundary_contract.md` Rule 11

  and projected from `location.timezone`.
- `docs/contracts/integration_spine_architecture_contract.md`:

- `CLAUDE.md`: TIMESTAMPTZ + business_date discipline; every

## What the slice ships

### Database

`db/migrations/202605050400_phase_8_business_date_denorm.sql`:

- **Add nullable `business_date DATE`** to `connector_sync_log`,
  `inbound_webhook_dead_letter`, `sanity_log`. Additive (no
  ACCESS EXCLUSIVE wait).
- **Backfill** in an inline DO block (no helper function: the
  migration applier already owns the locations table and is
  RLS-exempt; a SECURITY DEFINER helper would add deployment-role
  grant complexity for no functional benefit). One CTE-with-UPDATE
  per table, bounded `LIMIT 50000` per pass, looping until zero
  rows update. Denorm rule mirrors
  `lib/services/integration/iana_timezone_converter.dart`
  (`toBusinessDate`): project the source-truth instant through the
  location's IANA timezone, then subtract
  `business_day_rollover_hour` so events whose local time is
  before the rollover bucket to the prior business date.
  Empty-string / missing `locations.timezone` falls back to UTC
  (honest-fallback per `phase_7_55_time_boundary_contract.md`);
  NULL `business_day_rollover_hour` defaults to 0 (no shift). The
  DO block emits `RAISE NOTICE` for both row-count totals and the
  pre-backfill orphan-timezone count.
- **SET NOT NULL** on all three tables after backfill completes.
- **Operator-leading B-tree indexes:**
  - `connector_sync_log_business_date_idx (operator_id, business_date desc, occurred_at desc)`
  - `inbound_webhook_dead_letter_business_date_idx (operator_id, business_date desc, occurred_at desc)`
  - `sanity_log_business_date_idx (operator_id, business_date desc, detected_at desc)`
- **BEFORE INSERT trigger** on each table. Per-table trigger
  `<table>_set_business_date` calls the shared
  `public.phase_8_set_business_date` function with the source-truth
  timestamp column name as `TG_ARGV[0]`. Function is SECURITY
  DEFINER + OWNED BY `forge_admin` (BYPASSRLS) so the
  RLS-protected `public.locations` join works regardless of the
  inserter's tenant context. Same denorm rule as the backfill
  (timezone projection then rollover-hour subtraction). Honors
  caller-supplied `business_date` (no overwrite). Honest UTC
  fallback when `locations.timezone` is unresolvable.

### What the slice intentionally does NOT ship

- **No Dart changes.** The Phase 8 integration tables have no Dart
  repository wrappers yet (verified by grepping for `insert into
  public.connector_sync_log`; only the three Wave-1 sinks write,
  and they go through the trigger now). The spine-bridge sink
  fanout slice will mirror the trigger pattern when it lands.
- **No tracker / contract / phase-doc edits.** Slice prompt
  forbids; no-tracker discipline preserved.
- **No operator-facing UX.** Pure schema discipline.

## Click path (F&F engineer at staging psql)

The walkthrough is three numbered steps. Steps 1 and 3 use staging
psql to assert the schema state before vs after; step 2 runs the
migration. The trigger seam is exercised in step 3 by inserting a
row with `business_date = NULL` and verifying the trigger
denormalized it from `occurred_at` via the location's IANA zone.

### Step 1. Pre-migration schema (no business_date column)

**Action:** F&F engineer connects to staging Postgres as
`forge_admin` and asserts the three tables carry their original
shape: no `business_date` column, no recent-rows tenant-leading
index.

**SQL:**

```sql
\d+ public.connector_sync_log
\d+ public.inbound_webhook_dead_letter
\d+ public.sanity_log

select column_name, data_type, is_nullable
  from information_schema.columns
 where table_schema = 'public'
   and table_name in (
     'connector_sync_log',
     'inbound_webhook_dead_letter',
     'sanity_log'
   )
   and column_name = 'business_date';
```

**Expected output:**

```text
\d+ output: no business_date column on any of the three tables.

select returns: 0 rows. (No business_date column anywhere.)
```

### Step 2. Apply the migration

**Action:** Engineer applies the migration via the staging runbook
(or `psql -f db/migrations/202605050400_phase_8_business_date_denorm.sql`
as `forge_admin`). The migration is one transaction; it either
applies fully or rolls back.

**Migration trace (RAISE NOTICE lines staging will print):**

```text
NOTICE: phase_8_business_date_denorm: backfilled <N> connector_sync_log rows.
NOTICE: phase_8_business_date_denorm: backfilled <N> inbound_webhook_dead_letter rows.
NOTICE: phase_8_business_date_denorm: backfilled <N> sanity_log rows.
```

If any pre-existing row has an unresolvable
`locations.timezone` (NULL or empty string; should never happen
on a healthy schema since `locations.timezone` is `text not null`,
but the honest-fallback rule covers test fixtures and edge
states), the migration also prints:

```text
NOTICE: phase_8_business_date_denorm: <table> carries <N> rows
        without a resolvable location.timezone; UTC fallback will
        apply.
```

The migration's `commit;` closes the transaction. There is no
`schema_migrations` ledger in this codebase; the staging runbook
tracks applied filenames out-of-band. Step 3 below is the
definitive evidence the migration ran (column + index + trigger
state).

**Insert a row with business_date NULL (trigger denormalizes via
the Pacific-zone fixture location):**

The fixture seeds an operator + org_unit + Pacific-zone location
(IANA `America/Los_Angeles`, `business_day_rollover_hour = 4`) +
connection (see
`test/integration/business_date_denorm_test.dart` for the
identifiers; the test's `setUpAll` does the same seed).
2026-05-04T10:30:00Z = 03:30 PDT 2026-05-04, which is BEFORE the
04:00 rollover, so the trigger buckets the event to the prior
business date 2026-05-03 (matching `IanaTimezoneConverter
.toBusinessDate`).

```sql
insert into public.connector_sync_log (
  operator_id, location_id, connection_id,
  event_kind, occurred_at
) values (
  'bd800000-0000-0000-0000-0000000000a1'::uuid,
  'bd800000-0000-0000-0000-0000000000a2'::uuid,
  'bd800000-0000-0000-0000-0000000000a4'::uuid,
  'poll_success',
  '2026-05-04T10:30:00Z'
);

select to_char(business_date, 'YYYY-MM-DD') as business_date
  from public.connector_sync_log
 where operator_id = 'bd800000-0000-0000-0000-0000000000a1'::uuid
 order by occurred_at desc
 limit 1;
```

**Expected output:**

```text
business_date
--------------
 2026-05-03
```

(Pacific zone: 10:30 UTC = 03:30 PDT 2026-05-04, which is before
the 04:00 rollover so the event belongs to the PRIOR business
date 2026-05-03. Without the trigger the INSERT would have failed
the NOT NULL constraint with a clear `null value in column
"business_date"` error.)

**Verify caller-supplied business_date is preserved (trigger
