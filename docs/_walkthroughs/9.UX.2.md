## 9.UX.2 — Settings Team Roles (custom role editor + catalog viewer)

Date: 2026-04-30

## Scope

Add the operator-scoped role catalog viewer + custom-role create/edit/delete
editor to Settings → Team for owners with `team.roles.create_custom`. Live
mode consumes the existing `auth_operations_gateway` calls backed by B17
`/v1/admin/auth/roles` (already deployed staging rev `00018-ztq`); demo
mode runs the same surface against an in-memory catalog so the
walkthrough completes without staging access.

## Operator Walkthrough (`kDemoMode = true`)

1. Launch ForgeFlow in demo mode and sign in as the demo operator owner
   (`demo.operator@forgeflow.test` / `forge-flow-demo`).
2. Open Settings.
3. Select Team.
4. Scroll past **Members** and **Org Hierarchy** to the **Roles** section
   header (text trace: `settings_custom_roles_section` widget key visible
   in the Team tab).
5. Confirm the catalog renders the seeded baseline roles (every
   seeded row exposes a **View** affordance only — operator-facing
   edits route through `team.roles.create_custom`, which only mutates
   custom rows; seeded edits live behind `admin.roles.edit_seeded`)
   and the operator's existing custom roles. Each row shows
   allow / deny counts for its permission keys.
6. Tap **New role** (`settings_custom_roles_create_button`). The role
   editor dialog opens (`settings_role_editor_dialog`).
7. Enter a role key (`kitchen_lead`), display name (`Kitchen Lead`), and
   description.
8. Expand the **Forge & Flow** category and switch
   `forgeflow.shift.view` and `forgeflow.shift.edit` to **Allow**. Expand
   **Team** and switch `team.users.view` to **Allow**. Confirm the
   collapsed-category headers show the running allow count.
9. Tap **Save** (`settings_role_editor_save`). Confirm a snackbar appears
   (`Role "Kitchen Lead" created`) and the new row lands at the top of
   the **Custom roles** group with the **Custom** badge.
10. From **Members**, open the role-change dialog for the demo user.
    Confirm `Kitchen Lead` is now a selectable role option without
    closing/reopening Settings — the `_RoleCatalogToOptionsScope`
    adapter projects the live `teamRoleCatalogListenable` into
    `TeamSettingsSection.roleOptions`, so creating a custom role
    immediately makes it grantable without round-tripping the
    legacy `teamRoleOptions` listenable.
11. Grant `Kitchen Lead` to the demo user. Sign in as the demo user and
    confirm the surfaces gated by `forgeflow.shift.view` /
    `forgeflow.shift.edit` are reachable, while
    `forgeflow.weekly_plan.lock` (not granted) is hidden.
12. Return to Settings → Team → Roles, tap **Edit** on `Kitchen Lead`,
    flip `forgeflow.shift.edit` to **Inherit**, and Save. Confirm the
    snackbar (`Role "Kitchen Lead" updated`) and that the user loses
    edit access on next sign-in.
13. Tap **Delete** on `Kitchen Lead`. Confirm the modal asks for
    confirmation (`Delete role?`), Cancel leaves the role intact, and
    confirming triggers the snackbar `Role "Kitchen Lead" deleted` and
    drops the row from the catalog.
14. Sign in as a manager that holds only `team.roles.view` (no
    `team.roles.create_custom`). Open Settings → Team → Roles and
    confirm the catalog still renders, but **New role**, **Edit**, and
    **Delete** are absent — every row collapses to a **View** affordance
    that opens the editor in read-only mode.
15. Sign in as a user that holds neither `team.roles.view` nor
    `team.users.view`. Confirm the Team tab is hidden entirely (Settings
    collapses to Account-only).

## Contract Notes

- Reads and writes route through `AuthOperationsGateway`:
  - `listRoles` → `GET /v1/admin/auth/roles[?scope=…]` (gates on
    `team.roles.view`).
  - `createRole` → `POST /v1/admin/auth/roles` (gates on
    `team.roles.create_custom`).
  - `patchRole` → `PATCH /v1/admin/auth/roles/<roleId>` (gates on
    `team.roles.create_custom`).
  - `deleteRole` → `DELETE /v1/admin/auth/roles/<roleId>` (gates on
    `team.roles.create_custom`; rejects when active grants exist).
- The editor never invents new permission keys. The picker is seeded
  from `lib/auth/permission_keys.dart` (`PermissionKeys.all`, the
  frozen 96-key catalog from
  `docs/contracts/auth_permission_key_catalog.md`).
- Role-key validation mirrors the backend rule from
  `lib/services/auth/repository_auth_operations_gateway.dart`:
  `^[a-z][a-z0-9_]{2,63}$` (3–64 chars, lowercase letter prefix).
- `is_seeded` and `is_editable` come straight from the proxy
  `TeamRoleCatalogEntry` payload. The operator UI treats every seeded
  role as **View**-only regardless of `is_editable=true` — the
  contract grants seeded edits to super_admin via
  `admin.roles.edit_seeded` (MFA-required), which is not exposed on
  this surface. Custom roles expose **Edit** + **Delete** to actors
  holding `team.roles.create_custom`.
- Read-only actors (`team.roles.view` only) get a **View** affordance
  on every row that opens the editor with `readOnly: true` — the
  `Save` button is hidden, every form control is disabled, and
  `onPatchRole` is never invoked even if the parent passes one.
- The `permissions` list in a `PATCH` payload only carries permission
  keys whose effect changed in the dialog (`allow`, `deny`, or the
  string `inherit` to remove an explicit rule). Unchanged rules are
  omitted, mirroring the test expectation in
  `proxy_auth_operations_gateway_test.dart`.
- Demo mode (`kDemoMode = true` or no live gateway): the section
  consumes the seed catalog passed via `SettingsScreen.teamRoleCatalog`
  / `teamRoleCatalogListenable`. Mutation callbacks in the demo wiring
  append/replace/remove entries in-memory and re-publish through the
  same listenable that drives `TeamSettingsSection.roleOptions`, so
  newly created custom roles surface in the role-grant flow without a
  navigation reset.
