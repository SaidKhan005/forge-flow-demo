# 10a.2 Walkthrough — event_outbox dead-letter cap (F&F-internal click-path)

**Slice:** 10a.2 (Phase 10a — Shared Multi-Device State V1, dead-letter cap + transactional MOVE + `/health` depth metric)
**Mode:** F&F-internal staging only — no operator-facing UX in this slice. Per `memory/project_v1_lean_cut_2_2026_05_03.md`, the 11A.6 DLQ tile is deferred; V1 surface is logs + admin SQL + the `/health` envelope.
**Date:** 2026-05-04

This walkthrough closes the dead-letter half of the Phase 10a
follow-ups queued in `docs/_walkthroughs/10a.0.md`. The slice ships
the cap, the new `event_outbox_dead_letter` table, the transactional
MOVE inside the bridge worker, the `event_outbox_dlq_depth`
`/health` metric, and the F&F-internal triage flow. Operator-facing
visibility stays out of V1 — the framing question
(`memory/project_v1_lean_cut_2_2026_05_03.md`: "does this make the
operator trust the metrics faster, or does it just make engineering
feel safer?") puts the operator-facing tile on the deferred list.

The Hard Promise this slice realizes:

> Per-operator isolation is non-negotiable. RLS-ready schema from
> day one; Phase 9 enforces.

The new `event_outbox_dead_letter` table ships RLS-ready
(per-tenant SELECT/MODIFY policies via the `app_current_operator()`
wrapper, a tenant-leading B-tree index, partitioned by
`dead_lettered_at_month` with 90-day retention).

## What the slice ships

### Database

- `db/migrations/202605040300_phase_10a_2_dead_letter.sql` —
  `public.event_outbox_dead_letter` table mirrors `event_outbox`
  shape plus three new columns: `dead_lettered_at TIMESTAMPTZ`,
  `dead_lettered_at_month DATE` (partition key), `last_error TEXT`,
  `dead_letter_reason TEXT` (CHECK in
  `{'attempt_cap_exceeded','forced_dlq'}`). Tenant-leading recent-
  rows index `event_outbox_dead_letter_recent_idx (operator_id,
  dead_lettered_at desc, id)`. RLS leakproof wrapper policies
  (`event_outbox_dead_letter_per_tenant_select` / `_modify`) keyed
  on `public.app_current_operator()`. `pg_partman` monthly
  partitioning, 3 months premake, 90-day retention,
  `retention_keep_table = true`. Append-only grants: service_role
  gets SELECT/INSERT/UPDATE; forge_admin gets the full DML set;
  defensive REVOKE of DELETE from service_role.

### Repository

- `lib/infrastructure/persistence/postgres/repositories/event_outbox_dead_letter_repository.dart`
  — three methods, all gated through
  `OperatorScopedRepository.withTenant`:
  - `moveFromOutbox(...)` — the transactional MOVE. One CTE:
    ```sql
    WITH dead AS (
      DELETE FROM event_outbox
       WHERE operator_id = @op AND id = @id
         AND attempt_count > @threshold
      RETURNING *
    )
    INSERT INTO event_outbox_dead_letter (...)
    SELECT *, now(),
           date_trunc('month', now() AT TIME ZONE 'UTC')::date,
           @reason
    FROM dead
    RETURNING id::text AS id
    ```
    Both writes commit or roll back together. Returns `null` if the
    predicate filtered the row out (already moved by another shard,
    or attempt_count not actually past the cap).
  - `listByOperator(...)` — admin-side list ordered by
    `dead_lettered_at DESC, id DESC` for triage SQL.
  - `countByOperator(...)` — admin-side per-operator depth count.

### Bridge worker

- `tool/advisor_proxy/realtime_bridge.dart`:
  - `eventOutboxDlqCapEnvVar` (`EVENT_OUTBOX_DLQ_CAP`),
    `defaultEventOutboxDlqCap` (`5`), and `resolveEventOutboxDlqCap`
    helper. Missing/blank/non-numeric/sub-1 values fall back to the
    default; sub-1 caps would auto-DLQ every row on first failure
    so the resolver clamps back.
  - Optional `EventOutboxDeadLetterRepository?` constructor
    parameter (nullable so 10a.0 / 10a.1 callers without a
    dead-letter table keep working).
  - `int dlqCap` constructor parameter (clamped ≥ 1).
  - `_drainOperatorInner` partitions claimed rows by
    `attempt_count > _dlqCap` BEFORE the publish loop. Over-cap
    rows MOVE through the dead-letter repository (transactional
    CTE) and the publish loop skips them.
  - `_deadLetteredTotal` process-local counter; new
    `RealtimeBridgeLogKind.deadLettered` /
    `deadLetterMoveFailed` log kinds with `attempt_count` + `cap`
    metadata.

### `/health` metric

- `tool/advisor_proxy/health_producers/outbox_producers.dart` —
  new `eventOutboxDlqDepthProducer` registered under
  `event_outbox_dlq_depth`. SQL: `SELECT count(*) FROM
  public.event_outbox_dead_letter`. Thresholds: yellow at 1, red
  at 100.
- `tool/advisor_proxy/proxy_bootstrap.dart` — append-only marked
  region documenting `EVENT_OUTBOX_DLQ_CAP` (default,
  raise/lower triggers, restart-required semantics) plus
  `phase10a2DlqCapEnvVar` / `phase10a2DlqDepthMetricKey` constants.

### What the slice intentionally does NOT ship

- **No 11A.6 admin tile.** Per
  `memory/project_v1_lean_cut_2_2026_05_03.md`, operator visibility
  into DLQ depth at V1 volume is not justified. F&F engineers
  triage via log search + admin SQL.
- **No auto-replay job.** V1 = manual operator action only (post-V1
  lane).
- **No publisher-seam edits.** The DLQ logic lives in the bridge
  worker, not the publishers (`realtime_event_publisher.dart` /
  `pubsub_realtime_publisher.dart` byte-identical).

## Click path (F&F engineer at staging psql + curl)

The walkthrough is six numbered steps. Each step names the action,
the expected DB row state, and the expected `/health` JSON shape (or
SQL output). Steps 1–5 cover the happy path + env-var override;
step 6 is the adversarial transactional-rollback path.

### Step 1 — Seed an event_outbox row that fails to publish

**Action:** F&F engineer connects to staging Postgres as
`forge_admin` and seeds a single row that the bridge will be unable
to publish. The seed sets `attempt_count = 0`; the failure ladder
runs in the next steps.

**SQL (engineer types):**

```sql
INSERT INTO public.event_outbox
  (operator_id, topic, payload)
VALUES
  ('11111111-1111-1111-1111-111111111111',
   'rollup.invalidate.variance_week',
   '{"event_id":"poison-pill-1","occurred_at":"2026-05-04T18:00:00.000Z","note":"forced-failure for 10a.2 walkthrough"}'::jsonb)
RETURNING id;
```

The bridge worker runs in staging Cloud Run with
`PUBSUB_REALTIME_ENABLED=false` (in-process publisher) and the
publisher is forced into failure mode for this walkthrough's
operator id (staging fixture flips a publisher feature flag —
walkthrough operator runs the flip, code path is the same as the
unit tests' `_FailingPublisher`).

**Expected DB row state:**

```text
public.event_outbox row exists with:
  id              = <returned bigserial>
  operator_id     = 11111111-1111-1111-1111-111111111111
  topic           = "rollup.invalidate.variance_week"
  attempt_count   = 0
  picked_up_at    = NULL
  delivered_at    = NULL
  last_error      = NULL
  last_error_at   = NULL

public.event_outbox_dead_letter row count for operator = 0
```

**Verify:**

```sql
SELECT id, attempt_count, picked_up_at, delivered_at, last_error
  FROM public.event_outbox
 WHERE operator_id = '11111111-1111-1111-1111-111111111111'
 ORDER BY id DESC LIMIT 1;
-- attempt_count = 0; rest NULL
```

### Step 2 — Watch attempt_count climb to 5 across claim cycles

**Action:** Engineer waits for the bridge's claim loop (NOTIFY
wakes it on the INSERT, then 60s scheduled poll backstops). With
the publisher forced-failing, each claim does:

1. `claimBatch(...)` stamps `picked_up_at = now()`.
2. `publisher.publish(event)` throws `_SimulatedPublishFailure`.
3. Worker logs `realtime.bridge.publish_failed` and skips
   `markDelivered`.
4. Lease window (`claimReclaimAfter`, default 5 min) expires;
   `picked_up_at` becomes claimable again.
5. The companion `attempt_count` retry-ledger increment is the
   parallel Phase 10a follow-up (`docs/_walkthroughs/10a.0.md`
   "Out of scope" first follow-up). For walkthrough purposes the
   engineer manually advances `attempt_count` via:

   ```sql
   UPDATE public.event_outbox
      SET attempt_count = attempt_count + 1,
          last_error_at = now(),
          last_error = 'forced publish failure (walkthrough)',
          picked_up_at = NULL
    WHERE id = $POISON_PILL_ID;
   ```

**Expected DB row state at end of step (attempt_count = 5, equal
to the cap — NOT yet over):**

```text
public.event_outbox row:
  id              = $POISON_PILL_ID
  attempt_count   = 5
  picked_up_at    = NULL
  delivered_at    = NULL
  last_error      = "forced publish failure (walkthrough)"
  last_error_at   = ~now()

public.event_outbox_dead_letter row count for operator = 0
```

**Verify:**

```sql
SELECT id, attempt_count, last_error, picked_up_at IS NULL AS available
  FROM public.event_outbox
 WHERE id = $POISON_PILL_ID;
-- attempt_count = 5; available = true
```

### Step 3 — Push attempt_count past the cap; bridge MOVES the row

**Action:** Engineer bumps `attempt_count` to 6 and waits for the
next claim cycle. Bridge claims the row (now over-cap) and
partitions it into the `over_cap` set.

```sql
UPDATE public.event_outbox
   SET attempt_count = 6,
       picked_up_at = NULL
 WHERE id = $POISON_PILL_ID;
```

The next claim loop runs `_drainOperatorInner` which partitions
`attempt_count > _dlqCap (= 5)`:

```text
over_cap = [row]
keep     = []
moveFromOutbox(operatorId, locationId, eventId=$POISON_PILL_ID,
               attemptCountThreshold=5, reason='attempt_cap_exceeded')
  -> WITH dead AS (DELETE ... RETURNING *) INSERT ... RETURNING id
  -> single transaction commit
  -> _deadLetteredTotal += 1
  -> structured log:
       realtime.bridge.dead_lettered
       operator_id=11111111-1111-1111-1111-111111111111
       outbox_id=$POISON_PILL_ID
       topic="rollup.invalidate.variance_week"
       attempt_count=6
       dlq_cap=5
publish loop sees publishable = [] (over-cap row was filtered out)
```

**Expected DB row state:**

```text
public.event_outbox row count where id = $POISON_PILL_ID = 0
public.event_outbox_dead_letter row exists with:
  id                       = $POISON_PILL_ID  (carried forward)
  operator_id              = 11111111-1111-1111-1111-111111111111
  topic                    = "rollup.invalidate.variance_week"
  attempt_count            = 6
```

### Step 6 — Adversarial: force the dead-letter INSERT to fail mid-transaction; verify rollback

**Action:** Engineer drops the `event_outbox_dead_letter`
partition for the current month so the INSERT half of the MOVE CTE
hits a partition-not-found error. The DELETE half succeeds in the
CTE plan but Postgres rolls the whole statement back when the
INSERT fails. The bridge transaction wrapping the CTE also rolls
back (the wrapper re-throws on body exception). Result: the row
stays in the live queue with its original `attempt_count`.

```sql
-- Drop the May 2026 partition (forces INSERT to fail; DELETE-half
-- of the CTE rolls back with the rest of the statement).
ALTER TABLE public.event_outbox_dead_letter
  DETACH PARTITION public.event_outbox_dead_letter_p2026_05;
DROP TABLE public.event_outbox_dead_letter_p2026_05;
```

Engineer seeds a third row and pushes `attempt_count = 11` (over
the new cap):

```sql
INSERT INTO public.event_outbox
  (operator_id, topic, payload)
VALUES
  ('11111111-1111-1111-1111-111111111111',
   'rollup.invalidate.variance_week',
   '{"event_id":"poison-pill-3","occurred_at":"2026-05-04T19:00:00.000Z","note":"adversarial rollback test"}'::jsonb)
RETURNING id;
-- $POISON_PILL_3_ID

UPDATE public.event_outbox
   SET attempt_count = 11,
       last_error = 'forced publish failure (walkthrough — adversarial)',
       last_error_at = now(),
       picked_up_at = NULL
 WHERE id = $POISON_PILL_3_ID;
```

Bridge claim cycle:

```text
attempt_count (11) > dlqCap (10)  -> true
moveFromOutbox(...)
  -> withTenant body issues the WITH dead AS (DELETE ... RETURNING)
     INSERT ... CTE
  -> INSERT fails: relation "event_outbox_dead_letter_p2026_05"
     does not exist
  -> exception bubbles up
  -> wrapper rolls back the transaction
  -> NEITHER the DELETE NOR the INSERT lands
  -> _deadLetteredTotal stays unchanged
  -> structured log:
       realtime.bridge.dead_letter_move_failed
       operator_id=11111111-1111-1111-1111-111111111111
       outbox_id=$POISON_PILL_3_ID
       topic="rollup.invalidate.variance_week"
       attempt_count=11
       dlq_cap=10
       error_type=...
publish loop sees publishable = [] (over-cap row never reaches it)
```

**Expected DB row state:**

```text
public.event_outbox row $POISON_PILL_3_ID:
  attempt_count   = 11    (unchanged — DELETE rolled back)
  picked_up_at    = NULL  (lease released by transaction rollback)
  delivered_at    = NULL

public.event_outbox_dead_letter — still 1 row (only step-3's row;
  step-6's row did NOT land, neither did its DELETE-half).
```

**Verify:**

## Permission gating evidence

- **Tenant-scoped writes.** The MOVE CTE runs inside
  `withTenant(...)`; the wrapper emits `SET LOCAL
  app.operator_id` before the CTE executes. The migration's RLS
  policies (`event_outbox_dead_letter_per_tenant_select` /
  `_modify`) match `operator_id = public.app_current_operator()`
  so the policy admits both writes inside the same tenant
  transaction. Cross-tenant writes block at WITH CHECK.
- **Tenant-scoped reads.** `listByOperator` and `countByOperator`
  also run inside `withTenant`; the recent-rows index is
  `(operator_id, dead_lettered_at desc, id)` so the per-tenant
  policy folds into the index probe.
- **`/health` aggregate.** The `event_outbox_dlq_depth` producer
  runs through the `_buildRegistryProxyHealthCheckStore` admin-pool
  runner with `runAsSystem` because the `/health` envelope is a
  platform-wide aggregate (no tenant identifiers per the
  envelope contract).
- **Append-only by grant shape.** `service_role` gets
  SELECT/INSERT/UPDATE only. `forge_admin` gets the full DML set
  (the partition-drop retention sweep needs DELETE; per-row
  deletion is forbidden because retention is partition-cadence,
  not row-cadence). A defensive REVOKE re-asserts that
  service_role cannot DELETE even if a future grant pattern adds
  the broader DML set out of habit.
- **No new permission keys.** No operator-facing UX in this slice
  (per lean cut 2) → no new admin-permission catalog entry.
