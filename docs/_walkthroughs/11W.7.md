# 11W.7 Walkthrough — Account / Business setup screen

**Slice:** 11W.7 (Phase 11W — Operator Web Console)
**Mode:** `kDemoMode = true` (operator-web flavor; demo seed shipping with `11W.0`)
**Date:** 2026-05-04

This slice retires the V1 `AccountPlaceholderScreen` and ships the
real Operator Web Account screen. The screen mounts at the side-nav
`Account` route (id `kOperatorWebNavAccount`) and presents four
sections — Profile, Two-factor sign-in, Password, Terms and
conditions.

The slice is UX-shaped (not contract-shaped). It does not move any
auth/RLS boundary or change app logic; it expands an empty placeholder
into the four V1 sections the lean cut keeps in scope. The remaining
heavy account features (logo upload, custom branding, full billing,
audit-log export) stay deferred per `project_v1_lean_scope_cut.md` and
`project_v1_lean_cut_2_2026_05_03.md`.

**Wiring honesty (read this first):** `11W.7` ships the Account
*surface* with all four sections operator-visible and the demo
mutation paths (MFA enroll, password change) flipping local widget
state for walkthrough purposes. Real proxy round-trips against the
existing Phase 9 MFA / password-rotation routes — and the audit-log
writes those routes already perform — light up when `11W.0.live`
ships the gateway, mirroring the gateway-follows-shell pattern Phase
11A used. No new proxy routes, no new permission keys, no new audit
hooks are added in `11W.7`.

## What changed

### `lib/operator_web/screens/account_screen.dart` (new)

- `AccountScreen` — `StatefulWidget` taking the same
  `OperatorWebSession session` the placeholder took. Wraps the four
  V1 sections in a `SingleChildScrollView` + `Column` (eager build)
  rather than a top-level `ListView` so widget tests can `find.byKey`
  any section without first scrolling it into view; same scroll
  behaviour for the operator. The deviation from the contract's
  literal "ListView" is documented in the file header — sliver-lazy
  build was the only thing the change is dodging.
- Four sections, each a card with a stable `Key`:
  - `Key('account_section_profile')` — display name, email, phone,
    business. Read-only at V1; copy steers phone edits to the
    operator mobile app under Settings → Account. Renders `phone`
    from `session.phone`; falls back to "Not on file" when null.
  - `Key('account_section_mfa')` — enrollment status badge
    (`Key('account_section_mfa_badge')`) reflects
    `session.mfaEnrolled` at first paint and the local enroll-flip
    inside this widget's lifetime. `Enroll MFA` button when not
    enrolled, or `View backup codes` button when enrolled.
  - `Key('account_section_password')` — `Change password` button
    opens a 3-field modal (current / new / confirm). Demo submit
    surfaces a transient `Key('account_section_password_toast')`
    that auto-dismisses after 4 seconds.
  - `Key('account_section_tos')` — accepted version + date line
    (`Key('account_section_tos_accepted_line')`); `View current T&Cs`
    button opens a read-only dialog (`Key('view_tos_dialog')`)
    rendering the `DemoOperatorWebAuthSource.kDemoTosVersion` body
    inside a scoped `Key('view_tos_dialog_scroll')` so long bodies
    don't clip the dialog.
- Three modals: `Key('mfa_enroll_dialog')` (QR + 6-digit code field
  with autofocus), `Key('mfa_backup_codes_dialog')` (list scoped to
  `Key('mfa_backup_codes_dialog_list')` so finder counts don't drift),
  and `Key('change_password_dialog')` (autofocus on the current-
  password field; `onSubmitted` on the confirm field).
- Permission gate: `_canWriteAccount` returns true for
  `operator_owner` or `operator_admin` roles; `location_manager`
  falls through to read-only. Disabled buttons render a `Tooltip`
  with friendly-error copy ("Only operator admins can change MFA").
  Mirrors the proxy-side gate the existing Phase 9 routes already
  enforce. *Exception:* the `View backup codes` button is **not**
  gated on `canWrite` — viewing your own MFA recovery codes is not
  an admin-write action. A `location_manager` who has already
  enrolled MFA can still see their codes.
- Responsive: `LayoutBuilder` with breakpoint
  `_kProfileTwoColumnBreakpoint = 800`. Below that, the four Profile
  fields stack into a single column
  (`Key('account_section_profile_single_column')`); at or above, they
  render in a 2-column `Wrap`
  (`Key('account_section_profile_two_column')`). Sized so a 768px
  tablet viewport stacks regardless of whether the screen is rendered
  inside the shell (body column ≈ 548px) or standalone in tests, and
  a 1024px desktop viewport renders 2-column in either case.

### `lib/operator_web/auth/operator_web_auth_source.dart`

### `lib/operator_web/screens/account_placeholder_screen.dart`

## Click path (numbered steps)

### Step 1 — Open `app.forgeflow.app`

Browser viewport 1280×800 (desktop). Magic-link / mock session lands
the operator on `/account`.

**User action:** open `app.forgeflow.app` in a browser tab.

**Expected:**

- `Key('operator_web_shell_scaffold')` renders (header + side nav +
  body).
- Side-nav `Key('operator_web_nav_item_account')` is selected
  (sunset-tinted background).
- Body shows `Key('operator_web_account_screen')`.
- `Key('account_section_profile')` is visible. Display name reads
  "Demo Operator Owner"; email reads "owner@demo.forgeflow.test";
  Phone reads "Not on file" (with helper "Phone changes happen in
  the operator mobile app under Settings → Account.").

### Step 2 — Scroll to Two-factor sign-in

**User action:** scroll the body until `Key('account_section_mfa')`
is visible.

**Expected:**

- The status badge `Key('account_section_mfa_badge')` reads
  `MFA: Not enrolled` in slate grey (`AppColors.textMuted`) — driven
  by `session.mfaEnrolled = false` on the demo seed.
- `Key('account_section_mfa_enroll')` button visible with header
  "Turn on extra sign-in security" and explainer "When you turn this
  on, you'll need a 6-digit code from your phone every time you sign
  in from a new device. We'll walk you through setup."

### Step 3 — Tap "Enroll MFA"

**User action:** tap the button at `Key('account_section_mfa_enroll')`.

**Expected:**

- `Key('mfa_enroll_dialog')` opens with the 6-digit code field
  (`Key('mfa_enroll_dialog_code_field')`) autofocused. The dialog
  renders the otpauth payload at `Key('mfa_enroll_dialog_qr')` plus
  the explainer "Open your authenticator app, scan this code, then
  type the 6-digit code it shows you below."

### Step 4 — Type `123456` and confirm

**User action:** type `123456` into `Key('mfa_enroll_dialog_code_field')`,
then either press Enter or tap `Key('mfa_enroll_dialog_confirm')`.

**Expected:**

- The dialog closes (`Key('mfa_enroll_dialog')` no longer in tree).
- `Key('account_section_mfa_badge')` flips to `MFA: Enrolled` in
  green (`AppColors.positive`).
- The action row swaps to
  `Key('account_section_mfa_view_backup_codes')` with header "View
  backup codes" and explainer "Backup codes are one-time-use codes
  you can sign in with if you lose your phone or authenticator app.
  Save them somewhere safe."

> **Demo vs live:** in `11W.7` the badge flip is local widget state.
> Once `11W.0.live` wires the dialog to the existing Phase 9 MFA
> enrollment route, the proxy persists the enrollment, the audit log
> writes the row that route already produces, and the badge stays
> "Enrolled" across navigation + sign-out / sign-in cycles.

### Step 5 — Tap "View backup codes"

**User action:** tap `Key('account_section_mfa_view_backup_codes')`.

**Expected:**

- `Key('mfa_backup_codes_dialog')` opens listing 10 single-use
  backup codes inside `Key('mfa_backup_codes_dialog_list')` (rendered
  as `SelectableText` so the operator can copy them).
- The dialog body copy reads "Save these somewhere safe. If you lose
  your phone, any one of these codes lets you sign in once."
- Tap `Key('mfa_backup_codes_dialog_close')` to dismiss.

### Step 6 — Scroll to Password and tap "Change password"

**User action:** scroll until `Key('account_section_password')` is
visible, then tap `Key('account_section_password_change')`.

**Expected:**

- `Key('change_password_dialog')` opens with three fields:
  `Key('change_password_dialog_current')` (autofocused),
  `Key('change_password_dialog_new')`,
  `Key('change_password_dialog_confirm')`.
- Header copy reads "A strong password is one of the simplest things
  you can do to keep your business data safe. Mix letters, numbers,
  and a symbol — and don't reuse it from another site."

### Step 7 — Submit the demo form

**User action:** type the current password, type a new password
≥ 12 characters in both new + confirm fields, tap
`Key('change_password_dialog_submit')` (or press Enter on the
confirm field).

**Expected:**

- The dialog closes (`Key('change_password_dialog')` no longer in
  tree).
- `Key('account_section_password_toast')` renders under the Change
  password CTA with green check icon and the text "Password updated".
- After ~4 seconds the toast disappears on its own.

> **Demo vs live:** in `11W.7` the toast is purely client-side. Once
> `11W.0.live` wires the dialog to the existing Phase 9 password
> rotation route, the proxy verifies the current password against
> the password policy, performs the rotation, and writes the audit
> row that route already produces.

### Step 8 — Scroll to Terms and conditions

**User action:** scroll until `Key('account_section_tos')` is visible.

**Expected:**

- `Key('account_section_tos_accepted_line')` reads "Accepted v1.0 on
  2026-04-15".
- `Key('account_section_tos_view')` button labelled "View current T&Cs"
  is visible.
- Tapping it opens `Key('view_tos_dialog')` rendering the universal
  inbound-vendor T&Cs body inside `Key('view_tos_dialog_scroll')`
  (a scrollable read-only panel). The header line reads
  "Version 1.0.0 • effective 2026-05-03". Tap
  `Key('view_tos_dialog_close')` to dismiss. The dialog's max height
  scales with the viewport so the close button stays in view at
  768×1024.

### Step 9 — Permission gate negative path (location_manager)

**User action:** sign out, then re-enter via
`DemoOperatorWebAuthSource.completedAsLocationManager()` (the demo
session swapper exposes this path next to the existing owner / admin
seeds).

**Expected:**

- `Key('account_section_profile')` renders identically to step 1
  (read-only at every role).
- `Key('account_section_tos')` and `Key('account_section_tos_view')`
  remain visible (read-only T&Cs view).
- `Key('account_section_mfa_enroll')`'s `OutlinedButton.onPressed` is
  `null` (button disabled). Hovering reveals tooltip copy "Only
  operator admins can change MFA. If your role should include this,
  ask the operator owner on your account to update your role."
- `Key('account_section_password_change')`'s `OutlinedButton.onPressed`
  is `null`. Hovering reveals tooltip copy "Only operator admins can
  change account passwords from the web console. Floor staff and
  location managers can rotate their own password from the operator
  mobile app under Settings → Security."

### Step 10 — Resize viewport to tablet 768×1024

**User action:** resize the browser to 768×1024.

**Expected:**

- All four section keys (`account_section_profile`,
  `account_section_mfa`, `account_section_password`,
  `account_section_tos`) remain visible.
- The Profile section flips from
  `Key('account_section_profile_two_column')` to
  `Key('account_section_profile_single_column')`. Fields stack
  vertically with the same labels and helper copy.
- Section cards keep their existing chrome — same `AppColors`,
  same `AppTextStyles`, same `BorderRadius.circular(8)`. No layout
  overflow; no horizontal scroll.

### Step 11 — Sign out

**User action:** tap `Key('operator_web_header_signout')`.

**Expected:**

- The auth source emits `OperatorWebSignedOut`; the router redirects
  to the welcome screen (`Key('operator_web_welcome_token_field')`
  visible).

## Permission gating evidence

The Phase 9 proxy routes the screen wires into already enforce the
role gate server-side (`operator_owner` / `operator_admin` for write;
`location_manager` denied). The client-side gate in
`_canWriteAccount` is the friendly-error layer per the UX writing
standard.

| Role               | Profile | MFA enroll | View backup codes | Password change | T&Cs view |
| ------------------ | ------- | ---------- | ----------------- | --------------- | --------- |
| `operator_owner`   | read    | enabled    | enabled           | enabled         | enabled   |
| `operator_admin`   | read    | enabled    | enabled           | enabled         | enabled   |
| `location_manager` | read    | disabled   | enabled (if enrolled) | disabled    | enabled   |

The gate is keyed off `OperatorWebSession.roles`; the frozen
`PermissionKeys` catalog (`lib/auth/permission_keys.dart`) is
unchanged. No new keys were added. No new proxy routes were added.
The existing Phase 9 audit log writes the audit row on each MFA /
password mutation route as before — those routes stay unbroken;
`11W.0.live` swaps the in-screen demo flips for real calls into
them.

## Brand styling

`lib/theme/app_theme.dart` is unchanged. The Account screen reuses

(Playfair Display + IBM Plex) the rest of the operator-web shell uses:

- Section card chrome: `AppColors.backgroundSurface` body,
  `AppColors.borderSubtle` 1-pt border, `BorderRadius.circular(8)`.
- Section icon + accent text: `AppColors.sunsetDark`.
- Section explainer + secondary text: `AppColors.textSecondary` /
  `AppColors.textMuted`.
- Status badges: `AppColors.positive` (enrolled), `AppColors.textMuted`
  (not enrolled).
- CTA buttons: `OutlinedButton` with `AppColors.sunsetDark` border +
  foreground.
- Toast: `AppColors.positive` accent at 10% bg, 45% border.
