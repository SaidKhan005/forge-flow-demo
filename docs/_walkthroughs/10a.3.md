## 10a.3 Walkthrough - bounded event_outbox retention sweep + lag-hours metric (F&F-internal click-path)

**Slice:** 10a.3 (Phase 10a Shared Multi-Device State V1, layered: bounded retention sweep + sweep-history log + `/health` lag-hours metric)
**Mode:** F&F-internal staging only. No operator-facing UX in this slice (per `memory/project_v1_lean_cut_2_2026_05_03.md`, retention-sweep observability is engineering-grade only). V1 surface is logs + admin SQL + the proxy `/health` envelope.
**Date:** 2026-05-05

This walkthrough closes the bounded-sweep + sweep-history half of the Phase 10a retention work. The earlier 10a.3 slice (`db/migrations/202605050200_phase_10a_3_event_outbox_retention.sql`) shipped an unbounded `event_outbox_retention_sweep()` function and a daily 09:00 UTC pg_cron schedule. Two operational gaps remained:

1. A backlogged sweep (millions of delivered rows past the 7-day window during a Pub/Sub regional outage) would hold a long row-level lock on the live table, starving the bridge claim path.
2. With nothing recorded across sweep runs, the proxy `/health` envelope had no way to tell "sweep just ran" from "sweep has been broken for a week".

This slice ships:

- A new bounded function `public.run_event_outbox_retention_sweep()` (LIMIT 10000 per call) that DELETEs delivered rows older than the 7-day window and INSERTs one row into a new `public.event_outbox_retention_sweep_log` table per pass.
- A new pg_cron job `event_outbox_retention_sweep_daily` running at 03:00 UTC daily.
- A new `/health` producer `event_outbox_retention_lag_hours` keyed off `MAX(swept_at)` from the log table.
- An env-var override (`EVENT_OUTBOX_RETENTION_LAG_YELLOW_HOURS`, `EVENT_OUTBOX_RETENTION_LAG_RED_HOURS`) on the lag thresholds so a staging hot-fix can re-tune without a redeploy.

The Hard Promise this slice realizes:

> Per-operator isolation is non-negotiable. RLS-ready schema from day one; Phase 9 enforces.

The new `event_outbox_retention_sweep_log` table carries an always-NULL `operator_id` column so the tenant-leading index discipline lands cleanly even though the sweep aggregates platform-wide. Per CLAUDE.md "RLS performance discipline" and `tool/index_leading_column_lint.dart`, every B-tree on a table that declares `operator_id` MUST lead with it; the recent-pass index honors the rule.

## What the slice ships

### Database

- `db/migrations/202605051000_phase_10a_3_outbox_retention_sweep.sql`:
  - `public.event_outbox_retention_sweep_log` table with `id bigserial primary key`, `operator_id uuid null` (always NULL, present for index-discipline), `swept_at timestamptz not null default now()`, `deleted_count bigint not null check (deleted_count >= 0)`, `cap_hit boolean not null default false`. RLS off. Grants: `forge_admin` SELECT/INSERT/UPDATE/DELETE; `service_role` deliberately omitted.
  - Tenant-leading recent-pass index `event_outbox_retention_sweep_log_recent_idx (operator_id, swept_at desc)`.
  - SECURITY DEFINER function `public.run_event_outbox_retention_sweep()` owned by `forge_admin`. Body: a CTE picks up to 10000 victim ids (`select id from public.event_outbox where delivered_at is not null and delivered_at < now() - interval '7 days' order by delivered_at limit v_cap`), a single DELETE drops them, the function INSERTs one row into the log table with `(now(), v_deleted, v_deleted >= v_cap)`, and returns the deleted-row count.
  - Defensive grants: `revoke execute ... from public`, `grant execute ... to forge_admin`.
  - pg_cron schedule `event_outbox_retention_sweep_daily` at `'0 3 * * *'` (03:00 UTC daily). Idempotent unschedule-then-reschedule. Azure split-database NOTICE-and-return guard for the cross-`cron.database_name` case.

### `/health` metric

- `tool/advisor_proxy/health_producers/outbox_producers.dart`:
  - New `eventOutboxRetentionLagProducer` registered under `event_outbox_retention_lag_hours`. SQL: `select extract(epoch from (now() - max(swept_at))) / 3600 as lag_hours from public.event_outbox_retention_sweep_log`. Default thresholds: yellow 36h (sweep missed two daily cron passes), red 168h (sweep missed a full week).
  - NULL-safe: when `MAX(swept_at)` returns NULL (no sweep has ever logged a row), the producer projects `status: unknown`, `value: null`, `metadata: { tier: 2, sweep_never_ran: true }`.
  - Env-var override: `EVENT_OUTBOX_RETENTION_LAG_YELLOW_HOURS` and `EVENT_OUTBOX_RETENTION_LAG_RED_HOURS`. Resolver falls back to defaults on missing/blank/non-numeric/non-positive values; an inverted pair clamps red to `yellow + 1` so the yellow band never collapses.

### What the slice intentionally does NOT ship

- **No bridge worker edits.** `tool/advisor_proxy/realtime_bridge.dart`, `lib/services/realtime/realtime_event_publisher.dart`, and `lib/services/realtime/pubsub_realtime_publisher.dart` are byte-identical pre/post. The NOTIFY-as-wake-up-only invariant is preserved.
- **No retirement of the legacy 09:00 UTC sweep.** `forge_event_outbox_retention_sweep` (from `202605050200_phase_10a_3_event_outbox_retention.sql`) keeps running for one release cycle as a belt-and-braces fallback. A follow-up migration retires it after operators confirm the bounded path is keeping the table drained.
- **No operator-facing UX.** Per the V1 lean cut, retention-sweep observability is engineering-grade only. F&F engineers triage via log search + admin SQL.

## Click path (F&F engineer at staging psql + curl)

Four numbered steps. Each step names the action, the SQL or curl command, and the expected DB row state (or `/health` JSON shape) after the action.

### Step 1 - Seed three delivered event_outbox rows older than 7 days

**Action:** F&F engineer connects to staging Postgres as `forge_admin` and seeds three rows whose `delivered_at` falls past the 7-day retention window. The seed rows are flagged `delivered_at = now() - INTERVAL '8 days'` so they immediately match the sweep predicate.

**SQL (engineer types):**

```sql
INSERT INTO public.event_outbox
  (operator_id, topic, payload, delivered_at, picked_up_at, attempt_count)
SELECT
  '11111111-1111-1111-1111-111111111111',
  'rollup.invalidate.variance_week',
  jsonb_build_object(
    'event_id', 'retention-seed-' || gs::text,
    'occurred_at', '2026-04-27T00:00:00.000Z',
    'note', 'walkthrough seed - delivered 8 days ago'
  ),
  now() - interval '8 days',
  now() - interval '8 days',
  1
FROM generate_series(1, 3) AS gs
RETURNING id;
```

The seed values for `delivered_at` (8 days ago) put the rows squarely past the 7-day cutoff. `picked_up_at` and `attempt_count` mirror what the bridge would have stamped on a healthy publish ladder so the rows look indistinguishable from production-shaped delivered rows.

**Expected DB row state:**

```text
public.event_outbox row count where delivered_at IS NOT NULL
  AND delivered_at < now() - INTERVAL '7 days'  =  3
public.event_outbox_retention_sweep_log row count             =  0
```

**Verify:**

```sql
SELECT count(*)
  FROM public.event_outbox
 WHERE delivered_at IS NOT NULL
   AND delivered_at < now() - INTERVAL '7 days';
-- 3

SELECT count(*) FROM public.event_outbox_retention_sweep_log;
-- 0
```

### Step 2 - Run the bounded sweep manually; verify it deletes the seeded rows AND writes a log row

**Action:** Engineer invokes the bounded sweep directly (instead of waiting for the 03:00 UTC cron). The function returns the deleted-row count. With 3 rows past the window and a cap of 10000, all three should be deleted and `cap_hit` should be false on the resulting log row.

**SQL:**

```sql
SELECT public.run_event_outbox_retention_sweep();
-- 3
```

**Expected DB row state:**

```text
public.event_outbox row count where delivered_at IS NOT NULL
  AND delivered_at < now() - INTERVAL '7 days'  =  0   (sweep removed all three)
public.event_outbox_retention_sweep_log row count             =  1   (one row per pass)

public.event_outbox_retention_sweep_log row:
  id              = <returned bigserial>
  operator_id     = NULL    (platform-wide aggregate)
  swept_at        ~ now()
  deleted_count   = 3
  cap_hit         = false   (3 < 10000)
```

**Verify:**

```sql
SELECT count(*)
  FROM public.event_outbox
 WHERE delivered_at IS NOT NULL
   AND delivered_at < now() - INTERVAL '7 days';
-- 0

SELECT operator_id, swept_at, deleted_count, cap_hit
  FROM public.event_outbox_retention_sweep_log
 ORDER BY swept_at DESC LIMIT 1;
-- operator_id = NULL; deleted_count = 3; cap_hit = false; swept_at ~ now()
```

The un-delivered head of the queue (rows where `delivered_at IS NULL`) is untouched. Verify by counting un-delivered rows before and after; the count is identical because the bounded sweep's CTE filter is `delivered_at IS NOT NULL`.

```sql
-- Before the sweep + after the sweep should produce the same value;
-- the sweep does NOT remove un-delivered rows.
SELECT count(*) FROM public.event_outbox WHERE delivered_at IS NULL;
```

### Step 4 - Env-var override: tighten yellow to 1h, redeploy, verify the threshold flip

**Action:** Engineer tightens the yellow threshold from 36h to 1h to validate the override path. The lag value (a few seconds since the step-2 sweep) is still under 1h, so the metric stays green even with the lower bar. Then engineer artificially ages the log row by 90 minutes and confirms the new threshold flips the status to yellow.

```bash
gcloud run services update advisor-proxy \
  --region=northamerica-northeast2 \
  --update-env-vars=EVENT_OUTBOX_RETENTION_LAG_YELLOW_HOURS=1,EVENT_OUTBOX_RETENTION_LAG_RED_HOURS=24
```

After the new revision rolls out, hit `/health` again:

```bash
curl -s "$STAGING_PROXY/health" | jq '.metrics.event_outbox_retention_lag_hours.thresholds'
```

```json
{"yellow": 1, "red": 24}
```

Now backdate the log row to force the threshold to fire. The bounded sweep writes `swept_at = now()` server-side, so the engineer pushes the log row's `swept_at` back by 90 minutes via direct UPDATE (only `forge_admin` can do this; `service_role` lacks UPDATE on the log table by grant shape):

```sql
UPDATE public.event_outbox_retention_sweep_log
   SET swept_at = now() - interval '90 minutes'
 WHERE id = (SELECT max(id) FROM public.event_outbox_retention_sweep_log);
```

**Expected `/health` after the backdate:**

```json
{
  "status": "yellow",
  "value": 1.5,
  "unit": "hours",
  "description": "...yellow at 1h (sweep missed two daily cron passes) and red at 24h (sweep missed a full week).",
  "source": "event_outbox_retention_sweep_log",
  "owner": "Phase 10a",
  "observed_at": "2026-05-05T...Z",
  "thresholds": {"yellow": 1, "red": 24},
  "metadata": {"tier": 2}
}
```

`status: yellow` because `value (1.5) >= thresholds.yellow (1)` and `value < thresholds.red (24)`.

After the drill the engineer reverts the env override:

```bash
gcloud run services update advisor-proxy \
  --region=northamerica-northeast2 \
  --remove-env-vars=EVENT_OUTBOX_RETENTION_LAG_YELLOW_HOURS,EVENT_OUTBOX_RETENTION_LAG_RED_HOURS
```

The producer falls back to the documented defaults (36h yellow / 168h red). The next staging cron pass at 03:00 UTC writes a fresh `swept_at = now()` row and the metric returns to green.

## Permission gating evidence

- **Sweep function.** `public.run_event_outbox_retention_sweep()` is SECURITY DEFINER, owned by `forge_admin`. The cross-operator DELETE inherits `forge_admin BYPASSRLS` so the predicate sees rows across every tenant without juggling tenant context inside the cron caller. EXECUTE is REVOKEd from `public` and GRANTed to `forge_admin` only; `service_role` cannot trigger the sweep on its own.
- **Log table grants.** `forge_admin` gets the full DML set (SELECT/INSERT/UPDATE/DELETE). `service_role` is deliberately omitted; the log is platform-wide bookkeeping that tenants have no business reading or writing. The proxy `/health` producer reads through the admin pool.
- **Tenant-leading index.** Even though `operator_id` is always NULL on this table, the recent-pass index leads with `(operator_id, swept_at desc)` so the index-leading-column lint passes. Future per-operator rollup of sweep work could write a real value without re-keying the index.
- **`/health` aggregate.** The `event_outbox_retention_lag_hours` producer runs through `_buildRegistryProxyHealthCheckStore`'s admin-pool runner with `runAsSystem` because the envelope is platform-wide (no tenant identifiers per the envelope contract). The producer's metadata never carries `operator_id` or `location_id`.
- **No new permission keys.** No operator-facing UX in this slice means no new entry in the auth permission key catalog.
