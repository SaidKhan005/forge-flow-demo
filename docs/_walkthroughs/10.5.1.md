# 10.5.1 Walkthrough — Daypart bucketing engine

**Slice:** 10.5.1 (Phase 10.5 — Shift daypart-aware service period view + primary driver)
**Mode:** pure-function domain library; no UI surface, no I/O, no demo seed dependency
**Date:** 2026-05-02

This walkthrough proves the engine that 10.5.0's surface scaffold has
been waiting on. `DaypartBucketer` takes operational facts (POS lines,
labor punches, reservations) carrying restaurant-local timestamps and
classifies them into service-period buckets using
`ServicePeriodDefinitionResolver` + `BusinessDateResolver`. It is pure
domain code — no widgets are touched, no notifiers are added, no
read-service is wired. 10.5.2 will consume these segments to populate
the per-period covers / sales / FOH hours / wage accumulators.

The Hard Promise this slice contributes to:

> Shift's whole-day view is authoritative; 10.5 adds daypart
> alongside, never replacing.

The whole-day path remains untouched; the engine only produces the
inputs that the future daypart read service will consume.

## Boundary semantics — two views, one ruleset

Two semantics live in the engine; both derive from the phase doc.

1. **Point-in-time classification (POS line, reservation).** Inclusive
   at both `startLocalTime` and `endLocalTime`, compared at full
   sub-minute precision. An event at exactly 15:00:00.000 with Lunch
   11:00–15:00 belongs to Lunch (per the phase doc's worked example);
   `15:00:00.001` and beyond fall into the post-Lunch gap and bucket
   to `null`. Same rule applies symmetrically to rolls-past-midnight
   ends — `02:00:00.000` is Late Night, `02:00:00.001` is the gap.

   > An event at 15:00:00 with Lunch 11:00 to 15:00 and Dinner 17:00
   > to 22:00 belongs to Lunch.

   The classifier uses a `Duration` time-of-day comparison so seconds,
   milliseconds, and microseconds carry through the boundary check
   instead of being truncated. (Vendor POS feeds typically expose
   second precision; ignoring sub-minute components would silently
   widen each ending boundary by 59 seconds.)

   For back-to-back periods (no gap), the first-in-`sortOrder` period
   wins, matching the existing 10.5.0 active-chip resolver.

2. **Punch minute-counting.** Half-open at the upper end so the phase
   doc's worked example reconciles exactly:

   > Lunch intersection: 14:30 to 15:00 equals 30 minutes.

   The minute starting at 15:00:00 is therefore the first minute of
   the post-Lunch gap (it does not double-count back into Lunch).
   POS lines and labor minutes are different kinds of facts — a POS
   close is a dimensionless instant; a labor minute is a 60-second
   span. Treating both with consistent inclusive-end semantics would
   double-count the boundary minute; honoring the phase doc's
   worked-example arithmetic requires the half-open convention here.

3. **Business-date weekday governs applicability.** A 02:00
   Sunday-calendar instant with cutoff 04:00 belongs to Saturday's
   business date, so a Fri/Sat-only Late Night period stays
   applicable. The engine routes every fact through
   `BusinessDateResolver.resolve` first, then uses
   `DateTime.parse(businessDate).weekday` (ISO 1=Mon … 7=Sun) for
   the `applicableDays.contains` check. Wall-clock weekday is never
   consulted.

4. **Missing IANA timezone refuses to fall back.** The bucketer
   throws `MissingTimezoneError` rather than degrading to the device
   clock. This matches the boundary monitor's posture and
   propagates a configuration mistake out of the data layer instead
   of silently corrupting buckets. (The engine itself does not
   perform timezone conversion — inputs are assumed restaurant-local
   per the canonical-fact contract — but the IANA field's presence
   is asserted as a config check.)

## Engine API (one screen)

```dart
const location = BucketingLocationContext(
  iana: 'America/St_Johns',
  businessDayStartLocalTime: '04:00',
);
final defs = ServicePeriodDefinitionResolver.demoDefinitions;

// POS line → ServicePeriodId? (null = non_service / between periods)
final lunchHit = DaypartBucketer.bucketPosLine(
  BucketingPosLine(
    sourceId: 'order_xyz',
    eventLocalTimestamp: DateTime(2026, 5, 4, 12, 30), // Mon 12:30
  ),
  location,
  defs,
); // → 'lunch'

// Reservation → ServicePeriodId? (same point-in-time semantics)
final dinnerRes = DaypartBucketer.bucketReservation(
  BucketingReservation(
    sourceId: 'res_xyz',
    reservationLocalTimestamp: DateTime(2026, 5, 8, 18, 30),
  ),
  location,
  defs,
); // → 'dinner'

// Labor punch → List<LaborPunchSegment> (chronological, gap-aware)
final segments = DaypartBucketer.bucketLaborPunch(
  BucketingLaborPunch(
    sourceId: 'punch_xyz',
    clockedInLocal: DateTime(2026, 5, 4, 14, 30),
    clockedOutLocal: DateTime(2026, 5, 4, 22, 30),
  ),
  location,
  defs,
);
// → [
//      LaborPunchSegment(servicePeriodId: lunch,       start: 14:30, end: 15:00, minutes: 30),
//      LaborPunchSegment(servicePeriodId: non_service, start: 15:00, end: 17:00, minutes: 120),
//      LaborPunchSegment(servicePeriodId: dinner,      start: 17:00, end: 22:30, minutes: 330),
//    ]
```

## Worked example #1 — Punch-split (Mon 14:30 → 22:30)

This is the phase plan's worked example, extended to span the full
Dinner window (the plan's reference example used 14:30 → 19:00; the
test extends `clockOutLocal` to 22:30 to exercise the full Dinner
intersection).

| Slice                    | Period         | Start   | End     | Minutes |
|--------------------------|----------------|---------|---------|--------:|
| Lunch ∩ punch            | `lunch`        | 14:30   | 15:00   |      30 |
| Gap (between periods)    | `non_service`  | 15:00   | 17:00   |     120 |
| Dinner ∩ punch           | `dinner`       | 17:00   | 22:30   |     330 |
| **Total**                |                | 14:30   | 22:30   | **480** |

Reconciles to the punch's 8h00 duration. The non-service slice is
emitted explicitly so the future read service does not need to
recompute gap-time — it can either record it (drives the
`non_service` exclusion the plan calls out) or drop it.

## Worked example #2 — Boundary tie-break (Mon 15:00:00)

A POS line closing at exactly 15:00:00 on a Monday with the demo
definitions:

- `BusinessDateResolver.resolve(15:00, 04:00)` = `2026-05-04` (Mon,
  weekday 1).
- Lunch applicable on weekday 1: ✓.
- Lunch period [11:00, 15:00], inclusive end: 15:00 ∈ [11:00, 15:00] ✓.
- First match in `ordered(...)` wins: `lunch`.

The same instant inside a labor punch behaves differently —
`bucketLaborPunch` for a punch covering 14:45 → 15:30 produces:

| Slice                | Period        | Start | End   | Minutes |
|----------------------|---------------|-------|-------|--------:|
| Lunch ∩ punch        | `lunch`       | 14:45 | 15:00 |      15 |
| Post-Lunch gap       | `non_service` | 15:00 | 15:30 |      30 |

That divergence is intentional (see "Boundary semantics" above). The
engine documents both at the call site and in the public class
header.

## Worked example #3 — Late Night roll-over (02:00 Sun-calendar)

The Late Night demo definition spans 23:00 → 02:00 with
`rollsPastMidnight: true` and `applicableDays: [5, 6]` (Fri / Sat).
For an event at calendar Sun 2026-05-10 02:00:00:

- `BusinessDateResolver.resolve(02:00, 04:00)` = `2026-05-09` (Sat,
  weekday 6) because 02:00 falls before the cutoff and rolls back
  one calendar day.
- Late Night applicable on weekday 6: ✓.
- Late Night [23:00, 02:00] with `rollsPastMidnight`, instant
  minutes = 120: `120 >= 1380 || 120 <= 120` → `true` → `late_night`.

For a labor punch crossing the boundary (Sat 23:30 → Sun 01:30):

- `_businessDatesSpanning` = `{2026-05-09}` (both ends fall before
  the 04:00 cutoff so both resolve to Sat).
- `_periodIntervalsOnBusinessDate(Late Night, 2026-05-09, 04:00)` =
  `[(start: 2026-05-09 23:00, end: 2026-05-10 02:00)]` (rolls past
  midnight, end calendar day = start calendar day + 1).
- Intersect with punch [23:30, 01:30 next day]: single segment
  `late_night [23:30, 01:30, 120 min]`. No `non_service` slivers.

This is the case the plan calls out: a punch that crosses calendar
midnight stays on the originating business date and is correctly
attributed to the rolls-past-midnight period without hand-rolling
date math at the call site.

## Boundary checks

- **No widget code touched.** `lib/screens/shift_dashboard.dart` is
  unchanged; the conceptual pattern from `_DaypartScaffoldSection`
  was lifted into pure domain code without cross-importing the
  widget layer.
- **No service or read-service added.** `lib/services/`,
  `lib/state/`, and `lib/data/` are untouched. The engine returns
  pure value types (`LaborPunchSegment`, `String?`) — no providers,
  no notifiers, no I/O.
- **No I/O dependency.** The engine takes `DateTime` inputs that
  the caller has already mapped from vendor UTC to restaurant-local
  (per the canonical-fact contract). The bucketer does not import
  `package:timezone`, `package:provider`, or any `lib/data/`
  module.
- **No persisted timing config dependency.** The engine consumes
  `BucketingLocationContext` (a thin value type) and a
  `List<ServicePeriodDefinition>` directly. The deferred Settings
  editor and `RestaurantTimingConfigReadService` wiring remain
  prerequisites for *production* live data — not for the engine
  itself, which operates against any caller-supplied definitions
  list (demo or persisted).
- **No tracker or memory edits required by the engine itself.**
  Tracker movement (10.5.0 row → append `.1 accepted`; phase doc
  status line → 10.5.1 accepted) is part of slice handoff, not the
  engine surface.
- **Symbol overlap with the 10.5.0 widget resolver is intentional.**
  `_classifyInstant` in the engine and `_resolveActivePeriodId` in
  the widget share the same conceptual rules (inclusive endpoints,
  business-date weekday, first-in-`sortOrder` tie-break). The
  engine tightens those rules to full sub-minute precision; the
  widget still does minute-precision comparisons against
  `tz.TZDateTime.now(loc)` and a 30-second ticker, which keeps the
  operator-visible chip well within tolerance for an active-now
  indicator but is not exact at the second / millisecond grain.
  10.5.2 will replace the widget's local resolver with a call to
  this engine during read-service plumbing, at which point sub-
  minute exactness becomes shared. This slice ships the
  duplication deliberately to keep the 10.5.0 widget regression
  untouched.

## Notes for 10.5.2 (read service)

- The engine returns `non_service` slivers in punch segments. The
  read service should subtract these from CPLH / SPLH denominators
  per the phase doc's labor-punch split rule (Jim Taylor
  methodology).
- `LaborPunchSegment.minutes` is an integer because every input is
  truncated to minute precision; the read service can multiply by
  hourly wage and divide by 60 to recover wage dollars per the
  plan's worked example.
- Correction replay (the plan's `order_modified` /
  `punch_edit` / `punch_delete` semantics) is *not* in this slice.
  The engine is stateless; correction replay belongs in the read
  service that owns the per-fact source-id index.
- The accumulator (covers, sales, hours, CPLH, SPLH, PPA, blended
  wage) is also not in this slice — the engine emits buckets, the
  read service folds vendor payloads into per-period totals.
