## 9.UX.3 — Settings Team "Explain permissions" surface

Date: 2026-04-30

## Scope

Add a read-only "Explain permissions" surface that shows operators
exactly how a target user's resolved permission for a chosen key was
arrived at. The surface is reachable from each user's action menu in
Settings → Team and routes to a full-screen explainer that:

- Lets the operator pick any permission key from the frozen 96-key
  catalog (`PermissionKeys.all`), grouped by category prefix
  (`product`, `forgeflow`, `barrio`, `admin`, `team`, `billing`,
  `integration`, `workflow`).
- Lets the operator pin the resolution scope — "Operator-wide" (the
  default) or any of the operator's locations.
- Renders the resolution chain: one row per `user_roles` grant on the
  target, showing the source role, the rule effect on that role for
  the selected key (Allow / Deny / Inherit), the scope label
  (operator-wide / `{org_unit}` (`N` location[s]) / `{location}`),
  and whether the grant covers the selected scope.
- Surfaces the final effect — Allow / Deny / Not granted — as a pill
  computed by the live `PermissionResolver.resolve()` from
  `lib/auth/permission_resolution.dart`. The chain is purely
  explanatory; the resolver remains the single source of truth.

The surface is gated on `team.users.view` — the same key that gates
the Team tab itself — both at the menu entry and at the screen-level
refusal banner.

## Operator Walkthrough (`kDemoMode = true`)

1. Launch ForgeFlow in demo mode and sign in as the demo operator
   owner (`demo.operator@forgeflow.test` / `forge-flow-demo`).
2. Open Settings → Team. Locate a user with at least one role grant in
   the **Members** list.
3. Tap the `…` user-action menu for that user
   (`team_user_actions_<userId>`). Confirm a new "Explain permissions"
   entry appears alongside the existing actions.
4. Tap **Explain permissions**. The full-screen explainer opens
   (`settings_permission_explainer`). Confirm the AppBar reads
   "Explain permissions" and the target header shows the user's
   display name, email, role chip, optional location chip, and a
   grant count.
5. The picker defaults to the first ordered permission key. Open the
   picker (`settings_permission_explainer_picker`) and select
   `team.users.invite`. Confirm:
   - Each chain row (`settings_permission_explainer_chain_<grantId>`)
     shows the role display name, rule pill, and four labelled
     attributes: Source role, Scope, Scope applies at selected
     location, and Rule effect for `team.users.invite`.
   - For an operator-wide owner grant, the rule pill reads **Allow**,
     the scope reads **Operator-wide**, and the final pill
     (`settings_permission_explainer_final_effect`) renders **Allow**.
6. Switch the picker to a permission the target lacks (e.g.
   `forgeflow.weekly_plan.lock` for a non-owner). Confirm the chain
   rows render an **Inherit** rule pill with "No rule on this role"
   copy and the final pill renders **Not granted**.
7. Switch to a permission with an explicit deny on the target's role
   stack (build a fixture user that holds both an owner grant — which
   allows `team.users.invite` — and a custom role grant that denies
   `team.users.invite`). Confirm the deny rule wins: the rule pill on
   the deny grant renders **Deny**, the chain row attribute reads
   "Deny — the role explicitly blocks this permission and wins over
   allow rules", and the final pill renders **Deny**.
8. Use the scope picker
   (`settings_permission_explainer_scope_picker`) to switch from
   **Operator-wide** to a specific location the target does not hold
   a grant at. Confirm the chain row's "Scope applies at selected
   location" attribute flips to "No — grant excluded at this scope"
   and the final pill drops to **Not granted**.
9. Open the explainer for an org-unit-scoped grant (e.g. a manager
   with a grant under "East Region" covering three locations). Switch
   the scope picker to a location inside that org unit. Confirm the
   row's Scope attribute reads `East Region (3 locations)` and the
   "Scope applies at selected location" attribute reads "Yes". Switch
   to a location outside the unit — the same row's scope attribute
   stays the same, the apply attribute flips to "No — grant excluded
   at this scope", and the final pill drops to **Not granted**.
10. Sign out and sign in as a manager who lacks `team.users.view`.
    Open Settings → Team. Confirm the Team tab is locked behind the
    existing visibility policy (Phase 9.10) — the user-action menu is
    not reachable, and consequently the "Explain permissions" entry
    is unreachable as well.

## Contract Notes

- **Resolver is authoritative.** The screen calls
  `PermissionResolver.resolve(permissionKey, grants, rules,
  operatorId, locationId, now)` for the final pill. The chain rows
  trace the same data the resolver consumed, but no resolution logic
  is duplicated.
- **Inputs use already-loaded data.** `roleCatalog` flows from
  `SettingsScreen.teamRoleCatalog` (an existing
  `TeamRoleCatalogListed` consumer that gates Roles tab editing) —
  the live `teamRoleCatalogListenable` value is forwarded through
  `_RoleCatalogToOptionsScope`'s `(options, catalog)` builder so the
  explainer never resolves against a stale seed if the catalog
  hydrates after Settings opens. `orgUnitOptions` and
  `locationOptions` flow from the existing
  `SettingsScreen.teamOrgUnitOptions` /
  `SettingsScreen.teamLocationOptions`. There is no new gateway
  call, no new proxy route, no new permission key.
- **Fallback grant synthesis (always operator-wide).** Today's
  production wiring (`_teamUserFromEntry` in `forge_flow_app.dart`)
  leaves `TeamUserListItem.grants` at its `const []` default because
  `TeamUserListEntry` does not yet carry an authoritative
  `scope_type` field — that lands in the gateway slice that follows
  this lane. To keep the explainer useful before that slice ships,
  the screen synthesizes one fallback `TeamUserRoleGrant` from
  `target.userRoleId` + `target.roleId` when `target.grants` is
  empty. The synthesis is **always** `scope_type = 'operator_wide'`
  with no `locationId`. The reason: `TeamUserListEntry.locationId`
  projects `coalesce(ur.location_id, u.primary_location_id)`, so a
  non-null value is ambiguous — it could be either a
  `location`-scoped grant's `ur.location_id` OR an operator-wide
  grant attached to a user with a primary location. Synthesizing as
  `'location'` would silently drop true operator-wide grants at
  every other scope (the resolver's `coversLocation` filter excludes
  them) and the final pill would say "Not granted" even though the
  real `PermissionResolver` with the authoritative grant would
  allow. `'operator_wide'` is the only safe floor: the role's rules
  surface at every scope, matching what an operator-wide user
  actually sees. The trade-off is that a truly location-scoped user
  appears to have access at every scope until the upstream slice
  lands — the inline hint flags this approximation. The synthesized
  row renders an inline "Scope inferred from primary grant — full
  grant set is not yet projected onto this user." hint (key
  `settings_permission_explainer_synth_<userRoleId>`) and the
  Scope attribute reads "Operator-wide (inferred)" so the operator
  knows the trace was derived from the entry's primary grant rather
  than the full `user_roles` row set.
- **Chain semantics.** A chain row's rule pill reads:
  - **Allow** — the role has an explicit `allow` rule for the key.
  - **Deny** — the role has an explicit `deny` rule for the key.
    Deny wins over allow rules on sibling roles.
  - **Inherit** — the role has no explicit rule (the chain row
    reads "No rule on this role (inherits from defaults)").
- **Pill semantics.** The pill reads:
  - **Allow** — `PermissionResolver` returned `allow`.
  - **Deny** — `PermissionResolver` returned `deny` AND at least one
    grant covering the selected scope held a rule referencing the
    selected key.
  - **Not granted** — `PermissionResolver` returned `deny` AND no
    grant covering the selected scope held any rule for the selected
    key (default-deny path).
- **Scope picker.** Operator-wide is modeled as `locationId = ''`
  in the resolver call; location-scoped grants and org-unit grants
  fail `coversLocation('')` and drop out, matching the runtime
  semantics. Selecting a real location feeds that string straight
  into the resolver — operator-wide grants always cover, org-unit
  grants cover when the location is in `effectiveLocationIds`, and
  location-scope grants cover when the `location_id` matches.
- **Scope picker default — stale `locationId` defense.** The picker
  defaults to the target's primary `locationId` only when that
  `locationId` actually appears in `locationOptions`. If the
  target's primary location is missing (stale data, filtered
  options, or upstream not yet loaded), the picker silently falls
  back to "Operator-wide" rather than feeding `DropdownButton` a
  value with no matching item. The same defense runs at every
  rebuild — if `locationOptions` shrinks live, the dropdown's
  rendered value degrades to "Operator-wide" instead of asserting.
- **Stale-label fallback.** If a grant references an `org_unit_id` /
  `location_id` that is not in the parent's options list (e.g.
  deleted between the gateway fetch and the explainer opening), the
  scope label degrades to `Org unit (unknown)` /
  `Location (unknown)` rather than crashing. The same goes for a
  grant whose `role_id` is missing from the role catalog — the chain
  row falls back to `grant.roleLabel` and the rule attribute reads
  "No matching role rule (role not in catalog)".
- **Permission gating.** The screen short-circuits to a polite
  refusal banner if it ever receives an actor without
  `team.users.view`. The menu entry in `team_settings_section.dart`
  is gated on the same key, so this branch is reachable only via
  defensive routing.
- **Brand styling.** All chain rows, attribute labels, and the
  final-effect pill use `lib/theme/app_theme.dart` tokens
  (`AppColors.sunset` / `AppColors.sunsetDark`,
  `AppColors.peacock`, `AppColors.positive` /
  `AppColors.negative`, `AppTextStyles.body14` /
  `body13` / `mono12` / `mono10`). No hard-coded colors outside
  the chip-tone helpers, which derive from the same palette.

## Evidence

- `test/settings_permission_explainer_test.dart` — pins allow chain,
  deny chain (deny-wins), role-inherited allow with catalog
  display-name lookup, org-unit-inherited grant with `(N locations)`
  copy, location-scoped grant with location label, location-scoped
  grant excluded at non-matching scope (Not granted), no-rule
  fallback (Not granted), unknown-key fallback ("role not in
  catalog"), the locked-actor refusal banner, fallback synthesis for
  empty `target.grants` (Allow + inferred-scope hint with
  "Operator-wide (inferred)" Scope attribute), operator-wide
  synthesis covering a different scope than the entry primary
  location (pin against future regressions to location-scoped
  synthesis), null-location fallback, stale-location fallback, and
  the scope-picker defense against a target `locationId` missing
  from `locationOptions`.
- `test/team_settings_section_test.dart` — pins the menu entry's
  visibility against `team.users.view` (offered to viewer actor,
  hidden from locked actor) and confirms tapping the entry pushes
  the `SettingsPermissionExplainer` route.
- `test/settings_screen_widget_test.dart` — existing 55-test suite
  passes unchanged; the `Team tab renders for an allowed actor`,
  `Roles section renders catalog and create button for owner`, and
  `Roles catalog feeds TeamSettingsSection.roleOptions` cases
  exercise the same plumbing the explainer reuses.
