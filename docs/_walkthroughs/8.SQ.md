# 8.SQ Walkthrough — Square POS adapter (lifecycle = `documented`)

**Slice:** 8.SQ (Phase 8 — Wave B engineer-all-17 doctrine)
**Mode:** `kDemoMode = true` (operator app, deterministic seed). No
live HTTP — sandbox traffic is `8.SQ.live.sandbox`'s job.
**Date:** 2026-05-04
**Demo start condition:**
- Business date `2026-W18 Mon` (Monday of ISO week 18, 2026).
- Operator: "Demo Diner Co.", Location: "Toronto Yorkville".
- Shift dashboard scope: whole-day.
- POS card empty; `demo_mode_state.is_demo = true` for `pos`.
- Square is the operator's chosen POS in this walkthrough.

This walkthrough is a numbered click-path per
`docs/CODEX_PROMPT_GENERATION_STANDARD.md` Walkthrough Specificity.
Every step names the user action, the expected visual state, the
named widget(s) under test, and the named values that drive each
render.

The slice ships the Square adapter at lifecycle = `documented`. The
vendor picker shows a "Coming soon" pill on the Square row at V1
because production credentials have not yet been issued —
`8.SQ.live.sandbox` and `8.SQ.live.prod` slices promote the lifecycle
to `production_credentialed`, at which point the **Connect** button
goes live. The walkthrough still exercises the connect flow against
the sandbox / fixture path so reviewers can see the code paths
working.

## What changed in code

- `lib/integrations/pos/square_pos_adapter.dart` — `SquarePosAdapter`
  class implementing `PosAdapter`. Capability profile declares
  `lifecycle = VendorLifecycle.documented`, `coversFieldExposed =
  false`, `grantScope = operatorWide`, `webhookSupport =
  autoRegister`. The 7 framework methods (`connect`,
  `testConnection`, `backfill`, `pollIncremental`, `handleWebhook`,
  `disconnect`, plus `vendorId` / `displayName` / `capabilityProfile`
  getters) are wired with the documented Square endpoints.
- `lib/integrations/pos/square_webhook_signature_verifier.dart` —
  HMAC-SHA256 verifier over `notification_url + raw_body`,
  base64-encoded, header `x-square-hmacsha256-signature`. 24h replay
  tolerance via `square-initial-delivery-timestamp`. Constant-time
  compare (`constantTimeBytesEquals`).
- `test/integrations/pos/square_pos_adapter_test.dart` — 11 tests
  covering sanity hook count, sanity reject, idempotency replay,
  watermark mid-batch, signature reject, smoke (connect → backfill →
  poll → disconnect → reconnect), test-connection, covers fallback,
  24h replay, capability assertions, banned-items grep.
- `docs/integrations/square/{api_consumed,field_mapping,oauth_shape,webhook_signature,live_verification_checklist,partnership_status}.md` —
  the 6-file doc pack.

## Click-path

### 1. Empty POS card — operator picks Square

- Operator opens the app on `2026-05-04 (Mon, W18)`. Settings →
  Vendor connections.
- POS card slot reads "Connect your Point-of-sale (POS) system" with
  the **Choose your POS** button.
- Tap **Choose your POS** → vendor picker dialog.
  - **Widget under test:** `vendor_picker_square` row in
    `vendor_connections_picker_dialog`.
  - Square row shows the **Square** display name + a "Coming soon"
    pill (lifecycle = `documented`; production credentials not yet
    issued). Tapping the row expands a "Notify me when ready" capture
    in the Wave B chrome — but for this walkthrough the row's
    **Continue (sandbox)** affordance is enabled (engineering /
    sandbox path) and the operator selects it.

### 2. OAuth round trip (stubbed at proxy fixture)

- Tap **Continue (sandbox)**. Adapter `SquarePosAdapter.connect` is
  called with `oauthState = null` (start path). Adapter returns
  metadata carrying `oauth_authorize_path = '/oauth2/authorize'` and
  `scopes = ['ORDERS_READ', 'MERCHANT_PROFILE_READ']`.
- Proxy redirects to Square's authorize page (sandbox base
  `https://connect.squareupsandbox.com`).
- Operator approves → Square redirects to F&F callback with
  `?code=...&state=state-fixed`.
- Proxy exchanges code for tokens via `POST /oauth2/token` (V1 lean
  cut: env-var client secret; KMS rollout deferred), then re-invokes
  `SquarePosAdapter.connect` with `oauthState = 'state-fixed'`.
- Adapter calls `apiClient.registerWebhook(notificationUrl: 'https://api.forgeflow.app/v1/integrations/square/webhook/op_001/loc_001', events: ['order.created', 'order.updated'])` and
  returns `ConnectResult(status: connected, webhookUrl: <notification_url>, firstBackfillStarted: true)`.
- POS card flips to **Connected** state.
  - **Widget under test:** `_StatusBadge` in
    `lib/integrations/ui/vendor_connections/vendor_connections_widget.dart`.
  - **Expected ConnectionStatus:** `connected`.
  - **Expected metadata:** `webhook_subscription_id`,
    `notification_url`, `square_api_version: '2024-01-18'`,
    `scopes: ['ORDERS_READ', 'MERCHANT_PROFILE_READ']`.

### 3. Sales card live; covers card stays forecast — pill appears

- Tab to **Shift dashboard**. Read model resolves with
  `posSourceVendorId = 'square'`. Backfill seed has committed
  `actual_sales: 42.50` for `sq_ord_001` (closed at
  `2026-05-03T18:45:00Z`).
- Sales card renders `$42.50`, brand color, normal weight —
  IDENTICAL to today's chrome.
  - **Widget under test:** `SalesForecastCard` /
    `InputMetricCard(metric: salesCard.first)`.
  - **Expected MetricState:** `live`. Provenance `vendor_square`.
- Covers card renders the **forecast number** with the dashboard's
  forecast styling (NOT `MetricCardNotYetAvailable` — Square still
  produces a useful covers signal via the forecast).
  - **Widget under test:** `InputMetricCard(metric: coversCard.first)`.
  - **Expected MetricState:** `fallback`. Provenance
    `forecast_fallback`.
  - **Named value:** the canonical fact's `covers_source =
    forecast_fallback` is the trigger.
- PPA card renders the formatted number, IDENTICAL chrome.
  - **Widget under test:** `InputMetricCard` for `name == 'PPA'`.
  - **Expected MetricState:** `live`. Provenance `vendor_square`.
- CPLH card renders `MetricCardNotYetAvailable` widget (no labor
  source connected).
- Top-left dashboard pill renders ONE line:
  - **Widget under test:** `DataSourceHealthPill`
    (`lib/widgets/data_source_health_pill.dart`).
  - **Expected text** in `data_source_health_pill_headline`:
    `Covers: forecast (Square does not expose guest count)`.
  - When labor connects, the pill grows to two lines (CPLH live).
    When the operator switches to a covers-emitting POS later, the
    forecast line drops automatically.

### 4. Forged-signature webhook → 403, audit, no canonical write

- Send a `POST /v1/integrations/square/webhook/op_001/loc_001`
  carrying a payload with `event_id = 'sq_evt_forged_001'` and a
  tampered base64 signature in the
  `x-square-hmacsha256-signature` header.
- `SquareWebhookSignatureVerifier.verify` returns
  `valid: false, failureReason: 'HMAC-SHA256 mismatch'`.
- `InboundWebhookHandler` returns
  `WebhookOutcome.signatureInvalid` (HTTP 403). `connector_sync_log`
  records the rejected attempt; on the third such attempt the
  `inbound_webhook_dead_letter` row is written.
- No canonical fact is written. Sales card stays at the prior live
  number.

### 5. Malformed payload → 200 (drop), no canonical write

- Send a webhook whose body is `{"garbage": true}` (no `data.id`,
  no `data.object.order`). The signature is valid (HMAC over the
  garbage body matches).
- Adapter `_orderFromWebhookPayload` returns null;
  `_hydrateThinPayload` returns null (no `data.id`).
- `handleWebhook` returns `HandleWebhookResult(recordsWritten: 0)`.
  Framework logs to `connector_sync_log`. No canonical fact.

### 6. Future-dated event → sanity drop

- Send a webhook whose `data.object.order.created_at` is
  `2026-05-04T18:00:00Z` — six hours after the operator's clock.
- `InboundWebhookHandler` runs sanity guard step 4 (rule 2,
  `opened_in_future`) → drops the event with `WebhookOutcome.sanityDropped`
  (HTTP 200). `sanity_log` row written. No canonical fact.

### 7. Disconnect — sales card flips to `MetricCardNotYetAvailable`

- Settings → Vendor connections → Square card → **Disconnect**.
- `SquarePosAdapter.disconnect` calls `unregisterWebhook` +
  `revokeOauth` (best-effort; 404 tolerated). Returns
  `DisconnectResult(credentialsWiped: true, webhookUnregistered:
  true, watermarkPreserved: true)`.
- Tab to Shift dashboard. Sales card now renders
  `MetricCardNotYetAvailable` — no live POS source.
  - **Widget under test:** `MetricCardNotYetAvailable(metricLabel:
    'Sales')`.
  - **Expected MetricState:** `unavailable`. Provenance `none`.
- Covers card likewise renders the forecast number (forecast is
  always available even without a POS connected, but the pill text
  changes from "Covers: forecast (Square does not expose guest
  count)" to "POS: not yet connected").

### 8. Reconnect — watermark preserved, no rewind

- Settings → Vendor connections → Choose your POS → Square →
  **Continue (sandbox)** again. OAuth round trip stubs through the
  fixture.
- `SquarePosAdapter.connect` callback path runs again. New
  `connection_id` issued; the previous (`operator_id`, `location_id`)
  pair's watermark row is still present in
  `connector_sync_watermark` so the next `pollIncremental` starts at
  the prior `lastModifiedSeen` instead of rewinding 60 days.
  - **Named value asserted by test 6:** `watermarkStore.persists.last.lastModifiedSeen == highWaterPostBackfill`.

## Anchor-scenario evidence map

The walkthrough covers every anchor scenario the Phase 8 plan names:

- **Forged signature** → step 4 (HMAC mismatch → 403 + audit + no
  write).
- **Malformed payload** → step 5 (drop at adapter boundary; no
  `parse_warnings` per V1 lean cut 2).
- **Future-dated event** → step 6 (sanity rule 2 drop).
- **OAuth near-expiry** → indirectly via step 2's `30-day` access
  token TTL; explicit refresh-cron exercise lands in
  `8.SQ.live.sandbox`.
- **Disconnect → reconnect with watermark preserved** → steps 7-8.
- **Covers fallback** → step 3 (one top-left pill, forecast number
  in card, `covers_source = forecast_fallback`).
