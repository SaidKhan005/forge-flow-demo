## 4. Schema and RLS overview

### Table shape

```sql
public.leaderboard_scores (
  score_event_id uuid PK default gen_random_uuid(),
  operator_id    uuid NOT NULL,
  location_id    uuid NOT NULL,
  user_id        uuid NOT NULL    references public.users(user_id) on delete cascade,
  score_event_type text NOT NULL  check (1..64 chars, btrim'd),
  points         integer NOT NULL check (between -100000 and 100000),
  occurred_at    timestamptz NOT NULL,
  business_date  date NOT NULL    check (>= 2000-01-01),
  payload        jsonb NOT NULL default '{}'::jsonb,
  created_at     timestamptz NOT NULL default now(),
  -- RLS-Ready scaffolding: composite FK rejects rows attributed to a
  -- location that doesn't belong to the operator
  constraint leaderboard_scores_operator_location_fk
    foreign key (operator_id, location_id)
    references public.locations(operator_id, location_id)
    on delete cascade
);
```

### Operator-leading B-tree indexes (all leading with `operator_id`)

| Index | Lead | Use |
|-------|------|-----|
| `leaderboard_scores_operator_user_date_idx` | `(operator_id, user_id, business_date desc)` | per-user totals, weekly / monthly / all-time projection for one user |
| `leaderboard_scores_operator_location_date_idx` | `(operator_id, location_id, business_date desc)` | per-location split (multi-location operators) |
| `leaderboard_scores_operator_recent_idx` | `(operator_id, occurred_at desc)` | recent activity feed, dashboard widgets |

CI lint (`tool/rls_policy_lint.dart` index-posture sweep) enforces
that every B-tree index leads with `operator_id`.

### RLS posture (wrapper-only per 9.0Σ.b)

```sql
alter table public.leaderboard_scores enable row level security;

create policy "leaderboard_scores_per_tenant_select"
  on public.leaderboard_scores for select to service_role
  using (operator_id = public.app_current_operator());

create policy "leaderboard_scores_per_tenant_insert"
  on public.leaderboard_scores for insert to service_role
  with check (
    operator_id = public.app_current_operator()
    and location_id = public.app_current_location()
    and user_id in (
      select user_id from public.users
      where operator_id = public.app_current_operator()
    )
  );
```

No bare `current_setting('app.<name>', true)::uuid` reads;
`tool/rls_policy_lint.dart` rejects them. SELECT folds against the
operator-leading index because the wrapper is
`STABLE LEAKPROOF PARALLEL SAFE`. INSERT WITH CHECK pins three
axes:

- `operator_id = app_current_operator()` — the row's operator must
  match the SET LOCAL'd operator.
- `location_id = app_current_location()` — the row's location must
  match the SET LOCAL'd location, AND the composite FK on
  `(operator_id, location_id) → locations(operator_id,
  location_id)` rejects rows whose location does not belong to that
  operator at all.
- `user_id IN (SELECT user_id FROM public.users WHERE operator_id =
  app_current_operator())` — the scored user must belong to the
  same operator. Without this subquery the FK on
  `users(user_id)` alone would admit a cross-operator user UUID;
  the subquery folds against the indexed
  `users.operator_id` column. Pattern matches
  `role_permissions_per_tenant_modify` and
  `role_audit_log_per_tenant_select` in
  `202605020500_hardening_auth_rls_to_wrappers.sql`.

### Append-only grants

```sql
revoke all on public.leaderboard_scores from public;
grant  select, insert on public.leaderboard_scores to service_role;
grant  select, insert on public.leaderboard_scores to forge_admin;
revoke update, delete on public.leaderboard_scores from service_role;
revoke update, delete on public.leaderboard_scores from forge_admin;
```

Two-axis enforcement (no UPDATE/DELETE policy AND no UPDATE/DELETE
grants) keeps the table append-only. Corrections (e.g. revoked
Recognition badge from Phase 9.75) land as a fresh row with negative
points.

## 5. Tenant-isolation evidence (manual sanity path)

Because this slice ships no UX, the manual path verifies the schema +
RLS posture against a local Postgres after applying the migration.
The path uses **separate transactions** for each defense — the
allowed insert COMMITS first so the cross-tenant read step has a
real, durable row to fail to see.

```sql
-- 1. Apply the migration catalog through the new file:
--    \i db/migrations/202604250005_advisor_cloud_foundation.sql
--    ... (in order) ...
--    \i db/migrations/202605030000_phase_9_5_0_leaderboard_schema_rls.sql

-- 2. Seed a minimal two-operator fixture (operator A + operator B
--    each with one location and one user). Schema lives in
--    202604250005_advisor_cloud_foundation.sql.
insert into public.operators (operator_id, business_name, owner_email)
values
  ('11111111-1111-1111-1111-111111111111','OperatorA','a@example.test'),
  ('22222222-2222-2222-2222-222222222222','OperatorB','b@example.test');

insert into public.locations (operator_id, location_id, name, timezone)
values
  ('11111111-1111-1111-1111-111111111111',
   '33333333-3333-3333-3333-333333333333','LocA','America/Toronto'),
  ('22222222-2222-2222-2222-222222222222',
   '44444444-4444-4444-4444-444444444444','LocB','America/Toronto');

insert into public.users (user_id, operator_id, email)
values
  ('55555555-5555-5555-5555-555555555555',
   '11111111-1111-1111-1111-111111111111','user-a@example.test'),
  ('66666666-6666-6666-6666-666666666666',
   '22222222-2222-2222-2222-222222222222','user-b@example.test');

-- 3. Allowed insert under tenant A's context — COMMIT so the row
--    is durable for steps 5/6. The repository would do this via
--    withTenant; the manual SQL mirrors what `set_config(..., true)`
--    does so the policy WITH CHECK admits the row.
begin;
select set_config('app.operator_id',
  '11111111-1111-1111-1111-111111111111', true);
select set_config('app.location_id',
  '33333333-3333-3333-3333-333333333333', true);
select set_config('app.user_id',
  '55555555-5555-5555-5555-555555555555', true);
select set_config('app.bypass_rls_audit', 'tenant', true);

set local role service_role;

insert into public.leaderboard_scores
  (operator_id, location_id, user_id, score_event_type, points,
   occurred_at, business_date, payload)
values
  ('11111111-1111-1111-1111-111111111111',
   '33333333-3333-3333-3333-333333333333',
   '55555555-5555-5555-5555-555555555555',
   'mastery_complete', 25,
   '2026-05-03T12:30:00Z'::timestamptz,
   '2026-05-03'::date,
   '{"topic":"service_recovery"}'::jsonb)
returning score_event_id;
-- expected: returns one new uuid
commit;

-- 4. Cross-tenant write attempt under tenant A's context — try to
--    attribute the row to operator B. WITH CHECK rejects on the
--    operator/location predicate. Separate transaction so the
--    rollback below does not roll back step 3.
begin;
select set_config('app.operator_id',
  '11111111-1111-1111-1111-111111111111', true);
select set_config('app.location_id',
  '33333333-3333-3333-3333-333333333333', true);
select set_config('app.user_id',
  '55555555-5555-5555-5555-555555555555', true);
set local role service_role;

insert into public.leaderboard_scores
  (operator_id, location_id, user_id, score_event_type, points,
   occurred_at, business_date)
values
  ('22222222-2222-2222-2222-222222222222',
   '44444444-4444-4444-4444-444444444444',
   '66666666-6666-6666-6666-666666666666',
   'mastery_complete', 25,
   '2026-05-03T12:30:00Z'::timestamptz,
   '2026-05-03'::date);
-- expected: ERROR: new row violates row-level security policy
--   "leaderboard_scores_per_tenant_insert"
rollback;

-- 4b. User-tenant ownership attempt — under tenant A's context, try
--     to attribute a score to operator B's user (user_id belongs to
--     operator B). The new user-tenant subquery in WITH CHECK
--     rejects this even though the operator/location pair is A's.
begin;
select set_config('app.operator_id',
  '11111111-1111-1111-1111-111111111111', true);
select set_config('app.location_id',
  '33333333-3333-3333-3333-333333333333', true);
select set_config('app.user_id',
  '55555555-5555-5555-5555-555555555555', true);
set local role service_role;

insert into public.leaderboard_scores
  (operator_id, location_id, user_id, score_event_type, points,
   occurred_at, business_date)
values
  ('11111111-1111-1111-1111-111111111111',
   '33333333-3333-3333-3333-333333333333',
   '66666666-6666-6666-6666-666666666666',  -- operator B's user
   'mastery_complete', 25,
   '2026-05-03T12:30:00Z'::timestamptz,
   '2026-05-03'::date);
-- expected: ERROR: new row violates row-level security policy
--   "leaderboard_scores_per_tenant_insert"
rollback;

-- 5. Cross-tenant read — switch GUC to operator B's id, read the
--    table. The COMMITTED row from step 3 is still in the table, but
--    RLS hides it from operator B's SELECT.
begin;
select set_config('app.operator_id',
  '22222222-2222-2222-2222-222222222222', true);
select set_config('app.location_id',
  '44444444-4444-4444-4444-444444444444', true);
set local role service_role;

select count(*) from public.leaderboard_scores;
-- expected: 0  (operator A's committed row is hidden by RLS)

reset role;
rollback;

-- 5b. Same-tenant read sanity — switch back to operator A and verify
--     the COMMITTED row IS visible. Without this control step,
--     "0 visible from B" is ambiguous (the row could simply not
--     exist); confirming "1 visible from A" plus "0 visible from B"
--     is the actual cross-tenant denial proof.
begin;
select set_config('app.operator_id',
  '11111111-1111-1111-1111-111111111111', true);
select set_config('app.location_id',
  '33333333-3333-3333-3333-333333333333', true);
set local role service_role;

select count(*) from public.leaderboard_scores;
-- expected: 1  (operator A's committed row, still durable from step 3)

reset role;
rollback;

-- 6. EXPLAIN with operator A's GUC set — verify the planner folds
--    the per-tenant policy into the operator-leading index.
begin;
select set_config('app.operator_id',
  '11111111-1111-1111-1111-111111111111', true);
select set_config('app.location_id',
  '33333333-3333-3333-3333-333333333333', true);
set local role service_role;
set local enable_seqscan = off;

explain (format json)
select 1 from public.leaderboard_scores
where operator_id = '11111111-1111-1111-1111-111111111111'
  and user_id      = '55555555-5555-5555-5555-555555555555'
limit 1;
-- expected: Index Scan using leaderboard_scores_operator_user_date_idx
--   (or Bitmap Index Scan citing the same index name)

reset role;
commit;

-- 7. Cleanup — operator A's row from step 3 is durable. Drop the
--    fixture in reverse-FK order before re-running the walkthrough.
delete from public.leaderboard_scores
  where operator_id = '11111111-1111-1111-1111-111111111111';
delete from public.users
  where operator_id in (
    '11111111-1111-1111-1111-111111111111',
    '22222222-2222-2222-2222-222222222222'
  );
delete from public.locations
  where operator_id in (
    '11111111-1111-1111-1111-111111111111',
    '22222222-2222-2222-2222-222222222222'
  );
delete from public.operators
  where operator_id in (
    '11111111-1111-1111-1111-111111111111',
    '22222222-2222-2222-2222-222222222222'
  );
```

## 6. Tests run (verification)

- `dart analyze` — clean (`No issues found!`).
- `flutter test test/infrastructure/persistence/postgres/repositories/leaderboard_score_repository_test.dart`
  — unit-test sweep:
  - **insert under tenant context succeeds** — SET LOCAL canonical
    ordering (`operator_id` → `location_id` → `user_id` → tenant
    audit marker), INSERT runs after, returns server-generated
    `score_event_id`, transaction commits.
  - **parameter binding** — every untrusted axis (operator,
    location, user, score_event_type, points, occurred_at,
    business_date, payload) flows through `@`-bindings; never
    interpolated.
  - **occurredAt UTC normalization** — local-time DateTime is
    `.toUtc()`'d before binding so the timestamptz column receives a
    stable instant.
  - **businessDate local-day preservation** — `business_date` is
    formatted from `.year`/`.month`/`.day` verbatim with NO UTC
    conversion. A 23:30 local-time DateTime on May 3 still binds as
    `'2026-05-03'` regardless of the host timezone — without this
    the score would silently bin under the next day's bucket near
    midnight.
  - **TenantContext UUID validation** — malformed `operator_id`
    short-circuits BEFORE opening a transaction; no SET LOCAL
    round-trip, `pool.transactions` stays empty.
  - **insert returning no rows** — surfaces a `StateError` naming
    RLS; the transaction rolls back so the SET LOCAL session state
    cannot leak across the pool boundary.
  - **cross-tenant denial via SET LOCAL ordering** — SET LOCAL
    block runs BEFORE the SELECT; `app.bypass_rls_audit = 'tenant'`
    stamped (not 'system'); `set local role forge_admin` is NEVER
    emitted.
  - **EXPLAIN plan condition (operator-leading index)** — SELECT
    WHERE leads with `operator_id = @operator_id::uuid` so the
    planner folds the per-tenant policy into
    `leaderboard_scores_operator_user_date_idx`. Optional
    `[from/to]BusinessDate` appends without displacing operator_id
    from the lead.
  - **ORDER BY** — `business_date desc, occurred_at desc` matches
    the index sort posture so the planner satisfies the ORDER BY by
    index walk rather than a sort step.
  - **INSERT column ordering** — `operator_id`, `location_id` are
    the first two columns in the INSERT (RLS-Ready axes lead).
  - **row projection** — payload arriving as JSON string OR
    already-decoded Map both round-trip; malformed row surfaces a
    `StateError` so a producer that bypasses the repository INSERT
    shape fails fast at the read.
- `dart run tool/migration_drift_scanner.dart --fix --strict-docs`
  — clean (the new file's timestamp is BEFORE the current cutoff so
  the scanner's "newer than cutoff" check is empty; the report is

- `dart run tool/migration_cutoff_lint.dart` — clean (no

## 7. Boundary checks (out of scope)

- **No app logic changes.** No service-layer caller is wired in this
  slice. The `9.5a` user-scoped learning persistence prompt and the
  `9.5b` shared leaderboard read service are the consumers; they
  ship their own slices and will plumb this repository into the
  proxy / runtime when they land. CLAUDE.md Hard Promise #3 ("No app
  logic changes before `7.58`") plus the 9.5 plan's deliberate
  split keep this slice schema-only.
- **No UX surfaces.** Per the 9.5 plan's `Frontend Exposure`
  section, the operator/staff-facing leaderboard surfaces (Barrio
  personal stats card, weekly / monthly / all-time tabs, rank
  badges, tie-breaker disclosure) are owned by the `9.5.UX` slice.
  This walkthrough is therefore backend-only — the
  `docs/_walkthroughs/README.md` "demo-mode entry steps" requirement
  is satisfied by the `psql` walk in section 5 against a local
  Postgres, not a Flutter click path.
- **No projection / ranking logic.** The repository ships
  `recordScore` and `listScoresForUser` only. Top-N for a window,
  current rank for one user, tie-breakers, and time-window semantics
  (weekly / monthly / all-time) are Phase 9.5.x deliverables.
- **No UPDATE / DELETE methods.** The grant shape forbids both at
  the DB layer; the repository does not expose them. Corrections
  (e.g. revoked Recognition badge from Phase 9.75) MUST land as a
  fresh row with negative points so the append-only audit story
  holds.
- **No `package:postgres` import outside
  `lib/infrastructure/persistence/postgres/`.** The new repository
  imports only the in-package `postgres_executor.dart` and
  `tenant_context.dart`; no consumer outside this directory binds to
  raw `package:postgres` symbols. The
  `tool/postgres_import_lint.dart` lint stays clean.
- **No retention policy.** Score-event retention windows by
  `score_event_type` are an Operations-El-Podio decision (the later
  phase that depends on real POS / labor attribution per the 9.5
  plan's "Later — Operations El Podio" section). Until that lands,
  the table grows append-only and is bounded only by the daily
  per-operator write rate.
- **No live apply.** This migration is NOT yet applied on staging or
  Production1. The 9.5 launch lane will apply it once 9.5.UX has
  shipped enough surface to justify a board-level migration apply
  window. Idempotent posture (`if not exists` on table + indexes;
  `drop policy if exists` before `create policy`) means re-running
  is safe.
