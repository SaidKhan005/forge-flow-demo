# 9.UX.6 - Settings Account Audit Log

Date: 2026-04-30

## Scope

Add a self-service Audit Log viewer to Settings -> Account. The
operator sees their own `auth_events_audit` rows (sign-ins, password
changes, MFA factor / recovery events, role grant changes, session
revokes, invites) with friendly labels, relative timestamps, and an
expandable detail row that surfaces IP / device / scope metadata when
the proxy captured them. Reads flow through
`AuthOperationsGateway.listAuthEventsForActor` -> proxy -> Postgres so
the Flutter client never queries the database directly and per-user
RLS gates cross-user reads server-side.

## Operator Walkthrough (`kDemoMode = true`)

1. Launch ForgeFlow in demo mode (`flutter run -t lib/main_forgeflow.dart`)
   and sign in as the demo operator
   (`demo.operator@forgeflow.test` / `forge-flow-demo`).
2. Open Settings -> Account.
3. Confirm the **Audit log** section header renders below the **Active
   sessions** card (text trace: `find.text('Audit log')` resolves and
   the `audit_log_row_demo-audit-1` widget key is present). Six demo
   rows render in newest-first order:
   - Sign-in (a few minutes ago, tagged with IPv4 + CA),
   - Password changed (3 hours ago),
   - MFA enrolled (1 day ago),
   - Role grant added (2 days ago, scope: location),
   - Session revoked (3 days ago),
   - Sign-in (4 days ago, iPad UA).
4. Tap the **Sign-ins** filter chip (`audit_log_filter_sign_in`).
   Verify only the two `auth.user.signed_in` rows render and tapping
   **All** (`audit_log_filter_all`) restores the full list.
5. Tap the date-range chip (`audit_log_date_range_picker`). The
   Material `showDateRangePicker` opens; pick a window that includes
   only the last 24 hours and tap **Save**. Verify rows older than
   the window disappear (e.g. the role-grant row 2 days ago and the
   sign-in row 4 days ago). Tap the close icon
   (`audit_log_date_range_clear`) to remove the bound and restore
   the full ledger.
6. Tap **Load more** at the bottom (`audit_log_load_more`) when more
   than `pageSize` rows are queued. Verify the next page appends
   without erasing prior rows; the previous offset's rows stay visible
   above the new ones.
7. Tap an audit row (e.g. `audit_log_row_demo-audit-1`) and verify the
   expand-detail panel reveals event_type, IP, country, and user-agent
   metadata (`audit_log_row_demo-audit-1_details`).
8. Tap **Sign Out** to log out, sign back in, and pull-to-refresh the
   Settings -> Account scroll. Verify a fresh `Sign-in` row lands at
   the top of the audit log without a duplicate render of the prior
   sign-in row.

## Contract Notes

- Reads route through `AuthOperationsGateway.listAuthEventsForActor`
  -> `GET /v1/auth/audit-log` (auth-gated; the proxy resolves
  `(operator_id, location_id, user_id)` from the verified Firebase
  bearer token before delegating to the gateway). The proxy ignores
  any client-supplied `user_id` query param; only the JWT-resolved
  scope reaches the gateway.
- Pagination is server-side via `LIMIT` + `OFFSET`; the proxy clamps
  the per-request limit to a 100-row ceiling and defaults to 50.
- Filtering routes through `?event_kind=<key>` query params; the
  proxy maps the key to a coarse SQL `LIKE` pattern set
  (`AuthEventLabels.sqlPatternsFor`) so the per-user RLS leading
  index stays effective.
- Date-range filtering travels as `?from=<iso8601>` / `?to=<iso8601>`
  query params; the proxy parses both into UTC `DateTime` and the
  repository binds `occurred_at >= @from` / `occurred_at <= @to`.
  The widget builds the start and end bounds as **local** day
  start / end (00:00:00.000 / 23:59:59.999) before converting to
  UTC, so the picked dates are inclusive in the operator's local
  timezone (e.g. America/St_Johns selecting Apr 30 captures rows
  through Apr 30 23:59 local, not 21:29 local).
- Defense in depth on cross-operator and cross-user reads:
  1. The repository query is the **primary** defense. It pins
     `operator_id = @operator_id::uuid` AND
     (`actor_user_id = @user_id::uuid` OR
     `target_user_id = @user_id::uuid`), so a future admin-pool or
     miswired tenant wrapper cannot broaden same-user reads across
     operators.
  2. `runInTenantContext` issues `SET LOCAL app.user_id = ...` and
     the per-tenant RLS `SELECT` policy on `auth_events_audit`
     filters cross-operator rows. The live policy is tenant-only
     (not per-user), so the `user_id` clause carries the per-user
     defense alone — the operator clause + RLS form a redundant
     belt-and-braces gate at the operator level.
- Writer paths are unchanged. Append-only audit inserts continue to
  flow through the existing admin-pool repository binding; only the
  read projection uses the tenant-pool binding so RLS engages on the
  read side. The audit table's `REVOKE UPDATE / DELETE` grant shape
  stays intact.
- Demo mode (`kDemoMode = true` or no live gateway): the section
  installs `DemoAuditLogGateway` (in-memory) seeded with six stable
  rows from `DemoAuditLogFixtures` so the walkthrough can exercise
  the filter / load-more / expand path without staging.

## Notes

- No new permission keys: the surface is self-service so the actor's
  verified Firebase bearer token alone authorizes the read.
- Cross-user isolation acceptance: the proxy ignores any
  client-supplied `user_id` query param; only the JWT-resolved scope
  reaches `listAuthEventsForActor`. Future surfaces that need to view
  another user's events belong on the admin audit path
  (`/v1/admin/auth/users/<id>/audit-log`) and are out of scope here.
- `AuthEventLabels.labelFor` is the single-source-of-truth mapping
  between raw `event_type` strings and human-readable labels. The
  proxy projects the label server-side; the Flutter client falls
  back to deriving it locally if the proxy ever omits it, so a
  brand-new event_type still reads naturally.
