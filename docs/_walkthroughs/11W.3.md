# 11W.3 Walkthrough — Locations (Org Hierarchy) surface

**Slice:** 11W.3 (Phase 11W — Operator Web Console; Self-Service Parity block)
**Mode:** demo (`OPERATOR_WEB_DEMO_AUTH=true`)
**Date:** 2026-05-06

This slice ships the web parity for the mobile Settings -> Org
Hierarchy section. The Operator Web Console gains a `Locations`
route at the side nav. Operator owners and admins can browse the
n-ary org-unit tree, move locations between org units, and create
new regions / districts / location groups from a desktop browser.
Floor managers (`location_manager`) and operator supervisors get a
read-only tree (mutate buttons hidden, expand / collapse stays
interactive). Operator staff hit a friendly forbidden surface.

The slice extends the shared `demo_team_fixtures.dart` with the
parent-of-parent corp root (`Demo Bistro`) so the tree walkthrough
has a corp -> region -> location depth to exercise. 11W.1 (Members)
keeps consuming the same fixture set without changes — the only
new additions to the fixture file are projection helpers
(`teamOrgUnitEntryFromFixture` + `teamOrgLocationEntryFromFixture`)
and the `unitType` + `path` fields on `DemoTeamOrgUnitFixture`.

**Wiring honesty (read this first):** `11W.3` ships the Locations
surface against the in-memory `DemoWebTeamHierarchyGateway`. The
live HTTP gateway (`WebTeamHierarchyGatewayLive`) is built in this
slice and pinned via the path constants in `WebTeamHierarchyPaths`,
but the live `FirebaseOperatorWebAuthSource` mixes the gateway in
via the `OperatorWebTeamHierarchyGatewayProvider` interface in the
`11W.3.live` follow-up — same gateway-follows-shell pattern Phase
11A.0 -> 11A.1 used. No new proxy routes were added; the live
gateway hits the existing Phase 9 + 11A.1 routes
`/v1/admin/auth/org-units` (GET + POST) and
`/v1/admin/auth/locations/{id}/org-unit` (PATCH).

**Scope clarification — suspend / edit location:** the slice scope
locks to the org-tree visualization plus the audited create + move
actions defined in the parity contract § Hierarchy. Per-location
suspend / edit / timezone / business-day-rollover-hour fields live
on Phase 11A.1's admin location screen (`lib/admin/screens/operator_location_admin_screen.dart`)
and the corresponding 11A path. Adding an operator self-service
location-edit surface would require a new `/v1/admin/auth/locations/{id}`
PATCH route (today only the `/org-unit` sub-path is shipped) plus
a parity-contract update; both are out of scope for 11W.3 per the
"No new backend routes" hard constraint and the
"hierarchy-touches-grants" gating posture in
`docs/phases/phase_9/phase_9_auth_plan.md`.

**Cross-console pair:** `11A.13` Hierarchy tab is the matched
sibling per the parity contract acceptance gate #7 ("the pair lands
together or both stay active"). This walkthrough covers the
operator-side surface only; the F&F admin surface lands in `11A.13`
against the same parity contract section. Both must reach
acceptance before either merges.

## What changed

### `lib/operator_web/services/demo_team_fixtures.dart`

- `DemoTeamOrgUnitFixture` gains `unitType` + `path` so the
  projection helpers can produce a `TeamOrgUnitEntry` with the same
  shape as the live proxy payload.
- A new `demo-org-root` corp entry sits above `demo-org-east` +
  `demo-org-west`. East and West now reference `demo-org-root` as
  their parent so the tree depth has a corp -> region -> location
  walk.
- New projection helpers `teamOrgUnitEntryFromFixture` /
  `teamOrgLocationEntryFromFixture` so the demo + live hierarchy
  gateways share one row contract.

### `lib/operator_web/services/web_team_hierarchy_gateway.dart` (new)

Narrow `WebTeamHierarchyGateway` interface (just the org-hierarchy
surface of `AuthOperationsGateway`) plus the live
`WebTeamHierarchyGatewayLive` impl built on `package:http`. Hits
the existing Phase 9 + 11A.1 routes:

- `GET   /v1/admin/auth/org-units`
- `POST  /v1/admin/auth/org-units`
- `PATCH /v1/admin/auth/locations/{location_id}/org-unit`

Every write accepts a caller-minted `Idempotency-Key` and threads
it through as the `Idempotency-Key` request header. The gateway
never mints keys internally so the proxy `proxy_requests`
UNIQUE-key replay surfaces the original write on retry. No
`dart:io`, no `sqflite`.

### `lib/operator_web/services/demo_team_hierarchy_gateway.dart` (new)

In-memory `DemoWebTeamHierarchyGateway` reading the shared fixture
file. Caches mutation responses by idempotency key so a
re-submission of the same action returns the original outcome
rather than mutating again — matching the parity contract
§ Idempotency keys posture. Mutations are session-local; reloading
the page resets the data. The demo gateway also enforces the
parity-contract validation rules (empty name, duplicate name within
parent) so the screen layer can surface the locked copy without a
server round-trip.

### `lib/operator_web/widgets/location_card.dart` (new)

Reusable summary card for one location (key
`operator_web_location_card_<locationId>`). Shows the location
label + the org-unit path + an optional Move trailing button when
the actor is allowed to mutate.

### `lib/operator_web/widgets/org_unit_tree_view.dart` (new)

Recursive tree widget. Renders one `_OrgUnitNode` per org unit,
sorted alphabetically by `label`, with locations under each node
sorted alphabetically by `label`. Read-only audiences keep the
expand / collapse toggle but see no `Add child` or `Move` buttons.
Empty input renders the friendly fallback notice (`No hierarchy
yet. Setup needs a root unit first.`).

### `lib/operator_web/screens/hierarchy_screen.dart` (new)

Operator Web Console Locations screen. The header subtitle stays
role-agnostic (describing what the screen IS, not what the actor
can do); the per-audience signal lives on the read-only notice +
the per-row mutate buttons so a single read-only message never
double-renders. The add-child dialog auto-generates the technical
`label` from the display name when the user leaves the label blank,
sanitising any non-alphanumeric run into a single underscore so the
auto-gen output always satisfies the proxy's `a-z, 0-9, underscore`
label format constraint (e.g. `"South-West Region"` lands as
`"south_west_region"`).

Renders:

- Header (`operator_web_hierarchy_screen` +
  `operator_web_hierarchy_subtitle`).
- Read-only notice (`operator_web_hierarchy_readonly_notice`) for
  audiences without `team.roles.assign`.
- Tree view (`operator_web_org_unit_tree`) wrapping the recursive
  `OrgUnitTreeView` widget.
- Add-child dialog (`operator_web_org_unit_add_dialog`) with
  unit type / display name / label fields and the locked
  validation copy.
- Move-location dialog (`operator_web_location_move_dialog`) with
  a sorted dropdown of available org units excluding the location's
  current parent.
- Friendly forbidden surface
  (`operator_web_hierarchy_forbidden`) for actors without
  `team.users.view`.

Permission gate:

- `operator_owner` / `operator_admin` see every action enabled.
- `operator_manager` / `operator_supervisor` / `location_manager`
  see the tree read-only (no Add child, no Move; expand / collapse
  still works).
- Other roles fall through to a friendly forbidden surface.
- Permission-key snapshot trumps the role-tier fallback in both
  directions.

### `lib/operator_web/router/operator_web_router.dart`

- New nav id `kOperatorWebNavLocations = 'locations'` between
  Members and Vendor connections.
- New `OperatorWebTeamHierarchyGatewayProvider` interface so the
  auth source can supply a live or demo gateway implementation.
- Router-owned lazy `DemoWebTeamHierarchyGateway` fallback so the
  demo flavor never crashes when the auth source forgets to mix in
  the provider.

### `lib/main_operator_web.dart`

- `_DemoOperatorWebAuthSourceWithMembers` now also implements
  `OperatorWebTeamHierarchyGatewayProvider` and binds the demo
  hierarchy gateway alongside the demo team-users gateway, so a
  single demo session walks `/members` -> `/locations` against one
  shared fixture set.

## Click path (numbered steps)

### Step 1 — Open `app.forgeflow.app` (demo flavor)

Browser viewport 1280×900. The demo build lands the operator on
the welcome screen.

**User action:** open `app.forgeflow.app` in a browser tab.

**Expected:**

- `Key('operator_web_welcome_token_field')` visible.

### Step 2 — Sign in via the demo magic link

**User action:** type `demo-magic-link-token` into the welcome
screen's token field, set the demo password (≥ 12 characters),
enrol demo MFA (`123456`), accept the demo T&Cs.

**Expected:**

- `Key('operator_web_shell_scaffold')` renders.
- Side nav exposes Account, Members, Locations, Vendor connections,
  Data accuracy.
- Default landing is `/account`.

### Step 3 — Click Locations in the side nav

**User action:** click `Key('operator_web_nav_item_locations')`.

**Expected:**

- Body swaps to `Key('operator_web_hierarchy_screen')`.
- Tree (`Key('operator_web_org_unit_tree')`) renders the corp root
  `Demo Bistro`, with East Region (alphabetically first) before
  West Region. East Region holds `Downtown` then `North Loop`; West
  Region holds `Riverside`.

### Step 4 — Move Riverside under East Region

**User action:** click
`Key('operator_web_location_card_move_demo-loc-riverside')`. The
move dialog (`Key('operator_web_location_move_dialog')`) opens.
Pick `East Region (demo_bistro.east_region)` from the dropdown
(`Key('operator_web_location_move_dialog_target')`). Click
`Key('operator_web_location_move_dialog_submit')`.

**Expected:**

- Dialog closes.
- Snackbar `Location moved.` flashes at the bottom.
- `Riverside` now renders under East Region (alphabetically after
  `North Loop`); West Region is empty.

### Step 5 — Add a new region under the corp root

**User action:** click
`Key('operator_web_org_unit_add_child_demo-org-root')`. The
add-child dialog (`Key('operator_web_org_unit_add_dialog')`)
opens. Pick `Region` from the unit type dropdown. Type
`Lakeshore Region` into the display-name field. Click
`Key('operator_web_org_unit_add_dialog_submit')`.

**Expected:**

- Dialog closes.
- Snackbar `Org unit added.` flashes.
- Tree gains a `Lakeshore Region` node alongside East + West.

### Step 6 — Validate the locked add-child copy

**User action:** open the add-child dialog under any node again.
Click submit with the form empty.

**Expected:**

- `Org unit name is required.`
  (`Key('operator_web_org_unit_add_dialog_error')`).

Type `East Region` (the duplicate of an existing sibling under the
corp root) when the parent is `Demo Bistro` and submit.

**Expected:**

- `An org unit with this name already exists in this group.`
  (same key).

Cancel via `Key('operator_web_org_unit_add_dialog_cancel')` to
close the dialog.

### Step 7 — Permission gate negative path

**User action:** sign out of the demo owner, then re-enter using
`DemoOperatorWebAuthSource.completedAsLocationManager()`.

**Expected:**

- Locations screen renders read-only.
- `Key('operator_web_hierarchy_readonly_notice')` visible.
- No node exposes
  `Key('operator_web_org_unit_add_child_*')`.
- No location card exposes
  `Key('operator_web_location_card_move_*')`.
- The `Key('operator_web_org_unit_toggle_*')` toggles still work
  (read-only audience keeps interactivity).

A `staff` role lands on the friendly forbidden surface
(`Key('operator_web_hierarchy_forbidden')`) explaining who
manages locations.

### Step 8 — Sign out

**User action:** click `Key('operator_web_header_signout')`.

**Expected:**

- Auth source emits `OperatorWebSignedOut`. Welcome screen
  re-renders.

## Permission gating evidence

The Phase 9 + 11A.1 proxy routes already enforce role + permission
gates server-side. The client-side gate in
`kOperatorWebHierarchyAdmittedRoles` +
`kOperatorWebHierarchyWriteRoles` is the friendly-error layer per
the UX writing standard.

| Role                  | Tree | Add child | Move location |
| --------------------- | ---- | --------- | ------------- |
| `operator_owner`      | yes  | yes       | yes           |
| `operator_admin`      | yes  | yes       | yes           |
| `operator_manager`    | read | no        | no            |
| `operator_supervisor` | read | no        | no            |
| `location_manager`    | read | no        | no            |
| `operator_staff`      | forbidden | n/a  | n/a           |

When the live `OperatorWebSession.permissions` snapshot is hydrated
by the proxy, the gate consults `team.users.view` for the read
surface and `team.roles.assign` for the create + move actions. The
role-tier fallback above applies only when the snapshot has not
been hydrated yet (demo flavor + live bootstrap stage).
