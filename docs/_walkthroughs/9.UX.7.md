# 9.UX.7 - Self-Service Password Reset

Date: 2026-04-30

## Scope

Operator UX layer for the self-serve password reset flow plus the
proxy + Firebase action-page wiring needed for the in-app confirm
path to be reachable from a real emailed link. Adds:

- a "Forgot password?" link on the login screen,
- a branded request screen that posts to the proxy
  `POST /v1/auth/password/reset/request` route,
- a deep-link target screen that posts to
  `POST /v1/auth/password/reset/confirm`,
- the proxy `/request` route + `RepositoryPasswordResetRequestGateway`
  (privacy-preserving by latency floor as well as response body),
- Idempotency-Key dedupe on both reset routes via
  `ProxyAuthIdempotencyCache` so retries do not double-send the
  reset email or burn an oobCode on a confirm replay,
- a Firebase action-page handoff that redirects mobile clients to
  `forgeflow://reset-password?oobCode=...` so the in-app confirm
  screen handles the email-link tap (the web form remains as a
  fallback for browsers without the app installed).

The HIBP screening, last-5 password history, and Firebase Identity
Toolkit issuance still live behind the same gateways B48 landed —
this slice extends them with the request route, the timing-oracle
fix, and the idempotency cache.

## Operator Walkthrough (`kDemoMode = true`)

1. Launch ForgeFlow in demo mode (`flutter run -t lib/main_forgeflow.dart`).
   On the login screen, locate the **Forgot password?** link
   (`login_forgot_password_link`) below the password field.
2. Tap **Forgot password?**. Verify the
   `PasswordResetRequestScreen` opens with the heading "Reset your
   password" and the email field
   (`password_reset_request_email_field`) is empty (or pre-filled
   with the email typed on the login screen).
3. Enter `not-an-email` and tap **Send reset link**
   (`password_reset_request_submit_button`). Verify the client-side
   error banner (`password_reset_request_error_banner`) renders the
   copy "Enter a valid email address." and the request is **not**
   sent.
4. Clear the field, enter `demo.operator@forgeflow.test`, and tap
   **Send reset link**. Verify the privacy-preserving banner
   (`password_reset_request_confirmation_banner`) renders the copy
   "If an account exists for this email, you'll receive a reset
   link." regardless of whether the email belongs to a real account.
5. Repeat with `unknown.user@example.test`. Verify the same
   confirmation banner copy renders — the screen never branches on
   whether the email exists.
6. To exercise the deep-link target in demo mode, simulate the
   Firebase action page redirect by sending
   `forgeflow://reset-password?oobCode=demo-oob` to the app — on
   Android this fires through the AndroidManifest intent-filter; in
   the demo harness, an `InMemoryPasswordResetDeepLinkSource` emits
   the URI directly. The `PasswordResetDeepLinkHandler` parses the
   `oobCode` and pushes `PasswordResetConfirmScreen` onto the
   navigator. Verify the heading "Choose a new password" renders
   with helper copy mentioning the 8-character minimum
   (`PasswordPolicy.minLength`).
7. Enter `short` in both password fields and tap **Update password**
   (`password_reset_confirm_submit_button`). Verify the validation
   banner (`password_reset_confirm_validation_banner`) renders
   "Password must be at least 8 characters." without invoking the
   gateway.
8. Enter `fresh-pw` in the new password field and a different value
   in the confirm field. Verify the banner renders "Passwords do
   not match." without invoking the gateway.
9. Enter `fresh-pw` in both fields and tap **Update password**.
   Verify (a) the redirect callback fires, (b) the success snackbar
   (`password_reset_success_snackbar`) reads "Password updated.
   Please sign in.", and (c) the operator lands back on the login
   screen — there is no auto-sign-in.
10. Repeat the deep-link with `oobCode: demo-oob` and a too-short
    password (e.g. `pw`). Verify the policy-violation banner
    (`password_reset_confirm_error_banner`) renders "Choose a
    password that meets the password policy." and the operator stays
    on the confirm screen.

## Contract Notes

- Request route: `POST /v1/auth/password/reset/request` with body
  `{ "email": "<operator@host>" }`. The client treats both 200 and
  202 as success; 429 surfaces "Too many reset requests. Please
  wait a moment and try again."; other non-success statuses surface
  "Password reset is temporarily unavailable. Please try again." The
  client never branches on the response when the email is unknown —
  the screen always shows the same privacy-preserving banner.
- Confirm route: `POST /v1/auth/password/reset/confirm` with body
  `{ "oob_code": "...", "new_password": "..." }`. 200 yields a
  redirect + success snackbar. 422 is parsed for the rejection
  array; the screen surfaces specific copy for `pwned_in_breach`,
  `reused_from_history`, and `violates_policy`. 403/404 + the
  `password_reset_expired` / `_user_not_found` / `_scope_mismatch`
  codes surface "This reset link is no longer valid. Request a
  fresh link from the sign-in screen."
- Privacy posture: `RepositoryPasswordResetRequestGateway` always
  calls Firebase `sendPasswordResetEmail` for clean lookup results
  (whether matched or null), swallows `EMAIL_NOT_FOUND`, and pads
  to a 350ms latency floor in a `finally` block. Closes both the
  response-body and wall-clock latency oracles for the matched-vs-
  unknown case. The audit row only fires for matched emails
  (auditing unknown emails would just move the presence oracle
  into the audit log). Lookup *errors* (transient Postgres blips)
  intentionally **propagate** so the route returns 503 — sending a
  reset email without the corresponding audit row would be a worse
  outcome than surfacing a service-level "try again" signal.
- Idempotency: both reset routes require the `Idempotency-Key`
  header; missing keys return 400. The proxy holds an in-memory
  `ProxyAuthIdempotencyCache` (1-hour TTL by default, bounded at
  `maxEntries = 10000` with LRU eviction) keyed by `(route, key)`.
  **Cache policy: 2xx + terminal 4xx are cached; 5xx and 429 are
  NOT** — so a transient lookup blip doesn't lock the same key to
  a permanent 503, and a rate-limited operator who waits the
  rate-limit window can retry the same request without being
  pinned to a stale 429 for the full TTL. A retry with the same
  key after a 2xx replays the cached response (no second Firebase
  email, no burned oobCode); a retry after a 5xx or 429 hits a
  fresh gateway invocation and can recover when infrastructure
  is healthy or the rate-limit window passes. Concurrent retries
  with the same key collapse onto the in-flight future rather
  than racing. The bounded store + LRU eviction prevent the
  unauthenticated reset routes from being a memory-DoS vector
  when an attacker spams unique keys: an overflow degrades to a
  missed-dedupe penalty for the evicted client, never an OOM.
- Idempotency-Key lifecycle (client side): both reset screens own a
  stable key per logical attempt. The key is generated when the
  operator first taps Submit and is **reused** across same-input
  retries. The key **rotates** when the operator changes input
  (a new email on the request screen, or a new password on the
  confirm screen after a HIBP/policy rejection) or when the proxy
  returns a transient 429 — rate-limited responses are inherently
  "wait, then retry the same request", so pinning the key would
  defeat that semantic. Terminal 4xx rejections (other than 429)
  retire the key on the confirm screen so the next password
  attempt is a clean submit; transient 5xx / network failures
  keep the key pinned so the proxy can replay or recover. The
  Firebase action page web fallback follows the same rule — it
  generates a key on the first submit and rotates it only when
  the password changes.
- Email-link flow: the Firebase action page at `web/auth/action/`
  detects mobile user agents (Android/iOS) and redirects to
  `forgeflow://reset-password?mode=resetPassword&oobCode=...` once
  per session. The `PasswordResetDeepLinkHandler` parses the URI
  and pushes `PasswordResetConfirmScreen`. If the deep link does
  not resolve within ~1.2s (app not installed) the page falls back
  to the in-browser form, which posts to `/v1/auth/password/reset/confirm`
  with a self-managed `Idempotency-Key` header so desktop /
  app-not-installed users complete the reset without hitting the
  required-header 400.
- `kDemoMode` substitutes `DemoPasswordResetGateway` so the
  walkthrough runs without a live proxy. The demo gateway accepts
  any well-formed email and rejects candidate passwords shorter
  than `PasswordPolicy.minLength` (8) with a `password_policy_failed`
  rejection so the operator can see both the success and rejection
  paths.

## Files

- `lib/services/auth/password_reset_gateway.dart` (new) — abstraction
  with `requestReset` / `confirmReset`, `PasswordResetRejected`
  exception, `ScaffoldFailingPasswordResetGateway` (default,
  fail-closed), and `DemoPasswordResetGateway` (kDemoMode). The
  demo gateway and the confirm screen both default to
  `PasswordPolicy.minLength` (8) so client-side validation does
  not pre-reject candidates the server would accept.
- `lib/services/auth/proxy_password_reset_gateway.dart` (new) —
  proxy client; both routes are unauthenticated and idempotent.
- `lib/services/auth/password_reset_request_gateway.dart` (new,
  server-side) — proxy gateway that always calls
  `FirebaseAdminAuthClient.sendPasswordResetEmail` regardless of
  whether the local lookup matched, swallows `EMAIL_NOT_FOUND`,
  and pads to a 350ms latency floor (closes the timing oracle).
  The audit row fires only for known users; unknown-email lookups
  return success silently (no audit row leak). Exposes a
  `fromDependencies` constructor so unit tests can inject typedef
  fakes without standing up Postgres.
- `tool/advisor_proxy/proxy_idempotency_cache.dart` (new) —
  in-memory `ProxyAuthIdempotencyCache` keyed by `(route, key)`
  with TTL, concurrent-request collapsing, an LRU-bounded store
  (`maxEntries = 10000` default), and a 429/5xx-skip cache
  policy. Used by both reset routes to dedupe retries.
- `web/auth/action/index.html` — mobile clients are redirected to
  `forgeflow://reset-password?mode=resetPassword&oobCode=...` once
  per session before the in-browser form is shown; the form
  remains as a fallback if the deep link does not resolve within
  ~1.2s.
- `lib/services/auth/password_reset_deep_link_source.dart` (new) —
  abstraction over the platform-side incoming-URI stream;
  `WidgetsBindingPasswordResetDeepLinkSource` reads through Flutter's
  built-in navigation channel; `InMemoryPasswordResetDeepLinkSource`
  is the test seam.
- `lib/screens/auth/password_reset_deep_link_handler.dart` (new) —
  widget that listens to the source and pushes
  `PasswordResetConfirmScreen` when the URI matches the
  `forgeflow://reset-password?oobCode=...` contract.
- `lib/screens/auth/password_reset_request_screen.dart` (new) —
  branded card with privacy-preserving confirmation copy.
- `lib/screens/auth/password_reset_confirm_screen.dart` (new) —
  branded card with policy-violation copy + redirect snackbar on
  success.
- `lib/screens/auth/login_screen.dart` (additive carve-out) —
  "Forgot password?" link below the password field; navigation
  handler that pushes the request screen with the configured
  gateway.
- `lib/screens/auth/auth_gate.dart` (additive carve-out) —
  forwards `passwordResetGateway` into the unauthenticated
  `LoginScreen` and wraps it with `PasswordResetDeepLinkHandler`
  when both the gateway and the deep-link source are bound.
- `lib/forge_flow_app.dart`, `lib/barrio_app.dart`,
  `lib/services/auth/firebase_auth_runtime_bindings.dart`,
  `lib/main_forgeflow.dart`, `lib/main_barrio.dart` — bootstrap
  threads `passwordResetGateway` and `passwordResetDeepLinkSource`
  through to `AuthGate` so production builds reach the live proxy
  routes.
- `tool/advisor_proxy/advisor_proxy.dart`,
  `tool/advisor_proxy/proxy_bootstrap.dart`,
  `tool/advisor_proxy/main.dart` — proxy gains
  `POST /v1/auth/password/reset/request`, both reset routes wrap in
  `ProxyAuthIdempotencyCache`, and the production binding injects
  `RepositoryPasswordResetRequestGateway`.
- `android/app/src/main/AndroidManifest.xml` — adds the
  `forgeflow://reset-password` intent-filter so the OS hands the
  reset deep-link back to the app.

## Notes

- No new permission keys; the request and confirm routes are
  unauthenticated by contract (the request is the public
  "send me a link" surface; the confirm is reached from the
  email-link before the operator has signed back in).
- The existing inline "Email me a reset link" button on the login
  screen stays in place; this slice is purely additive. Production
  bootstrap can later remove the inline path once the new
  Forgot-password flow is the canonical entry point.
- Backend deploy of `/v1/auth/password/reset/request` is owned by
  B48; this UX surface is ready to consume the route as soon as
  the proxy lands it. In the meantime, the scaffold-failing default
  gateway surfaces a clear error rather than silently succeeding.
