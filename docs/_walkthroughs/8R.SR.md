# 8R.SR Walkthrough — SevenRooms reservation adapter (documented)

**Slice:** 8R.SR (Phase 8R — Reservations Wave B adapter)
**Mode:** `kDemoMode = true` (operator app, deterministic seed)
**Date:** 2026-05-04
**Lifecycle at slice close:** `documented` (Connect button hidden
behind "Coming soon" pill until `8R.SR.live.sandbox` flips to
`sandbox_verified`)

This walkthrough exercises every adapter seam the engineering slice
ships against the documented SevenRooms partner API shape. Live HTTP
is the `8R.SR.live.sandbox` / `8R.SR.live.prod` slice's job; here
every network surface is fed by the test-double seams declared in
`lib/integrations/reservation/sevenrooms_reservation_adapter.dart`
(`SevenRoomsReservationGateway` / `SevenRoomsAuthClient` /
`SevenRoomsWebhookClient` / `SevenRoomsReservationsClient`).

The Hard Promise this slice realizes:

> Phase 8 = pure transport swap. Vendor connectors write existing
> SQLite tables only; cleanup is `7.57` / `7.58` / `7.61`.

The adapter writes the existing canonical reservation rows through
`OperatorScopedRepository.withTenant`. No business logic moves.

This is the first **manualPaste** webhook adapter in Wave B. Operator
flow differs from autoRegister vendors (Toast / Lightspeed): F&F
displays the webhook URL + signing-secret instructions for the
operator to paste into the SevenRooms admin portal manually, rather
than calling a vendor subscription endpoint.

## Click path

### Connect (manualPaste happy path, demo-mode flip)

1. Operator opens **Settings → Vendor Connections**. The Vendor
   Connections widget renders one card per documented vendor.
2. Operator scrolls to the **Reservations** section and taps the card
   with `Key('vendor_picker_sevenrooms')`, labelled **SevenRooms**.
   The card chrome reads "Coming soon" until `8R.SR.live.sandbox`
   promotes the lifecycle to `sandbox_verified`; for the engineering
   slice the demo-mode build includes a debug-only "Connect (demo)"
   button so the rest of the click-path is exercisable.
3. Operator taps **Connect (demo)**. The SevenRooms keypaste connect
   form opens with three fields: **Client ID**, **Client secret**,
   **Venue ID** (per `oauth_shape.md` — partner credential pack).
4. Operator pastes the demo credential triple:
   - `client_id`: `partner-client-abc`
   - `client_secret`: `partner-secret-xyz`
   - `venue_id`: `sr-venue-7c2f`
5. Operator taps **Connect**. The flow drives
   `SevenRoomsAuthClient.authenticate` (stubbed in demo mode); the
   stub returns:
   - `venue_id: sr-venue-7c2f`
   - `access_token_credential_id: cred-access-1`
6. The card flips to **Connected (webhook pending)**. The
   `connector_connection.metadata` reads
   `{venue_id: sr-venue-7c2f, webhook_state: pending_paste}`.
   `connector_sync_log` gains one row with `event_kind = 'connect'`.
   **`SevenRoomsWebhookClient.subscribe` is NEVER invoked** —
   verified by the test
   `manualPaste: connect ... webhookClient.subscribe NEVER invoked`.
7. The card expands to show the **Manual webhook paste** panel with
   the F&F webhook URL and numbered instructions (per
   `webhook_signature.md` Manual paste instructions). The widget
   `Key('vendor_picker_sevenrooms_webhook_url')` displays:

   ```
   https://api.forgeflow.app/v1/webhooks/sevenrooms/conn-1
   ```

   Next to the URL: a **Copy** button
   (`Key('vendor_picker_sevenrooms_webhook_url_copy')`).

   Below the URL: numbered operator-facing copy:

   ```
   1. Open your SevenRooms admin portal in a new tab.
   2. Go to Settings → Integrations.
   3. Click "Add webhook URL."
   4. Paste this URL into the "Webhook URL" field: <copied above>
   5. In the "Event filter" picker, check:
        - reservation.created
        - reservation.updated
        - reservation.cancelled
   6. Click "Save." SevenRooms will show you a signing secret on the
      confirmation screen — it looks like a long random string.
   7. Copy the signing secret and paste it back here in F&F to confirm
      the connection.
   ```

   Below the instructions: a single text field
   `Key('vendor_picker_sevenrooms_signing_secret_paste')` and a
   **Confirm signing secret** button.

8. The Vendor Connections widget enqueues a 60-day backfill (the
   adapter's `backfill` method runs against the
   `SevenRoomsReservationsClient` fixture). Five canonical reservation
   rows land in the operator-scoped fact table:
   - `sr-resv-1001`: `reservation_at: 2026-05-04T22:30:00Z`,
     `party_size: 2`, `status: booked`
   - `sr-resv-1002`: `reservation_at: 2026-05-04T22:45:00Z`,
     `party_size: 4`, `status: arrived`,
     `status_transitions.arrived: 2026-05-04T22:48:00Z`
   - `sr-resv-1003`: `reservation_at: 2026-05-04T23:00:00Z`,
     `party_size: 6`, `status: seated`,
     `status_transitions.seated: 2026-05-04T23:05:00Z`
   - `sr-resv-1004`: `reservation_at: 2026-05-04T23:15:00Z`,
     `party_size: 3`, `status: cancelled`
   - `sr-resv-1005`: `reservation_at: 2026-05-04T23:30:00Z`,
     `party_size: 2`, `status: booked`

   `business_date = 2026-05-04` (location-local, 4 AM rollover).

9. Operator returns to **Shift dashboard**. The reservation card
   flips from `MetricCardNotYetAvailable` to live counts ("In the
   Books: 5 reservations"). The top-left honesty pill drops
   "Reservations: not yet connected." Cards stay visually clean per
   `metric_card_honesty_contract.md`.

### Forged-signature webhook → 403 + audit + no fact write

1. Once the operator has pasted the webhook URL into the SevenRooms
   admin portal and confirmed the signing secret back in F&F, the
   vendor delivers a webhook to
   `https://api.forgeflow.app/v1/webhooks/sevenrooms/conn-1` with
   payload claiming `venue_id: sr-venue-7c2f` and
   `id: sr-resv-1001`, **but the signature header has one nybble
   flipped** (test fixture `tamperedSevenRoomsWebhook`).
2. `InboundWebhookHandler.dispatch` step 1 runs
   `SevenRoomsWebhookSignatureVerifier.verify`. The verifier computes
   the expected HMAC-SHA256 over the raw body and runs
   `constantTimeBytesEquals` — the result is **false**.
3. The handler records a failed attempt via
   `gateway.recordFailedAttempt` (audit row written), returns
   `WebhookOutcome.signatureInvalid` with status code **403**.
4. **No canonical-fact write occurs.** `connector_sync_log` shows no
   `webhook_received` row for this `vendor_event_id`. Shift
   dashboard cards remain unchanged.

### First valid signed webhook arrives → status flips to Connected

1. SevenRooms delivers a properly signed webhook (operator has pasted
   the webhook URL into the SevenRooms portal AND pasted the signing
   secret back into F&F).
2. `InboundWebhookHandler.dispatch` runs steps 1-4 (signature OK,
   binding cross-check OK, idempotency claim OK, sanity OK).
3. The handler dispatches to
   `SevenRoomsReservationAdapter.handleWebhook`. The adapter writes
   the canonical reservation row.
4. The framework's webhook-state path flips
   `connector_connection.metadata.webhook_state` from
   `pending_paste` to `verified`. The Vendor Connections card chrome
   updates from "Connected (webhook pending)" to "Connected".

### Subsequent forged signature → still 403

1. Once `webhook_state = verified`, the adapter is in steady-state.
   Any subsequent forged signature follows the same step 1-3
   rejection path as the first forged delivery.

### Malformed payload → log row + dropped

1. The vendor delivers a webhook whose signature passes but the
   payload omits `id` (test fixture
   `sevenRoomsMalformedReservation`).
2. The handler reaches step 5 and calls
   `SevenRoomsReservationAdapter.handleWebhook`. The adapter's
   `_projectCanonicalRecord` returns null because `id` is missing.
3. The adapter returns `HandleWebhookResult(recordsWritten: 0)`. The
   framework's dispatch unwind writes a `connector_sync_log` row with
   `event_kind = 'webhook_received'`, `records_count = 0`.
4. **No canonical-fact write occurs.** Shift dashboard cards remain
   unchanged. No `parse_warnings` JSONB column is touched (V1 lean
   cut 2 deletes that channel).

### Future-dated event → log row + dropped via sanity hook

1. SevenRooms delivers a webhook whose signature passes and payload
   parses cleanly but `arrival_time` is 5 days in the future
   (test fixture pattern `sevenRoomsFutureDatedReservation`).
2. `InboundWebhookHandler.dispatch` step 4 runs
   `VendorTimestampSanity.evaluate`. Future-dated rule fires.
3. The framework writes a `sanity_log` row + `connector_sync_log`
   `event_kind = 'sanity_drop'` row. The handler returns
   `WebhookOutcome.sanityDropped` with status code **200**.
4. **The adapter's `handleWebhook` is not called.** No canonical
   fact write. Shift dashboard cards remain unchanged.

### Disconnect → reconnect preserves watermark

1. Operator opens **Settings → Vendor Connections** and taps
   **Disconnect** on the SevenRooms card. A confirmation modal
   reminds the operator to also remove the F&F webhook URL from the
   SevenRooms admin portal manually (because manualPaste vendors do
   not have a vendor-side unregister endpoint).
2. The adapter calls
   `SevenRoomsAuthClient.revoke(accessTokenCredentialId: cred-access-1)`
   — best-effort; vendor outage shouldn't block disconnect.
3. The gateway runs `wipeCredentialsAndDisconnect`:
   `connector_connection.status = 'disconnected'`, credentials
   wiped, **`connector_sync_watermark` row preserved**.
4. `DisconnectResult` returns
   `webhookUnregistered: false` (no programmatic unregister occurred —
   manualPaste).
5. Shift dashboard reservation card flips back to
   `MetricCardNotYetAvailable`. The top-left honesty pill
   re-includes "Reservations: not yet connected."
6. Operator taps **Reconnect**; keypaste form runs again. The
   adapter's first `pollIncremental` after reconnect passes the
   preserved `connector_sync_watermark.cursor_token` to
   `SevenRoomsReservationsClient.fetchReservationsPage`. **No
   reservation rows are re-fetched / re-written**; backfill picks up
   exactly where it left off (test
   `smoke: connect → backfill → poll → disconnect → reconnect`).
