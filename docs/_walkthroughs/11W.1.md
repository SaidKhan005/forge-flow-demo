# 11W.1 Walkthrough — Members surface

**Slice:** 11W.1 (Phase 11W — Operator Web Console; Self-Service Parity block)
**Mode:** demo (`OPERATOR_WEB_DEMO_AUTH=true`)
**Date:** 2026-05-05

This slice ships the web parity for the mobile Settings → Team list. The
Operator Web Console gains a `Members` route at the side-nav. Operator
owners + admins can filter the team, invite new teammates, and
suspend / reactivate / soft-delete / reset password / reset MFA / force
sign-out from a desktop browser. Floor managers (`location_manager`)
get a read-only members list; floor staff hit a friendly forbidden
surface.

The slice ALSO creates the shared demo team fixture file every other
11W parity slice (Roles, Hierarchy, Sessions, Audit Log, Security)
extends. Running the walkthrough puts every operator-facing widget
on this slice through its paces.

**Wiring honesty (read this first):** `11W.1` ships the Members
*surface* against the in-memory `DemoWebTeamUsersGateway`. The live
HTTP gateway (`WebTeamUsersGatewayLive`) is built in this slice and
unit-tested against `MockClient` so the wire contract is pinned
today, but the live `FirebaseOperatorWebAuthSource` mixes the
gateway in via the `OperatorWebTeamUsersGatewayProvider` interface
in the `11W.1.live` follow-up — same gateway-follows-shell pattern
Phase 11A.0 → 11A.1 used. No new proxy routes were added; the live
gateway hits the existing `/v1/admin/auth/users` + `/v1/admin/auth/invites`
routes Phase 9 + 11A.1 already shipped.

**Cross-console pair:** `11A.12` (F&F Operations Console Members +
Invites parity) is the matched sibling per the parity contract
acceptance gate #7 ("the pair lands together or both stay active").
This walkthrough covers the operator-side surface only; the F&F
admin surface lands in `11A.12` against the same parity contract
section. Both must reach acceptance before either merges.

**Surface-map note:** the parity contract Surface map names the
operator self-service routes `/v1/auth/team/users` and
`/v1/auth/team/invites`. The Phase 9 + 11A.1 proxy ships those
routes only under the `/v1/admin/auth/...` prefix today (the mobile
gateway in `lib/services/auth/proxy_auth_operations_gateway.dart`
also calls them at the `/v1/admin/auth/...` paths). The live web
gateway matches mobile, hitting `/v1/admin/auth/users` and
`/v1/admin/auth/invites`. A separate routing-cleanup follow-up will
either rename the proxy routes or update the contract Surface map
once the F&F admin path vs. operator self-service path split lands
end-to-end (tracked via the contract's "If a slice prompt needs a
new route, the parity contract is incomplete" rule).

**Force sign-out (deferred):** the parity contract § Members + Invites
lists Force sign-out as a row action. `11W.1` deliberately defers
that action to Phase 11W.4 Sessions, which owns the
`team.session.force_logout` write through `/v1/auth/team/sessions`.
Routing it through the team-users surface (e.g. shoehorning it onto
`POST /v1/admin/auth/users/{user_id}/suspend`) would write the wrong
audit-row action and gate on the wrong permission key. Suspend
already cuts a member's ability to sign in until reactivated;
ending every active session right now is the additive Sessions
slice's job.

## What changed

### `lib/operator_web/services/demo_team_fixtures.dart` (new)

Shared fixture data set for every Phase 11W parity slice. Declares:

- `kDemoOperatorIdFixture = 'demo-operator'` and the matching
  business name (`Demo Bistro`).
- 3 locations (`Downtown`, `North Loop`, `Riverside`).
- 2 org units (`East Region` containing Downtown + North Loop;
  `West Region` containing Riverside).
- 6 demo users covering each non-admin seeded role plus one
  custom-role holder (`Floor Captain`). Status spread covers
  `active`, `suspended`, `dormant_30`, `soft_deleted` so every status
  filter chip has at least one matching row in the demo set.
- 1 pending invite so the invite-flow demo has a row to compare
  against after submission.
- Projection helpers `teamUserEntryFromFixture` /
  `teamInviteEntryFromFixture` so the demo gateway and downstream
  slices share the same row contract as the live gateway.

### `lib/operator_web/services/web_team_users_gateway.dart` (new)

Narrow `WebTeamUsersGateway` interface (just the team-users +
invites surface of `AuthOperationsGateway`) plus the live
`WebTeamUsersGatewayLive` impl built on `package:http`. Hits the
existing Phase 9 + 11A.1 routes:

- `GET    /v1/admin/auth/users`
- `GET    /v1/admin/auth/invites`
- `POST   /v1/admin/auth/invites`
- `DELETE /v1/admin/auth/invites/{invite_id}`
- `POST   /v1/admin/auth/users/{user_id}/suspend`
- `POST   /v1/admin/auth/users/{user_id}/reactivate`
- `POST   /v1/admin/auth/users/{user_id}/soft-delete`
- `POST   /v1/admin/auth/users/{user_id}/reset-password`
- `POST   /v1/admin/auth/users/{user_id}/reset-mfa`

Every write accepts a caller-minted `Idempotency-Key` and threads it
through as the `Idempotency-Key` request header. The gateway never
mints keys internally so the proxy `proxy_requests` UNIQUE-key
replay surfaces the original write on retry. No `dart:io`, no
`sqflite`.

### `lib/operator_web/services/demo_team_users_gateway.dart` (new)

In-memory `DemoWebTeamUsersGateway` reading the shared fixture file.
Caches mutation responses by idempotency key so a re-submission of
the same action returns the original outcome rather than mutating
again — matching the parity contract § Idempotency keys posture.
Mutations are session-local; reloading the page resets the data.

### `lib/operator_web/screens/members_screen.dart` (new)

Operator Web Console Members screen. Renders:

- Header (`operator_web_members_screen` →
  `operator_web_members_invite_button`) with the locked invite CTA.
- Filter rail (`operator_web_members_filter_rail`) with search,
  status, role, location, and two-factor filters.
- Members table (`operator_web_members_table`) with one row per
  filtered user, sorted by `last_active_at DESC` then `email ASC`
  (sort is applied client-side in `_filteredUsers` so the live
  proxy ordering is not a load-bearing assumption).
  Each row exposes a per-row action menu
  (`operator_web_members_row_actions_<userId>`) gated on the
  `team.users.*` permission keys when `OperatorWebSession.permissions`
  is hydrated; falls back to the role tier
  (`operator_owner`/`operator_admin`) when the snapshot is empty.
  Action options include Suspend, Reactivate, Reset password, Reset
  two-factor sign-in, and Remove from team — keys
  `members_row_action_<action>`. Soft-deleted rows render no action
  menu at all (Restore lives on the F&F admin path per Phase 11A.12;
  Force sign-out is deferred to 11W.4).
- Pagination bar (`operator_web_members_pagination`) showing the
  current `Showing X to Y of N` window with prev / next icons.
- Pending invites panel (`operator_web_members_pending_invites`)
  listing every outstanding invite by email + role + location.

Permission gate:

- `operator_owner` / `operator_admin` see every action enabled.
- `operator_manager` / `location_manager` see the table read-only
  (no action menus, invite button disabled).
- Other roles fall through to a friendly forbidden surface
  (`operator_web_members_forbidden`) explaining who manages members.

## Permission gating evidence

The Phase 9 + 11A.1 proxy routes already enforce role + permission
gates server-side. The client-side gate in `kOperatorWebMembersAdmittedRoles`
+ `kOperatorWebMembersWriteRoles` is the friendly-error layer per the
UX writing standard.

| Role               | Members list | Invite | Suspend / Reactivate | Reset password / MFA | Soft delete |
| ------------------ | ------------ | ------ | -------------------- | -------------------- | ----------- |
| `operator_owner`   | read         | yes    | yes                  | yes                  | yes         |
| `operator_admin`   | read         | yes    | yes                  | yes                  | yes         |
| `operator_manager` | read-only    | no     | no                   | no                   | no          |
| `location_manager` | read-only    | no     | no                   | no                   | no          |
| `operator_staff`   | forbidden    | n/a    | n/a                  | n/a                  | n/a         |

Force sign-out is deferred to Phase 11W.4 Sessions and is not in
this slice's row action menu. When the live `OperatorWebSession.permissions`
snapshot is hydrated by the proxy, the gate consults
`team.users.view` for the read surface and the `team.users.invite /
.deactivate / .reactivate / .soft_delete / .reset_password /
.reset_mfa` keys for the row actions. The role-tier fallback above
applies only when the snapshot has not been hydrated yet (demo
flavor + live bootstrap stage).
