# 9.UX inheritance-hint slice — role-change dialog per-grant hints

Date: 2026-04-30
Lane: `reverent-shirley-d8c5dc`

## Slice scope

This slice ships **the rendering capability only**. The
`_RoleGrantDialog` in `lib/screens/team/team_settings_section.dart`
is now wired to render an `Active grants` block above the assign
form when the target user has one or more `TeamUserRoleGrant`
entries on `TeamUserListItem.grants`. Each row carries a single-line
inheritance hint keyed off `scope_type`. The block is opt-in:
`grants` defaults to `const []`, so the Active-grants surface stays
hidden when no authoritative grant data is available.

The production data path **does not** seed `grants` in this slice.
The current `TeamUserListEntry` shape projects
`coalesce(ur.location_id, u.primary_location_id)` into
`entry.locationId` (see `users_repository.dart`
`selectTeamUsersByOperator`), so a non-null `entry.locationId` is
ambiguous — it can be either an `ur.location_id` from a
`location`-scoped grant OR a `u.primary_location_id` (display home)
attached to an `operator_wide` grant. No field on the entry
disambiguates `scope_type`, so any best-effort derivation in
`forge_flow_app.dart:_teamUserFromEntry` would mislabel real rows
(an `operator_wide` owner with a primary location would render as
`Direct at {label}` instead of `Applies operator-wide`). Honesty
over coverage: `grants` is left empty on the production path.

This slice therefore lands **the rendering half** of Gap 2 from
`docs/_walkthroughs/9.UX.4.audit.md` for the role-change dialog
surface. The data half (gateway-side `scope_type` + full grant
list on `TeamUserListEntry`, OR a separate `listGrantsForUser`
gateway method) requires changes inside `lib/services/auth/`,
which Block 2 of this lane explicitly blocks. When that follow-up
slice lands, the upstream loader populates `TeamUserListItem.grants`
with authoritative data and the rendering branches already covered
by widget tests take over without any UI change.

## Render contract

Hint copy keyed off `scope_type`:

| `scope_type`     | Copy                                                |
| ---------------- | --------------------------------------------------- |
| `operator_wide`  | `Applies operator-wide`                             |
| `org_unit`       | `Inherited via {org_unit.label} (N location[s])`    |
| `location`       | `Direct at {location.label}`                        |

Plural agreement on the org-unit branch:
- `effective_location_ids.length == 1` → `(1 location)`
- otherwise → `(N locations)`

Lookup-miss fallback (the unit/location was deleted between the
gateway fetch and the dialog opening so the section's already-loaded
options no longer carry the label):

- `org_unit` lookup miss → `org_unit (unknown)`
- `location` lookup miss → `location (unknown)`
- never throws.

## Operator walkthrough (kDemoMode = true)

The walkthrough below was executed against the multi-grant test
fixture in `test/team_settings_inheritance_hint_test.dart`'s
`multi-grant user renders all three scope branches in one dialog`
case, which seeds three grants on a single demo user (one of each
scope type) — the same shape Block 3 step 2 of the slice prompt
calls for.

1. **Open Settings → Team.** `TeamSettingsSection` mounts with the
   actor permissioned for `team.users.view` + `team.roles.assign`.
2. **Tap the user-actions menu** for `multi@example.test`
   (`team_user_actions_user-multi`). The popup lists `Change role`
   first because `team.roles.assign` is held.
3. **Tap `Change role`.** `_openRoleDialog` runs `showDialog` and the
   `_RoleGrantDialog` renders with three live grants:

   | Grant key                              | Role label  | Inheritance hint                          |
   | -------------------------------------- | ----------- | ----------------------------------------- |
   | `team_role_change_grant_grant-multi-op`  | Owner       | `Applies operator-wide`                   |
   | `team_role_change_grant_grant-multi-org` | Manager     | `Inherited via East Region (3 locations)` |
   | `team_role_change_grant_grant-multi-loc` | Supervisor  | `Direct at Vancouver Robson`              |

   Asserted via `find.text(...)` — see the test output above.
4. **Singular case (separate fixture):** the
   `org_unit grant with 1 effective location renders singular "1 location"`
   test passes the same dialog with `effective_location_ids = ['loc-vancouver']`
   and the hint reads `Inherited via East Region (1 location)`.
5. **Stale-label case (separate fixture):** the
   `org_unit grant whose unit is missing from the loaded options falls back to "org_unit (unknown)"`
   test passes an empty `orgUnitOptions` list (simulating the
   `East Region` row deleted between fetch and render). The dialog
   renders `org_unit (unknown)` and `tester.takeException()` returns
   `null`, proving the fallback never throws.

The widget tests above exercise the same `_RoleGrantDialog` that
mounts in `Settings → Team → user-action menu → Change role` under
`kDemoMode`, but they seed `TeamUserListItem.grants` directly. The
production loader in `forge_flow_app.dart:_teamUserFromEntry`
deliberately leaves `grants` empty (see the slice-scope section
above for the `coalesce(ur.location_id, u.primary_location_id)`
ambiguity that blocks safe derivation), so on a real
`Settings → Team → Change role` path today:

- The `Active grants` block stays hidden — the dialog renders the
  existing assign form unchanged. This is the same behavior the
  `user with no grants renders no Active grants block` widget test
  pins.
- Once the gateway-side follow-up populates `TeamUserListItem.grants`
  with authoritative `scope_type` + `effective_location_ids` data,
  the rendering branches lit up by the widget tests engage
  automatically — `_teamUserFromEntry` becomes a pass-through and
  the dialog body changes without any further UI work.

Why we don't ship a derivation in this lane:

- `entry.locationId` is `coalesce(ur.location_id,
  u.primary_location_id)`. An `operator_wide` grant for a user
  who carries a `primary_location_id` (the common case for
  non-roaming staff) would be mis-labeled as `'location'` scope
  and the dialog would render `Direct at {primary location}`
  instead of `Applies operator-wide`. That is a misleading
  display, worse than no display.
- `org_unit` scope cannot be derived at all — the entry shape
  carries no `org_unit_id`.
- The entry shape carries no `scope_type` field. Any inference is
  guessing.

The honest scope of this lane is therefore: rendering capability +
test coverage, locked behind the `grants.isNotEmpty` gate, ready
for the gateway slice to land authoritative data without further
section / dialog work.

## Brand-styling

- Active-grants container uses the existing
  `AppColors.backgroundSurface` + `AppColors.borderSubtle` shell
  (matches the invite panel container at
  `team_settings_section.dart:_TeamInvitePanel`).
- "Active grants" header + per-grant role label use
  `AppTextStyles.body14` with `AppColors.textPrimary` (semibold,
  primary text).
- Inheritance hint label uses `AppTextStyles.body12` with
  `AppColors.textMuted` — italic, smaller, lower-emphasis weight.
  This is the same pair the existing `Child locations inherit
  org-unit grants.` muted hint already uses below the dialog's
  org-unit dropdown, so the visual hierarchy is consistent.

## Permission-gating (not weakened)

The role-change dialog is reachable only from the user-action menu,
which only emits the `Change role` entry when
`canAssignRole = TeamScopeVisibilityPolicy.canMutateTarget(...,
required: 'team.roles.assign')` is true. Per-grant rendering inside
the dialog body does not bypass this gate — the dialog itself never
opens for an actor without `team.users.view` (kernel test:
`hides Team destination for actors without team.users.view`).
