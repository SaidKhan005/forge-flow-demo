# 8.0 Walkthrough — Inbound integration framework + metric honesty + timestamp sanity

**Slice:** 8.0 (Phase 8 — POS / labor / reservation integration framework, V1 lean cut 2)
**Mode:** `kDemoMode = true` (operator app, deterministic seed). Sandbox OAuth where named.
**Date:** 2026-05-04
**Demo start condition:**
- Business date `2026-W18 Mon` (Monday of ISO week 18, 2026).
- Operator: "Demo Diner Co.", Location: "Toronto Yorkville".
- Shift dashboard scope: whole-day.
- All vendor connections empty. `demo_mode_state.is_demo = true` for `pos`, `labor`, `reservation`.

This walkthrough is a numbered click-path per the
`docs/CODEX_PROMPT_GENERATION_STANDARD.md` Walkthrough Specificity
section. Every step names the user action, the expected visual state,
the named widget(s) under test, and the named values
(`MetricState` / `provenance`) that drive each render.

The slice realizes three Hard Promises:
1. **Phase 8 = pure transport swap.** Vendor connectors write existing
   tables only.
2. **Demo mode persists post-launch.** `kDemoMode` is a writer-side
   switch; same tables, same reads, same UI either way.
7. **F&F holds all provider keys server-side.** No BYO-key.

And it closes the operator-trust contract from
`docs/contracts/metric_card_honesty_contract.md`: phantom zeroes are
gone; the `DataSourceHealthPill` is the single window into
degradation; metric cards in `live` / `partial` / `fallback` render
identical chrome; `MetricCardNotYetAvailable` renders only when
state is `unavailable`.

## Click-path

### 1. Empty state — POS card and dashboard pill

- Operator opens the app on `2026-05-04 (Mon, W18)`. Settings →
  Vendor connections.
- POS card section is empty. Card slot reads:
  > **Connect your Point-of-sale (POS) system**
  > Forge & Flow needs to read sales and order data from your POS to
  > power your dashboard, baseline math, and Shift live view. Pick
  > yours and we walk you through connecting it.
  > [Choose your POS]
- Tab back to **Shift dashboard**. Top-left dashboard pill is
  ABSENT (yes — even though demo data is loading, the read model
  has not yet been built; the pill is only assembled once the
  read model is available).
  - **Widget under test:** `_ShiftDashboardHealthPill`
    (`lib/screens/shift_dashboard.dart`) → emits `SizedBox.shrink`
    via `data_source_health_pill_absent` key when no metrics report
    `isDegraded`.
  - **Expected MetricState:** every dashboard metric is in
    `MetricState.unavailable` because `posSourceVendorId == null`
    and `laborSourceVendorId == null`. The dashboard pill normally
    SHOWS in this state — but iter1 demo seed loads a live
    fixture, so for the click-path purpose: as soon as a vendor is
    connected, expect the pill to appear and disappear per steps
    below.

### 8. Reconnect Lightspeed → pill goes away once data lands

- Settings → POS card → **Reconnect** (same flow as step 2).
- Sandbox OAuth completes; card flips back to **Connected**.
- Watermark resumes; the first backfill batch replays the missed
  window. Until that batch commits, `actualCovers` may stay zero
  and the dashboard CPLH/PPA cards continue to render
  `MetricCardNotYetAvailable` (they only flip to `live` when
  `actualCovers > 0` AND `posSourceVendorId != null`).
- After the first backfill batch commits ≥1 record:
  - PPA, Sales, Covers cards flip to `live`. Provenance
    `vendor_lightspeed_lsk`.
  - CPLH stays `live` (labor was connected throughout).
  - Top-left pill DISAPPEARS.
  - `demo_mode_state.is_demo` for `pos` flips to `false` (the
    flip-on-first-backfill-commit policy fires).

### 9. Adversarial: forged webhook signature

- A bad actor sends a forged Lightspeed webhook to
  `/v1/webhooks/lightspeed_lsk/<operator_id>/<location_id>`.
- The proxy invokes `InboundWebhookHandler.dispatch`. The
  `_StubSignatureVerifier`-style verifier returns `valid = false`.
- Expected outcome:
  - **Widget under test:** none (server-side flow).
  - HTTP status `403`.
  - `WebhookOutcome.signatureInvalid`.
  - `inbound_webhook_idempotency.attempt_count` increments to 1.
  - No canonical fact written.
- After three forged retries: `inbound_webhook_dead_letter` row
  with `failure_kind = 'signature_invalid'`. No DLQ tile in
  observability admin (V1 lean cut 2 trim); the row stays for
  forensic read by support via the proxy debug console.

### 10. Adversarial: malformed payload

- Lightspeed (or a forged source) sends a payload with the
  expected signature but an unexpected field shape (e.g.,
  `business_id` is a JSON object instead of a string).
- Expected outcome:
  - **Widget under test:** none.
  - The adapter's `handleWebhook` throws on parse.
  - `WebhookOutcome.adapterError`.
  - HTTP status `500` so the vendor retries.
  - `inbound_webhook_idempotency.attempt_count` increments;
    after three failures the event lands in
    `inbound_webhook_dead_letter` with `failure_kind =
    'adapter_error'`.
  - Queue is NOT poisoned — the dispatch loop continues to
    accept new events. **No `parse_warnings` or `parse_partial`
    is recorded** (V1 lean cut 2 removed those columns).

### 11. Adversarial: future-dated event

- Lightspeed sends a webhook with `opened_at = now() + 5 days`.
- The handler runs steps 1–3 (signature, binding, idempotency) all
  green. Step 4 — vendor timestamp sanity guard — fires.
- Expected outcome:
  - **Widget under test:** none.
  - `VendorTimestampSanity.evaluate` returns `failed = true`,
    `rule = SanityRule.openedInFuture`,
    `rule!.sqlValue = 'opened_in_future'`.
  - `WebhookOutcome.sanityDropped`.
  - HTTP status `200` (we accept the request from the vendor's
    perspective; we just never write a canonical fact).
  - `sanity_log` row written with `rule = 'opened_in_future'`,
    `payload_summary` carrying `opened_at` + `now`.
  - `connector_sync_log` row written with
    `event_kind = 'sanity_drop'`.
  - No canonical fact written. The dashboard's
    business-date-2026-W18-Mon view stays clean.

### 12. Adversarial: closed_at < opened_at

- Lightspeed sends a webhook with `closed_at` an hour BEFORE
  `opened_at`.
- Expected outcome:
  - `VendorTimestampSanity.evaluate` returns `failed = true`,
    `rule = SanityRule.closedBeforeOpened`,
    `rule!.sqlValue = 'closed_before_opened'`.
  - `WebhookOutcome.sanityDropped`.
  - `sanity_log` row written with `rule = 'closed_before_opened'`.
  - `connector_sync_log` row written with `event_kind =
    'sanity_drop'`.
  - No canonical fact written.

### 13. OAuth near-expiry refresh + 3-strike auto-disable

- Time-travel the test clock so an existing
  `vendor_credentials.token_expires_at` is `now() + 30 minutes`
  (within the 24-hour `kRefreshExpiryHorizon`).
- The `pg_cron` job invokes
  `OAuthRefreshCronRunner.runOnce`. The vendor responds with a new
  envelope.
- Expected outcome:
  - `connector_sync_log` row written with `event_kind =
    'auth_refresh'`.
  - `vendor_credentials.consecutive_refresh_failures = 0`.
  - Connection stays `connected`.
  - **No `pg_advisory_lock` involved at V1 (lean cut 2 trim).**
- Drive a vendor failure path: refresher returns
  `VendorRefreshOutcome.failure(...)` three consecutive ticks.
- Expected outcome on the third tick:
  - `connector_connection.status` flips to `error`.
  - `audit_logs` row written.
  - **No `email_outbox` row emitted at V1.** Operator sees the
    state in admin UI; email alert wiring lands later.
  - The Vendor connections card shows the `error` status badge.
    Tooltip: "Something is wrong. Most often the vendor revoked
    our access. Click Reconnect and sign back in."
