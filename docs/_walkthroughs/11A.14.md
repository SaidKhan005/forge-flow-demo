# 11A.14 Walkthrough — Audited support actions (cross-operator admin)

**Slice:** 11A.14 (Phase 11A — F&F Operations Console)
**Mode:** `-DemoMode` (admin Flutter Web client + in-memory audited
support actions admin gateway, no live proxy required)
**Date:** 2026-05-06

This walkthrough covers the admin click path for the new
`Audit log and support actions` route mounted at
`/admin/audited-support-actions` in `lib/admin/admin_routes.dart`.
The slice ships the cross-operator audit-log review surface plus an
Actions panel for the F&F admin to run support escalations
(Reset MFA / Initiate password reset / Issue paired-approval
erasure) against a picked operator. The slice is the only Wave 3
slice that adds a new permission key — `admin.users.reset_mfa_factors`
— via additive migration.

## Click path (text trace)

### Step 1 — Sign in as super_admin and open the route

Launch the admin console with `-DemoMode -Device chrome`, sign in
as `super.admin@forgeflow.test`, click `Audit log and support
actions` in the side nav.

**Expected:**

- The route mounts the operator-picker screen first
  (`Key('admin_operator_picker_screen')`) — the surface is scoped
  to one operator at a time.
- The picker dialog renders with an operator dropdown.

### Step 2 — Pick Demo Diner Co.

Choose `Demo Diner Co.` in the operator dropdown, leave Toronto
Yorkville selected, tap `Use selection`.

**Expected:**

- The surface mounts
  (`Key('admin_audited_support_actions_screen')`) with the picked
  operator named in the page header subtitle ("Review the audit log
  and run support actions for Demo Diner Co. ...").
- The Actions panel (`Key('admin_asa_actions_panel')`) renders at
  the top of the body with three rows: `Reset member MFA`,
  `Initiate password reset`, `Issue paired-approval erasure`. The
  Reset MFA and erasure rows show an `MFA` chip (lock icon plus the
  literal text); the password reset row does not.
- The Audit log card (`Key('admin_asa_audit_log')`) renders below
  the Actions panel with the locked filter set
  (`Key('admin_asa_filters')`) — actor dropdown, target_kind
  dropdown, free-text target ID, time-window dropdown, the
  `actor_kind` multi-select chip group (F&F admin surface only,
  three chips), AND the `action` multi-select chip group covering
  every value in `kAuditLogFilterableActions` — and 3 rows visible
  (`admin_asa_audit_row_seed-diner-1` /
  `admin_asa_audit_row_seed-diner-2` /
  `admin_asa_audit_row_seed-diner-3`). Each row carries a copy
  button on the target ID
  (`admin_asa_audit_row_copy_target_<event_id>`), a `View payload`
  toggle when the payload is non-empty
  (`admin_asa_audit_row_payload_toggle_<event_id>`), and a
  human-readable `Occurred YYYY-MM-DD HH:MM local (UTC ...)`
  timestamp.

### Step 3 — Apply an actor_kind filter

In the filters bar, toggle the `F&F admin` chip
(`Key('admin_asa_filter_actor_kind_forge_admin')`), then tap
`Apply filters` (`Key('admin_asa_filter_apply')`).

**Expected:**

- The audit-log table re-renders with only the
  `admin.session.force_logout` row from the 11A.13 walkthrough
  visible (one row).

### Step 3a — Apply an action multi-select filter

Clear the actor_kind filter; toggle the action chip for
`admin.session.force_logout`
(`Key('admin_asa_filter_action_admin.session.force_logout')`); tap
`Apply filters`.

**Expected:**

- The audit-log table renders only the `seed-diner-3` row.

### Step 3b — Pick a custom date range

Open the time-window dropdown
(`Key('admin_asa_filter_time_window')`), pick `Custom range`. The
two date-picker buttons appear
(`admin_asa_filter_custom_from` + `admin_asa_filter_custom_to`).
Picking dates and tapping `Apply filters` re-runs the query against
the chosen window.

### Step 3c — Copy a target ID + view payload

Tap `admin_asa_audit_row_copy_target_seed-diner-3` — a snackbar
reads `Copied target ID to clipboard.` and the system clipboard
holds `session-diner-owner-mobile`.

Tap `admin_asa_audit_row_payload_toggle_seed-diner-3` — the
collapsed JSONB payload reveals as `user_id: demo-user-diner-owner`.
Tapping again hides the payload.

### Step 3d — Pagination

When the audit log returns more than 200 rows, a `Load more rows`
button (`admin_asa_audit_log_load_more`) appears at the bottom of
the table. Tapping it fetches the next cursor and appends the
incoming rows to the visible list. The button hides when
`next_cursor` is null.

## Permission gating evidence

- Client side (admin console): the route is only reachable when
  the auth gate admits the caller (`super_admin` or `ff_support`).
  The `_buildAuditedSupportActions` builder reads
  `state.session.roles` and computes
  `canEdit = roles.contains('super_admin')`; the screen consumes
  `editingEnabled` to drive the read-only banner and the
  visibility of every mutate affordance.
  `canResetMfaFactors` / `canIssuePairedErasure` /
  `canExportAuditLog` are conservatively `false` until a future
  session-claim resolver flips them from MFA-required claims.
- Defence in depth at the gateway seam:
  `AuditedSupportActionsAdminGateway.{exportAuditLogCsv,
  resetMemberMfa, initiatePasswordReset,
  issuePairedApprovalErasure}` each throws
  `AuditedSupportActionsForbiddenException` when
  `actorIsForgeAdmin == false`. Asserted by "every mutation throws
  Forbidden when actorIsForgeAdmin is false".
- Defence in depth on `admin_reason`: every gateway write throws
  `AuditedSupportActionsGatewayError(errorCode:
  'admin_reason_required')` on empty reason.
- Cannot-self-pair pinning: the gateway throws `cannot_self_pair`
  with the locked validation copy when the second-leg confirmation
  is by the same admin who opened the request; the screen surfaces
  the same copy in an error banner.
- Catalog keep-in-sync pinning: a gateway-test group asserts the
  new key is present in `PermissionKeys.all` AND in
  `PermissionKeys.requiresMfa` AND in the additive migration file
  AND in the catalog markdown row (with the `| yes |` MFA marker).
