# 11W.2 Walkthrough: Roles + Permission Explainer + custom-role builder

**Slice:** 11W.2 (Phase 11W: Operator Web Console; Self-Service Parity block)
**Mode:** demo (`OPERATOR_WEB_DEMO_AUTH=true`)
**Date:** 2026-05-05

This slice ships the web parity for the mobile Settings, Roles surface.
The Operator Web Console gains a `Roles` route at the side-nav.
Operator owners + admins see the seeded role catalog read-only, build
custom roles from a 9-category permission tree, and manage role grants
on member rows. Floor managers (`location_manager`) get a read-only
roles list; supervisors and staff hit a friendly forbidden surface.

The slice extends the shared demo team fixture file from 11W.1 with
per-role permission allow-sets and a baseline grant ledger so the
Roles surface, Permission Explainer, and custom-role builder all
render against the same fixture data the Members surface uses.

**Wiring honesty (read this first):** `11W.2` ships the Roles
*surface* against the in-memory `DemoWebTeamRolesGateway`. The live
HTTP gateway (`WebTeamRolesGatewayLive`) is built in this slice and
unit-tested against `MockClient`; the live `FirebaseOperatorWebAuthSource`
mixes the gateway in via the `OperatorWebTeamRolesGatewayProvider`
interface in the `11W.2.live` follow-up, same gateway-follows-shell
pattern Phase 11A.0 -> 11A.1 used. No new proxy routes were added; the
live gateway hits the existing `/v1/admin/auth/roles` +
`/v1/admin/auth/role-grants` routes Phase 9 + 11A.1 already shipped.

**Cross-console pair:** `11A.13` Roles tab (F&F Operations Console
Roles + Hierarchy + Sessions inspect) is the matched sibling per the
parity contract acceptance gate #7 ("the pair lands together or both
stay active"). This walkthrough covers the operator-side surface
only; the F&F admin Roles tab lands in `11A.13` against the same
parity contract section. Both must reach acceptance before either
merges.

**Permission Explainer copy is verbatim:** the parity contract
forbids paraphrasing catalog `description` text. Verbatim copy lives
in `kPermissionExplainerDescriptions` in
`lib/operator_web/screens/permission_explainer_screen.dart` and is
sourced from the migrations that seed `public.permission_keys.description`:

- `db/migrations/202604250008_auth_schema_foundation.sql`
- `db/migrations/202604270000_phase_9_0a_scope_extensions.sql`
- `db/migrations/202604280014_phase_9_0sigma_h2_audit_privacy_role.sql`
- `db/migrations/202604300002_phase_9_mfa_hardening_launch_roles.sql`
- `db/migrations/202605040000_phase_8_0_integration_framework.sql`

If a description reads poorly to an operator, the fix is to update
the migration + catalog doc + `lib/auth/permission_keys.dart` + this
description map together in a separate slice. Do NOT paraphrase the
copy in the UI.

**Role-grant assign / revoke flow:** the parity contract describes
role-grant assign / revoke as the "from member rows" interaction.
`11W.2` exposes the role-grant write contract via the
`WebTeamRolesGateway.createRoleGrant` /
`WebTeamRolesGateway.revokeRoleGrant` methods (same proxy routes
the mobile gateway already hits). The Members row action that calls
those methods lands in the `11W.1.UX.1` follow-up so this slice can
stay scoped to the catalog + builder + explainer; the gateway is
ready and the fixture set carries the seeded grants today, so the
follow-up only wires the row-action UI without touching auth-server
code.

## What changed

### `lib/operator_web/services/web_team_roles_gateway.dart` (new)

Narrow `WebTeamRolesGateway` interface (just the role-catalog +
role-grant slice of `AuthOperationsGateway`) plus the live
`WebTeamRolesGatewayLive` impl built on `package:http`. Hits the
existing Phase 9 + 11A.1 routes:

- `GET    /v1/admin/auth/roles`
- `POST   /v1/admin/auth/roles`
- `PATCH  /v1/admin/auth/roles/{role_id}`
- `DELETE /v1/admin/auth/roles/{role_id}`
- `POST   /v1/admin/auth/role-grants`
- `DELETE /v1/admin/auth/role-grants/{user_role_id}`

Every write accepts a caller-minted `Idempotency-Key` and threads it
through as the `Idempotency-Key` request header. The gateway never
mints keys internally so the proxy `proxy_requests` UNIQUE-key
replay surfaces the original write on retry. No `dart:io`, no
`sqflite`.

### `lib/operator_web/services/demo_team_roles_gateway.dart` (new)

In-memory `DemoWebTeamRolesGateway` reading the shared fixture file.
Caches mutation responses by idempotency key so a re-submission of
the same action returns the original outcome rather than mutating
again, matching the parity contract Idempotency keys posture.
Mutations are session-local; reloading the page resets the data.

The demo gateway also enforces the same business-rule guards the
proxy ships: seeded roles can never be edited or deleted from the
operator self-service surface (`role_not_editable`), and a custom
role with active grants cannot be deleted until every grant is
revoked first (`role_has_active_grants`).

### `lib/operator_web/services/demo_team_fixtures.dart` (modified)

Extended the `DemoTeamRoleFixture` shape with `description` +
`permissionKeys` fields so the Roles surface and Permission Explainer
have the per-role permission allow-set and verbatim description text
the live catalog returns. Each seeded role fixture carries a baseline
allow-set that mirrors the migration's `role_permissions` cross-join
closely enough for a believable walkthrough. Custom Floor Captain
ships with a 4-permission allow-set per the parity contract demo
fixture rules.

Added `kDemoTeamRoleGrantsFixture` and `DemoTeamRoleGrantFixture` so
the Roles surface and (future) Members row-action flow can render
which members hold which role without dragging in the Members
gateway. Six seeded grants, one per fixture user, including the
Floor Captain assignment on Dakota Singh.

Added projection helpers `teamRoleEntryFromFixture` +
`teamGrantSnapshotFromFixture` so the demo gateway and downstream
slices share the same row contract as the live gateway.

### `lib/operator_web/screens/permission_explainer_screen.dart` (new)

Operator Web Permission Explainer screen mounted at
`/roles/explainer`. Renders the frozen permission key catalog as 9
category blocks in the locked order from the parity contract:
`product` -> `forgeflow` -> `barrio` -> `admin` -> `team` ->
`billing` -> `integration` -> `integrations` -> `workflow`.

Each block keys off `Key('operator_web_permission_explainer_category_<category>')`.
Each row keys off `Key('operator_web_permission_explainer_row_<key>')`
with the verbatim catalog description in
`Key('operator_web_permission_explainer_desc_<key>')`. MFA-required
keys (per `PermissionKeys.requiresMfa`) render an inline lock chip
keyed off `Key('operator_web_permission_explainer_mfa_<key>')` with
the contract-mandated tooltip `Requires multi-factor authentication.`

### `lib/operator_web/screens/custom_role_editor_screen.dart` (new)

Operator Web custom-role builder screen mounted at
`/roles/edit/:id` (or `/roles/edit/new` for create mode). Layout:

- Metadata card (`operator_web_custom_role_editor_screen`) with
  display name (`operator_web_custom_role_editor_display_name`),
  role key (`operator_web_custom_role_editor_role_key`), and
  description (`operator_web_custom_role_editor_description`)
  fields. Role keys lock once a role is created (only mutable in
  create mode).
- Permission picker (`operator_web_custom_role_editor_permissions`)
  reusing the 9-category layout from the Explainer with one
  checkbox per key (`operator_web_custom_role_editor_perm_<key>`).
  Selecting a key flips an in-memory `Set<String>`; saving writes a
  `permissions[]` payload of `{permission_key, effect: 'allow'}`
  rows for each selected key, plus `effect: null` rows for any keys
  the operator cleared so the proxy clears the explicit allow rule.
- Save / cancel buttons; save is disabled until name + role key (in
  create mode) + at least one permission are filled in. Save threads
  a screen-minted idempotency key through the gateway. Errors
  surface in a panel keyed `operator_web_custom_role_editor_error`.

The frozen-catalog guard fires both client-side (the picker only
exposes keys in `PermissionKeys.all`) and server-side (the proxy
returns `validation_failed/permission_key_unknown` when an unknown
key is submitted). The screen mirrors the rejection by surfacing the
locked copy `One or more permission keys are not in the catalog.
Pick keys from the list below.`

## Permission gating evidence

The Phase 9 + 11A.1 proxy routes already enforce role + permission
gates server-side. The client-side gate in
`kOperatorWebRolesAdmittedRoles` + `kOperatorWebRolesWriteRoles` is
the friendly-error layer per the UX writing standard.

| Role               | Roles list | New role | Edit custom | Delete custom |
| ------------------ | ---------- | -------- | ----------- | ------------- |
| `operator_owner`   | read       | yes      | yes         | yes           |
| `operator_admin`   | read       | yes      | yes         | yes           |
| `operator_manager` | read-only  | no       | no          | no            |
| `location_manager` | read-only  | no       | no          | no            |
| `operator_supervisor` | forbidden | n/a   | n/a         | n/a           |
| `operator_staff`   | forbidden  | n/a      | n/a         | n/a           |

When the live `OperatorWebSession.permissions` snapshot is hydrated
by the proxy, the gate consults `team.roles.view` for the read
surface and `team.roles.create_custom` for the create + edit + delete
paths. The role-tier fallback above applies only when the snapshot
has not been hydrated yet (demo flavor + live bootstrap stage).
