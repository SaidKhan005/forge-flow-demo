# 11A.3a Walkthrough - Corpus admin surface

**Slice:** 11A.3a (Phase 11A - F&F Operations Console)
**Mode:** `-DemoMode` (admin Flutter Web client + in-memory corpus
gateway, no live Voyage / Anthropic / Cloud Run admin proxy required)
**Date:** 2026-05-01

This walkthrough covers the admin click path called out in the 11A.3a
prompt's *Operator walkthrough* section: viewing the corpus version
ledger, uploading a markdown seed, previewing the diff, committing it
as a new corpus version, rolling back to a prior version, and
verifying that non-super-admin demo identities cannot mutate. The
demo source is opt-in (`-DemoMode`); production binds the live
Firebase admin auth source + HTTP gateway
(`HttpCorpusAdminGateway`) against the F&F admin Cloud Run proxy.

## Authority files exercised

- `lib/main_admin.dart` - production binds
  `HttpCorpusAdminGateway` against
  `--dart-define=ADMIN_PROXY_BASE_URI=...` and wraps
  `AdminConsoleApp` in `AdminConsoleServicesScope` with the corpus
  gateway alongside the operator/location and pricing gateways. Demo
  falls back to the seeded in-memory corpus gateway in
  `admin_routes.dart`.
- `lib/admin/admin_routes.dart` - Corpus route promoted from
  placeholder to live; `AdminConsoleServicesScope` grows a
  `corpusAdminGateway` field and a default in-memory demo seed
  carrying two corpus versions (the v1 initial seed plus a v2 with
  daypart guidance).
- `lib/admin/screens/corpus_admin_screen.dart` - the corpus admin
  surface. Versions list, version detail card, upload affordance,
  staged-diff card with new / modified / inactivated chunk
  sections, commit + rollback buttons, action-error banner,
  read-only banner.
- `lib/admin/models/corpus_admin_models.dart` -
  `CorpusBundle`, `CorpusVersionRef`, `ChunkPreview`, `CorpusDiff`,
  `UploadCommand`, `CommitCommand`, `RollbackCommand`, plus the
  launch-time upload allowlist (`kCorpusUploadAcceptedContentTypes`)
  and size cap (`kCorpusUploadMaxBytes`).
- `lib/admin/services/corpus_admin_gateway.dart` - HTTP +
  in-memory gateway implementations. The in-memory gateway runs a
  small markdown chunker (split on H2 headings) so the demo diff has
  realistic shape without invoking Voyage / Anthropic.
- `lib/infrastructure/persistence/postgres/repositories/corpus_repository.dart`
  - cross-operator `corpus_versions` + `advisor_source_chunks`
  reads and writes through `withSystem`. `commitVersion`
  transactionally supersedes the prior current version, inserts a
  fresh `corpus_versions` row, stamps active chunks
  `superseded_at = now()`, and writes the new chunk set under the
  new `version_id`. `rollbackToVersion` re-points the active corpus
  at the rolled-back chunk set under a new ledger row whose
  `rollback_of` carries the target id.
- `db/migrations/202605010000_phase_11A_3a_corpus_versions_ledger.sql`
  - `corpus_versions` table (`version_id`, `created_by`,
  `created_at`, `summary`, `rollback_of`, `superseded_at`),
  `advisor_source_chunks.version_id` (informational
  first-introduced pointer) and `advisor_source_chunks.superseded_at`
  columns, plus the `corpus_version_chunks(version_id, chunk_id)`
  many-to-many membership table. The membership table is the
  authoritative answer to "which chunks belong to this version" —
  upserting a chunk row never overwrites a prior version's
  `version_id`, which would otherwise destroy the historical
  snapshot (v1 with A+B; v2 keeping A; rollback to v1 must still
  recover both A and B). Indexes:
  `corpus_versions(version_id)`,
  `corpus_versions(created_at desc)`,
  `advisor_source_chunks(version_id)`,
  `advisor_source_chunks(superseded_at)`,
  `corpus_version_chunks(version_id)`,
  `corpus_version_chunks(chunk_id)`. RLS on `corpus_versions` and
  `corpus_version_chunks` admits the service role only;
  `forge_admin` table grants are issued explicitly because
  BYPASSRLS does not grant table privileges.
- `tool/advisor_proxy/advisor_proxy.dart` -
  `/v1/admin/corpus/versions`, `/v1/admin/corpus/versions/{id}`,
  `/v1/admin/corpus/upload`, `/v1/admin/corpus/preview-diff`,
  `/v1/admin/corpus/commit`, `/v1/admin/corpus/rollback` route
  handlers; CORS preflight admits `Idempotency-Key` via the
  dedicated `_setAdminCorpusCorsHeaders` helper; method-scoped role
  gate (`kFfCorpusAdminReadRoles` = `super_admin` + `ff_support`
  for `GET`; `kFfCorpusAdminWriteRoles` = `super_admin` for `POST`);
  every non-GET route requires the `Idempotency-Key` header (400
  `missing_idempotency_key` otherwise); structured 4xx for
  `unsupported_content_type`, `binary_or_unsupported_file`,
  `upload_too_large`, `unknown_preview_token`, `unknown_version`.
- `tool/advisor_proxy/proxy_bootstrap.dart` -
  `RepositoryCorpusAdminProxyGateway` binding wired from
  `CorpusRepository` + `AuthEventsAuditRepository` over the admin
  pool. The launch binding wires the read + rollback paths against
  Postgres directly; the upload + commit pipeline lights up in
  11A.3b once the markdown chunker is split out of
  `tool/advisor_corpus/main.dart` into a server-side helper. The
  binding rejects upload + commit with a typed
  `corpus_pipeline_not_configured` 503 in the meantime so the route
  never silently writes an empty version row in production.

## Demo identities

Demo auth fixture emails (any password accepted in demo mode); admit
decisions match the 11A.0 / 11A.1 / 11A.2 walkthroughs.

| Email                         | Roles            | Admit decision     | Corpus edit |
| ----------------------------- | ---------------- | ------------------ | ----------- |
| `super.admin@forgeflow.test`  | `super_admin`    | Admin shell        | Yes         |
| `support@forgeflow.test`      | `ff_support`     | Admin shell        | No          |
| `operator@forgeflow.test`     | `operator_owner` | Forbidden surface  | n/a         |

The default in-memory corpus gateway is seeded with two fixture
versions on the `methodology_seed.md` document. v1 is a superseded
historical row; v2 is the current active version with one extra
daypart chunk relative to v1.

`ff_support` is admitted to the admin shell but the Corpus route
proxy gates the mutate endpoints to `super_admin` only. Production
wires the read-only screen for `ff_support` automatically: the
Corpus route builder reads `AdminConsoleServicesScope.adminAuthSource`
and uses a `StreamBuilder` over `source.stream` to compute
`editingEnabled = roles.contains('super_admin')` on every auth state
change. `main_admin.dart` always wraps `AdminConsoleApp` with
`AdminConsoleServicesScope`, plumbing the source for both demo and
live modes; the demo `support@forgeflow.test` fixture lands on the
read-only branch end-to-end.

## Click path (text trace)

### Step 1 - Sign in as a demo super-admin

Launch the admin console with `-DemoMode -Device chrome` and sign in
as `super.admin@forgeflow.test`.

**Expected:** branded admin shell renders with the side nav. The
`Corpus` item is now live (no longer the "Markdown corpus admin
lands in 11A.3" placeholder subtitle).

### Step 2 - Open Corpus

Click `Corpus` in the side nav.

**Expected:**

- Body region renders the new `Corpus` surface
  (`Key('admin_corpus_screen')`).
- Header reads `Corpus` with a subtitle
  `Markdown corpus admin. Upload a seed, preview the diff against
  the active corpus, commit, or rollback to a prior version.`.
- Versions list (left column) shows the two seeded versions. The
  first row is the v2 demo version with the green `Current` chip
  (`Key('admin_corpus_current_<v2-id>')`) and the summary "Added
  daypart guidance". The second row is the v1 historical version
  (no Current chip), with its own `Rollback` button visible
  (`Key('admin_corpus_rollback_<v1-id>')`).
- Detail card (right column) defaults to v2. Detail rows show
  `Status: Current`, `Created at`, `Created by: demo-super-admin`,
  the summary, and `Chunks: 3`.
- A `Chunks in this version` card shows three `_ChunkPreviewTile`s,
  one per `methodology_seed.md` chunk.

### Step 3 - Upload a fresh markdown seed

Click `Upload markdown` (`Key('admin_corpus_upload_button')`). The
demo picker dialog (`Key('admin_corpus_demo_picker_dialog')`) opens
with a pre-filled `methodology_seed.md` body that adds an `Operator
review` section.

Click `Stage upload` (`Key('admin_corpus_demo_picker_submit')`).

**Expected:**

- The dialog closes.
- The detail pane grows a `Staged upload` card
  (`Key('admin_corpus_staged_diff')`) with the auto-generated summary
  ("Uploaded methodology_seed.md (+1 new, ~2 modified, -1
  inactivated)" or similar — exact counts depend on how the demo
  chunker splits the seed body).
- The diff card shows three sections: `New` (green dot), `Modified`
  (sunset dot), `Inactivated` (red dot). Counts render through the
  `admin_corpus_diff_*_count` keys; chunk tiles render through
  `admin_corpus_diff_<section>_<chunk_id>` keys.
- Commit + Discard buttons are visible
  (`Key('admin_corpus_commit_button')` /
  `Key('admin_corpus_discard_button')`).

### Step 4 - Commit the upload

Click `Commit`.

**Expected:**

- The staged diff card disappears.
- A `Corpus updated.` SnackBar shows.
- A new version row prepends the list with the green `Current` chip;
  the prior v2 row drops the chip and gains a `Rollback` button.
- The detail pane re-renders against the new current version with
  the staged chunk set.

### Step 5 - Rollback to a prior version

Click `Rollback` on the v1 row (the oldest version)
(`Key('admin_corpus_rollback_<v1-id>')`).

**Expected:** the confirmation dialog
(`Key('admin_corpus_confirm_dialog')`) opens with the title `Rollback
to this version?`. Click `Rollback` (`Key('admin_corpus_confirm_ok')`).

**Expected:**

- The dialog closes.
- A `Corpus rolled back.` SnackBar shows.
- A fresh version row appears at the top with the `Current` chip and
  a `rollback of <v1-short>` line under the summary.
- The detail pane re-renders with v1's chunk set re-attached to the
  new active version.

### Step 6 - Verify ff_support sees a read-only Corpus

Sign out, sign in as `support@forgeflow.test`.

**Expected:** the admin shell still renders (`ff_support` is
admitted to the console). Click `Corpus`. In live mode the screen
issues `GET /v1/admin/corpus/versions`, which the proxy admits
because `ff_support` is in `kFfCorpusAdminReadRoles`. The data
renders, and the screen is in **read-only mode**: the `View-only:
corpus uploads, commits, and rollbacks require the super_admin
role.` banner shows (`Key('admin_corpus_readonly_banner')`), the
`Upload markdown` button is absent, the staged-diff card is absent,
and every `Rollback` button on the prior version rows is absent.

Server-side defence-in-depth: any mutation that bypassed the UI
would still be rejected by the write-only gate
(`kFfCorpusAdminWriteRoles`), asserted by
`test/services/proxy_corpus_admin_routes_test.dart` tests
`POST /v1/admin/corpus/upload rejects ff_support with 403`,
`POST /v1/admin/corpus/commit rejects ff_support with 403`, and
`POST /v1/admin/corpus/rollback rejects ff_support with 403`.

### Step 7 - Edge: binary upload rejected with banner

Sign back in as `super.admin@forgeflow.test`, click `Upload
markdown`, paste a body that begins with a null byte sequence (the
demo picker treats it as binary) and submit.

**Expected:** the staged-diff card does not appear; the action-error
banner (`Key('admin_corpus_action_error')`) renders the
`upload appears to be binary; only markdown is accepted` message.
The current corpus is untouched.

### Step 8 - Edge: non-admin fail-closed

Sign out, sign in as `operator@forgeflow.test`.

**Expected:** the branded forbidden card renders. The Corpus
surface, side nav, and header bar are absent. Asserted indirectly by
`test/admin_operator_location_screen_test.dart` test
`non-admin user is blocked by the admin auth gate` (the gate sits
above the route catalog, so the same fail-closed branch covers
Corpus).

## Permission gating evidence

- Client side (admin console): the corpus route is only reachable
  when the auth gate admits the caller (`super_admin` or
  `ff_support`); `operator@forgeflow.test` lands on the forbidden
  card. The screen exposes an `editingEnabled` flag (default `true`)
  that hides every mutate affordance and renders a `View-only:
  corpus uploads, commits, and rollbacks require the super_admin
  role.` banner; the read-only branch is asserted in
  `test/admin/corpus_admin_screen_test.dart`.
- Server side (proxy): every `/v1/admin/corpus/*` request verifies
  the Firebase bearer token through `_resolveVerifiedClaimsOrWrite`
  and then evaluates a method-scoped role set —
  `kFfCorpusAdminReadRoles` (`super_admin` + `ff_support`) for
  `GET`, `kFfCorpusAdminWriteRoles` (`super_admin` only) for every
  mutation method. Asserted by
  `test/services/proxy_corpus_admin_routes_test.dart`.

## Idempotency evidence

- Every non-GET corpus route requires the `Idempotency-Key` header.
  Missing key → 400 `missing_idempotency_key`. Same key replayed →
  the in-memory gateway returns the cached `CorpusVersionRef` /
  `CorpusDiff`; production proxies write the request to
  `proxy_requests` keyed by `(route, idempotency_key)` so
  retransmits collapse to one ledger row. Asserted in
  `test/admin/corpus_admin_gateway_test.dart` test
  `commit replays cached version on key reuse` and the proxy test
  `POST /v1/admin/corpus/commit dedupes on Idempotency-Key`.

  (`version_id` nullable, `superseded_at` nullable); existing

  `corpus_pipeline_not_configured` 503; the live chunker pipeline
  ships in 11A.3b. Read + rollback paths land live in 11A.3a so the
  corpus ledger and rollback wiring can be exercised against staging
  before the full upload pipeline is wired.
- No tracker updates and no commits.
