### 3. Engineering anchor — backfill watermark per batch + sanity-hook reject

- Engineering slice anchor verified by
  `test/integrations/labor/agendrix_labor_adapter_test.dart`
  group `backfill`.
- Adapter runs a 60-day backfill against a fake API client returning
  three records: `sampleAgendrixTimeEntry` (good),
  `futureDatedAgendrixTimeEntry` (sanity hook returns `false`),
  `secondAgendrixTimeEntry` (good).
- Expected outcome:
  - `command.sanityHook` is called once per record (3 calls);
    `vendorEventId` arguments are `'te_412901'`, `'te_999001'`,
    `'te_412902'` in order.
  - The future-dated record (`'te_999001'`) is dropped — no canonical
    write — because the hook returns `false`. Framework already wrote
    `sanity_log` + `connector_sync_log 'sanity_drop'`; the adapter
    skips the canonical write.
  - The other two records are upserted via
    `AgendrixCanonicalSink.upsertTimePunch`.
  - `BackfillResult.recordsWritten == 2`; `BackfillResult.completed
    == true`.
  - **Expected watermark advance(s):** at least one
    `advanceWatermark` call after the batch commit; the persisted
    `cursor_token` matches the page's `nextCursor` (empty string when
    the page chain is exhausted).

### 4. Engineering anchor — polling tick reads watermark and resumes

- Engineering slice anchor verified by the same test group.
- After the backfill in step 3, `pollIncremental` is invoked with
  `lastModifiedSeen` set to the backfill's persisted value.
- The fake API client returns one new record on the next tick. The
  adapter:
  - Calls `command.sanityHook` once (returns `true`).
  - Upserts via `upsertTimePunch`.
  - Calls `advanceWatermark` with the page's `nextCursor` (empty
    string here) and the new `lastModifiedSeen`.
- Expected `PollIncrementalResult.recordsWritten == 1`,
  `sanityDropped == 0`.

### 6. Engineering anchor — mid-batch crash resume from cursor

- Engineering slice anchor verified by the watermark test group.
- The fake API client throws on page 3 (`crashAfterPage = 2`). Pages
  1 and 2 deliver records; page 3 throws.
- Expected behavior:
  - Two `advanceWatermark` calls land before the throw (one per
    successful page).
  - The last persisted cursor is `'cursor-after-batch-2'`; the last
    persisted `last_modified_seen` is the page-2 timestamp
    (`2026-05-02 23:48:01 UTC`).
  - On resume (next worker invocation), the adapter is constructed
    again with `BackfillCommand.resumeFromCursor =
    'cursor-after-batch-2'`. The fake's reset sequence shows the
    adapter requests the page chain starting from that cursor —
    verified by
    `apiClient.requestedCursors.contains('cursor-after-batch-2')`.
  - No record is double-written because the canonical UNIQUE
    collapses any retry of pages 1-2.

### 7. Engineering anchor — handleWebhook throws (poll-only)

- Engineering slice anchor verified by
  `test/integrations/labor/agendrix_labor_adapter_test.dart`
  group `handleWebhook`.
- Calling `adapter.handleWebhook(...)` with any payload throws
  `UnsupportedError('Agendrix does not support webhooks; pollOnly')`.
- The framework's `InboundWebhookHandler.dispatch` consults
  `capabilityProfile.webhookSupport` BEFORE dispatch and never
  delivers a webhook to a poll-only adapter; the throw is the
  defense-in-depth signal that catches a future router refactor that
  forgets the gate.
- **Webhooks N/A — pollOnly path; signature reject test skipped.**
  See `webhook_signature.md` (single line N/A) and
  `live_verification_checklist.md` row "Webhook signature
  verification" (checked off ✅ N/A in advance).

### 8. Engineering anchor — OAuth near-expiry refresh via cron

- Engineering slice anchor verified by the existing
  `test/integration/oauth_refresh_cron_test.dart` (framework slice
  8.0; the adapter does not need its own copy — the cron refreshes
  every Wave B vendor's `vendor_credentials` via
  `oauth_refresh_cron.dart`).
- Time-travel the test clock so `vendor_credentials.token_expires_at
  = now() + 30 minutes` for the Agendrix connection.
- The cron job runs `refresh_expiring_inbound_vendor_tokens()` and
  re-mints the access token via `POST /v2/oauth/token` with
  `grant_type = refresh_token`. Sliding rotation: a fresh refresh
  token is returned and persisted; the prior is dropped server-side
  by Agendrix.
- Expected outcome:
  - `connector_sync_log` row: `event_kind = 'auth_refresh'`.
  - `vendor_credentials.consecutive_refresh_failures = 0`.
  - Connection stays `connected`.
  - **No advisory lock** (lean cut 2 trim).
  - **No email_outbox row at V1** (deferred to `9.8.email`).
- On three consecutive failures, `connector_connection.status` flips
  to `error`; admin widget surfaces the operator-facing copy "Please
  reconnect Agendrix and sign back in."

### 9. Engineering anchor — disconnect → reconnect watermark preservation

- Engineering slice anchor verified by the connect/disconnect smoke
  test group.
- `adapter.disconnect(...)` returns `(credentialsWiped: true,
  webhookUnregistered: true, watermarkPreserved: true)`.
- `connector_sync_log` row: `event_kind = 'disconnect'` with
  `payload_preview` carrying the reason + actor.
- After disconnect, the watermark row in
  `connector_sync_watermark` for `(operator, location, vendor)` is
  preserved (not deleted). On reconnect, `pollIncremental` is invoked
  with `lastModifiedSeen` set to the persisted watermark; the fake
  empty-page response confirms no record is double-written or
  skipped.
- **Expected sink state:** `watermarkAdvances` is non-empty across
  the disconnect call.

### 10. Adversarial — future-dated time entry (sanity drop)

- The polling tick fetches a record with `start_time = now() + 5
  days`.
- The framework's `sanityHook` (bound in
  `tool/integration_sync_worker/integration_sync_worker.dart`) calls
  `VendorTimestampSanity.evaluate` and writes a `sanity_log` row
  with `rule = 'shift_in_future'`. The hook returns `false`.
- Adapter behavior:
  - Skips the canonical write for `'te_999001'`.
  - Increments `PollIncrementalResult.sanityDropped`.
  - Continues processing the remaining records.

### 11. Adversarial — webhook delivery attempt (poll-only)

- A bad actor (or vendor misconfiguration) sends a forged HTTP request
  to `/v1/webhooks/agendrix/<operator_id>/<location_id>`.
- The proxy resolves `vendorId = 'agendrix'` and consults the
  registered adapter map. **Forged-signature step replaced by:**
  the framework router reads
  `adapter.capabilityProfile.webhookSupport == VendorWebhookSupport.pollOnly`
  and returns `404` with `WebhookOutcome.vendorNotFound`-equivalent
  semantics — the adapter never receives the request, and
  `handleWebhook` is not invoked. No canonical fact is written.
- This anchor replaces the per-vendor signature-reject test for
  signing vendors. See `webhook_signature.md` (N/A line) and the
  `handleWebhook` test that asserts the throw as defense-in-depth.
