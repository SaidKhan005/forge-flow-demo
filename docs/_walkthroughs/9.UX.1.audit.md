# 9.UX.1 — MFA event_outbox enqueue audit

Audited the two MFA producer sites against the
`event_outbox_contract.md` producer rules (location_id present,
event_id UUID in payload, no secrets in payload).

## Files audited

- lib/services/mfa/mfa_recovery_request_gateway.dart
- lib/services/mfa/mfa_removal_worker.dart

`grep eventOutbox|EventOutbox|\.enqueue\(` over `lib/services/mfa`
returned hits only in these two files; no other MFA enqueue paths
exist.

## Gap 1 — location_id

- mfa_recovery_request_gateway.dart:137 — `locationId:
  target.locationId!` is passed alongside `operatorId:
  target.operatorId` (line 136). The lookup at line 129 short-circuits
  with `queued: false` when `target.locationId == null`, so the `!`
  is sound. No change needed; already conformant.
- mfa_removal_worker.dart:110 — `locationId: request.locationId`
  passed alongside `operatorId: request.operatorId` (line 109).
  `MfaFactorRemovalRequestRecord.locationId` is non-nullable
  (mfa_factor_removal_requests_repository.dart:26). No change
  needed; already conformant.

## Gap 2 — event_id

- mfa_recovery_request_gateway.dart:141 — `'event_id': requestId`
  where `requestId = _idFactory()` (line 133) and the default
  `_idFactory` is `_uuidV4` (lines 88, 160-174), a UUID v4
  generator using `Random.secure()` with the version (4) and
  variant (RFC 4122) bits set. No change needed; already
  conformant.
- mfa_removal_worker.dart:114 — `'event_id': request.requestId`.
  `request.requestId` is the removal request's UUID primary key
  (cast `@request_id::uuid` in
  mfa_factor_removal_requests_repository.dart:68). One outbox
  event is enqueued per completed request (`markCompleted` guards
  on pending state at line 89), so reusing the request UUID as the
  event_id is stable and unique per delivery. No change needed;
  already conformant.

## Gap 3 — secrets in payload

- mfa_recovery_request_gateway.dart:140-155 — payload carries
  `event_id`, `occurred_at`, `event_type`, `user_id`, `user_email`,
  `operator_id`, `location_id`, `reason`, `admin_user_ids`,
  `admin_emails`. No recovery codes, TOTP seeds, or raw factor
  material. Emails and user ids are routing identifiers, not
  factor material. No change needed; already conformant.
- mfa_removal_worker.dart:113-121 — payload carries `event_id`,
  `event_type`, `occurred_at`, `operator_id`, `location_id`,
  `user_id`, `factor_id`. `factor_id` is the `mfa_factors` row
  identifier, not the TOTP seed or recovery-code hash. The actual
  factor material is wiped by
  `_mfaFactorsRepository.revokeTotpFactor` (line 71) and
  `revokeActiveRecoveryCodeFactorsForUser` (line 77) and is never
  copied into the outbox payload. No change needed; already
  conformant.

## Outcome

All three gaps return clean across both producers. No code
changes applied; no scrub helper required.
