# 9.UX.4 - Settings Team Org Hierarchy

Date: 2026-04-30

## Scope

Add the `org_units` (`ltree`) browser, child-unit creation, location-move, and
org-unit-scoped invites/role grants to Settings -> Team for every signed-in
operator owner / manager.

## Operator Walkthrough (`kDemoMode = true`)

1. Launch ForgeFlow in demo mode and sign in as the demo operator owner
   (`demo.operator@forgeflow.test` / `forge-flow-demo`).
2. Open Settings.
3. Select Team.
4. Confirm the location tree renders under the **Org Hierarchy** section
   header, showing the seeded **Forge & Flow** root unit and the operator's
   single demo location underneath it (text trace: `org_hierarchy_section`
   widget key + `Forge & Flow` label visible).
5. Tap the add-child icon next to the root and add a child unit
   (type: `region`, label: `east`, name: `East Region`). Confirm the new
   region renders as a child of the root.
6. Tap **Move** next to the demo location, select the newly created
   `East Region` from the dropdown, and save. Confirm the location now
   renders nested under the new region in the tree.
7. Open the role-change dialog for the demo user from the Members table.
   Confirm a third **Org unit** segment now appears in the scope selector.
   Select **Org unit**, choose the `East Region`, and Save. Confirm the
   inheritance hint copy renders ("Child locations inherit org-unit grants.").
8. Repeat using the **Invite members** form: enter an email + role, select
   the **Org unit** segment, choose the `East Region`, and Send. Confirm the
   pending invite row renders with the org unit context.
9. Sign in as a Team viewer that lacks `team.roles.assign` (locked test
   actor `_settingsTeamLockedActor`). Open Settings -> Team and confirm
   the Org Hierarchy tree still renders with read-only copy
   ("Read-only view. Hierarchy edits and grants are locked for this
   account.") and that the add-child / move-location / org-unit segment
   controls are not present.
10. Sign in as a user without `team.users.view`. Confirm the Team tab
    is hidden entirely (the Settings tab bar collapses to Account-only).

## Contract Notes

- Reads and writes route through `AuthOperationsGateway` extensions:
  - `listOrgHierarchy` -> `GET /v1/admin/auth/org-units`
    (gates on `team.users.view`).
  - `createOrgUnit` -> `POST /v1/admin/auth/org-units`
    (gates on `team.roles.assign`).
  - `moveLocationToOrgUnit` ->
    `PATCH /v1/admin/auth/locations/<locationId>/org-unit`
    (gates on `team.roles.assign`).
- Tenant-scoped Postgres reads / writes go through `OrgUnitsRepository`
  in the proxy (per-tenant RLS via `app_current_operator()`). The repo
  injects `(operator_id, location_id)` via `runInTenantContext`; raw
  `package:postgres` access is forbidden outside
  `lib/infrastructure/persistence/postgres/`.
- `org_units` is the per-operator corp/region/district/location_group
  hierarchy stored as a Postgres `ltree` (item 1 / Q2 from
  `phase_9_scalability_decisions_2026-04-27.md`). The
  `set_location_org_unit_path()` trigger in
  `db/migrations/202604290101_phase_9_hierarchy_access_wiring.sql`
  refreshes `locations.org_unit_path` from `org_units.path` whenever
  `parent_org_unit_id` changes - the proxy only writes
  `parent_org_unit_id` and the trigger handles the denormalized path.
- Org-unit grants flow through `user_roles.scope_type = 'org_unit'`
  with a `org_unit_id` FK. The migration's
  `user_effective_locations` materialized cache + trigger fan
  child-location coverage out so descendant locations inherit the
  unit-level grant; permission gates / RLS / claims pick the right
  scope automatically.
- No new permission keys: existing `team.users.view`,
  `team.users.invite`, and `team.roles.assign` cover the surface.
- Demo mode (`kDemoMode = true` or no live gateway): a deterministic
  in-memory hierarchy seeded with the operator's primary location is
  used for the walkthrough; child-unit and move-location writes mutate
  the in-memory state so the UI flows complete without a backend.
