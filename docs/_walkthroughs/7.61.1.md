# 7.61.1 Walkthrough — `HistoryTeachingAnalyzer` lookup honesty

**Slice:** 7.61.1 (Phase 7.61 — Driver-key audit fix, Finding F-1)
**Status:** Accepted 2026-05-03
**Mode:** `kDemoMode = true` (operator app, deterministic seed)
**Date:** 2026-05-03

This slice closes Finding F-1 from
[`docs/archive/phases/phase_7_61/phase_7_61_audit_plan.md`](../archive/phases/phase_7_61/phase_7_61_audit_plan.md):
the banned `firstWhere(orElse: () => LeverCards.coversDown / ppaUp)`
pattern in `HistoryTeachingAnalyzer.summarize` (the same pattern
`7.58.UX.5` removed from every renderer site, kept here in the analyzer
because the upstream `HistoryPatternBuilder` filter made the orElse
defensive in practice).

The contract reference is R-CONS-2 + R-STOR-7 in
[`docs/contracts/phase_7_61_driver_key_contract.md`](../contracts/phase_7_61_driver_key_contract.md):
service consumers that produce a downstream summary whose value will be
rendered MUST resolve through `LeverCards.lookup` and surface a `null`
return as an explicit degraded state — not a fall-through to a real
catalog card.

`7.61.2` (F-2 — empty-state default flip on `mostCommonLeakId`) and
`7.61.3` (F-3 — `demo_fixture_data.dart` cleanup) ship in their own
lanes. This walkthrough does not touch their files.

## What changed

### `lib/services/history_teaching_analyzer.dart`

- Lines 88-91 (now lines 88-99): `final leakCard =
  LeverCards.all.firstWhere(... orElse: () => LeverCards.coversDown)`
  → `final LeverCardData? leakCard = LeverCards.lookup(mostCommonLeakId)`
  followed by `if (leakCard == null) { mostCommonLeakId = ''; maxCount = 0; }`.
  Because `mostCommonLeakId` is now `''` after a null lookup, the
  daypart-frequency loop a few lines down naturally produces an empty
  `topLeakDayparts` (no record's `leverId` matches `''`). The
  constructor call passes `leakCard?.sideLabel ?? 'No leak pattern yet'`
  symmetric with the pre-existing `'No benchmark pattern yet'` default.
  Net effect: an unknown id zeros out **id, count, dayparts, and side
  label** together — there is no escape path through any of the four
  leak fields into downstream copy.
- Lines 131-134 (now lines 120-172): the benchmark block was
  restructured around an **upstream catalog allow-list filter**
  applied to `benchmarkRecords` itself —
  `records.where((r) => r.isBenchmark && _knownLeverIds.contains(r.leverId))`.
  This is the contract's R-CONS-2 first option ("filter to known
  catalog ids before producing the summary"), versus the leak side
  which uses the second option ("resolve through `LeverCards.lookup`").
  Asymmetric on purpose: applying the same allow-list to the leak side
  would push the all-unknown case onto the F-2 default `'covers_down'`
  (line 79) and re-introduce the silent overclaim until 7.61.2 flips
  that default to `''`.
  
  The upstream filter closes a class of bug the post-tie-break null
  check alone could not — mixed inputs where a known id wins the
  tie-break but an unknown sibling's daypart bleeds into
  `benchmarkDayparts`. Pre-fix `splh_up x10 on Sat` + `made_up x1 on Sun`
  returned `benchmarkDayparts == ['Sat Dinner', 'Sun Lunch']` because
  `benchFreq` aggregated across all benchmark records regardless of
  leverId; `LearnTeachingAnalyzer.studyLine` would then render
  "Study benchmark dayparts: Sat Dinner / Sun Lunch." — fabricating a
  study target out of a phantom benchmark. Post-fix only Sat Dinner
  survives. (Reviewer P1.)
  
  `benchmarkDayparts` also moves inside the `benchCard != null` branch
  so an unknown most-common id zeros it out in lockstep with id,
  count, and side label. With the upstream filter that branch is
  defense-in-depth (every id reaching `bFreq` is in the catalog, so
  `lookup` never returns null on this path); the else branch stays as
  a guardrail in case the filter is ever loosened.

Both sites carry a one-block comment naming the slice and citing
R-CONS-2 + R-CONS-9 + R-STOR-7. Line 79
(`String mostCommonLeakId = 'covers_down';` — Finding F-2) is
intentionally untouched; that empty-state default flip is owned by
`7.61.2`. The new reset happens AFTER `mostCommonLeakId` has been
computed, only when the lookup detects a non-catalog id — it does not
override the empty-state default itself, and the existing F-2 holdout
test stays `skip:`-marked (lookup of `'covers_down'` returns the real
card, so the reset doesn't fire on the empty-set path).

### `test/contracts/phase_7_61_driver_key_test.dart`

- New group `F-1 — unknown id zeros out every summary field, no
  silent overclaim` with seven assertions, each pinning a different
  escape path:
  1. **Unknown leak id, all four leak fields** —
     `mostCommonLeakId == ''`, `mostCommonLeakCount == 0`,
     `mostCommonLeakSideLabel == 'No leak pattern yet'`,
     `topLeakDayparts.isEmpty`. Pins R-CONS-9's "catalog id OR empty
     string" rule and prevents the
     `'Fix no leak pattern yet first in Mon Lunch.'` copy bug
     downstream.
  2. **Unknown benchmark id, all four benchmark fields** — same
     shape: `mostCommonBenchmarkId == ''`, count zero, placeholder
     side label, `benchmarkDayparts.isEmpty`. Prevents the
     `'Study benchmark dayparts: Sat Dinner.'` copy bug.
  3. **Known leak id preserves count + dayparts** — golden-path
     regression guard. Two `cplh_down` records → `cplhDown` side
     label, count 2, dayparts `['Mon Lunch']`.
  4. **Known benchmark id preserves count + dayparts** — same shape
     for the benchmark side using `splh_up`.
  5. **Known leak + unknown sibling** — known wins tie-break, and the
     unknown record's daypart (`Wed Dinner`) does not bleed into
     `topLeakDayparts`. Pins the daypart-frequency loop's
     `r.leverId == mostCommonLeakId` filter as the leak-side gating
     mechanism.
  6. **Known benchmark + unknown sibling (Reviewer P1)** —
     `splh_up x1 on Sat` + `made_up x1 on Sun` → `benchmarkDayparts ==
     ['Sat Dinner']` only. The unknown record's `Sun Lunch` MUST NOT
     leak in. Pre-fix this returned `['Sat Dinner', 'Sun Lunch']`.
     Pins the upstream `_knownLeverIds.contains(r.leverId)` filter on
     `benchmarkRecords` as the benchmark-side gating mechanism.
  7. **Known benchmark wins by tie-break order even when unknowns
     have higher raw count** — `splh_up x1` + `made_up x10` → the
     upstream filter drops the 10 unknown rows before `bFreq`, so
     `splh_up` surfaces as the real benchmark with `benchmarkDayparts
     == ['Sat Dinner']`. Without the upstream filter the unknown
     would have dominated `bFreq`, won the tie-break, and triggered
     the "no benchmark pattern yet" reset — silencing the real
     benchmark.

The pre-existing R-CONS-9 F-2 holdout test stays `skip:`-marked —
removing the skip is owned by `7.61.2`. Lookup of `'covers_down'`
(the F-2 default) returns the real coversDown card, so the F-1
reset does not fire on the empty-set path; the F-1 fix and the F-2
fix compose cleanly when both land.

## Demo seed shape (relevant for this walkthrough)

`MockReplayDataSeed.generateForDate('2026-03-27')` produces a current
week (`2026-W13`) where Mon-Thu lunch and dinner are closed,
Fri lunch is closed, and Fri dinner / late_night / Sat / Sun are
projected. Closed shifts run through `LaborModel.determineLever` to
get a real lever id; `HistoryPatternBuilder` filters out the
`'on_model'` sentinel and any id outside the 16-entry catalog before
emitting `HistoryPatternRecord`s, so under the default seed every
record `HistoryTeachingAnalyzer.summarize` ever sees carries a known
catalog id.

That upstream filter is exactly why F-1 was a defensive-only finding
at audit time: the orElse never fired in practice. The fix exists so
that a future producer (Phase 8 vendor connector, manual SQL insert,
test fixture) cannot silently turn an unknown id into a real coversDown
or ppaUp card by skipping the builder.

## Click path (text trace)

### Step 1 — Launch the operator app in demo mode

`lib/main_forgeflow.dart` boots the operator shell with
`MockReplayDataSeed` attached. Default business date `2026-03-27`
(Friday in W13).

**Expected:** the operator home renders with the seeded current-week
data. No change from `7.58.UX.5` baseline.

### Step 2 — Variance > Learn → PRIMARY LEAK card (golden path)

Tap **Variance**. Tap **Learn**. The Recurring Leak chapter renders
the PRIMARY LEAK card. The seeded W13 history has at least one closed
shift fed by `LaborModel.determineLever` (e.g. `cplh_down` from a
Tue-lunch over-staffed scenario), so
`HistoryTeachingAnalyzer.summarize` returns
`mostCommonLeakId = 'cplh_down'` and
`mostCommonLeakSideLabel = 'FOH ONLY'`.
[`variance_learn_tab.dart:151-153`](../../lib/screens/variance/variance_learn_tab.dart)
runs `LeverCards.lookup('cplh_down')`, gets the real
`LeverCardData.cplhDown`, and the carousel renders the four-card
"Recurring Leak" sequence (snapshot / what happened / what to do /
teaching note).

**Expected:** byte-identical to the `7.58.UX.5` baseline. The
`LeverCards.lookup` call replacing `firstWhere(orElse: …)` is
behaviorally equivalent for known ids.

### Step 3 — Variance > Learn → REPEATABLE WINS chapter (golden path)

Tap the **Repeatable Wins** chapter chip. The benchmark card reads
`LearnRepeatableWinSummary.dominantLeverId` (lowercase canonical) and
runs it through `LeverCards.lookup` at
[`variance_learn_tab.dart:157-158`](../../lib/screens/variance/variance_learn_tab.dart).
For the W13 seed this resolves to the dominant favorable lever (e.g.
`splh_up`) and renders the matching benchmark card.

**Expected:** byte-identical to the `7.58.UX.5` baseline.

### Step 4 — Inject an unknown leverId via the contract test (defensive surface)

The default seed cannot reach the unknown-id branch — the
`HistoryPatternBuilder` filter at
[`history_pattern_builder.dart:34, :42`](../../lib/services/history_pattern_builder.dart)
drops anything outside `LeverCards.all` before
`HistoryTeachingAnalyzer.summarize` ever sees it. The contract test
in
[`test/contracts/phase_7_61_driver_key_test.dart`](../../test/contracts/phase_7_61_driver_key_test.dart)
synthesizes `HistoryPatternRecord`s with `leverId: 'made_up_lever'`
directly (skipping the builder) and asserts the post-fix behavior:

```
input  : 2× HistoryPatternRecord(leverId='made_up_lever', isBenchmark=false)
output : mostCommonLeakId            = ''                       (was 'made_up_lever' pre-fix)
         mostCommonLeakCount         = 0                        (was 2 pre-fix)
         mostCommonLeakSideLabel     = 'No leak pattern yet'    (was 'BOTH SIDES' pre-fix)
         topLeakDayparts             = []                       (was ['Mon Lunch','Tue Dinner'] pre-fix)

input  : 1× HistoryPatternRecord(leverId='made_up_lever', isBenchmark=true)
output : mostCommonBenchmarkId        = ''                       (was 'made_up_lever' pre-fix)
         mostCommonBenchmarkCount     = 0                        (was 1 pre-fix)
         mostCommonBenchmarkSideLabel = 'No benchmark pattern yet' (was 'BOTH SIDES' pre-fix)
         benchmarkDayparts            = []                       (was ['Sat Dinner'] pre-fix)
```

Downstream effect on
[`learn_teaching_analyzer.dart`](../../lib/services/learn_teaching_analyzer.dart):
since `historySummary != null` (records exist, the analyzer ran), it
falls into the else-branch at line 60-83 and copies the analyzer's
zeroed values into `LearnTeachingSummary`. The `topLeakDayparts.isEmpty`
condition picks the short copy:
`primaryFixLine = 'Fix no leak pattern yet first.'`, NOT
`'Fix no leak pattern yet first in Mon Lunch.'` — the daypart can no
longer escape into the sentence. Same for the benchmark study line.
[`variance_learn_tab.dart:151-153`](../../lib/screens/variance/variance_learn_tab.dart)
then runs `LeverCards.lookup('')` → null → falls into the
`badgeLabel: 'NO PATTERNS YET'` placeholder card at
[lines 166-171](../../lib/screens/variance/variance_learn_tab.dart),
using the now-honest `primaryFixLine` as the body. Pre-7.61.1 the
analyzer would have stamped `'BOTH SIDES'` into the side label and
`'Mon Lunch'` into the dayparts, the placeholder card body would have
read "Fix both sides first in Mon Lunch." — a fully-fabricated
sentence built from a phantom lever. The fix closes that hole at the
analyzer layer, so every downstream consumer (today
`LearnTeachingAnalyzer`; tomorrow whatever Phase-8 vendor connector
or admin surface reads the summary) inherits the same honest empty
state.
