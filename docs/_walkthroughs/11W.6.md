# 11W.6 Walkthrough — Security surface

**Slice:** 11W.6 (Phase 11W — Operator Web Console; Self-Service Parity block)
**Mode:** demo (`OPERATOR_WEB_DEMO_AUTH=true`)
**Date:** 2026-05-06

This slice ships the web parity for the mobile Settings -> Security
section. The Operator Web Console gains a `Security` route in the
side nav. Every authenticated operator-web actor sees their own MFA
factor inventory, password rotation, and recent sign-in activity.
Floor managers (`location_manager`) see only their own data; cross
team MFA reset is on `11W.1` Members or via `11A.14` support
escalation.

**Wiring honesty (read this first):** `11W.6` ships the Security
surface against the in-memory `DemoWebSecurityGateway`. The live
HTTP gateway (`WebSecurityGatewayLive`) is built in this slice and
wired against the existing Phase 9 routes for MFA + password change
+ audit log; no new backend routes were added. The live
`FirebaseOperatorWebAuthSource` mixes the gateway in via the new
`OperatorWebSecurityGatewayProvider` interface in the
`11W.6.live` follow-up — the same gateway-follows-shell pattern
Phase 11A.0 -> 11A.1 used.

**Validation copy posture:** the parity contract `§ Security` locks
four operator-facing strings verbatim. The slice surfaces them on
the matching server-side error codes plus on the screen's local
policy check so the operator gets the same copy whether the proxy
or the dialog catches the rejection first:

- Wrong current password -> "Current password is incorrect."
- Password too weak -> "Password must be at least 12 characters
  with one number and one symbol."
- Password reuse -> "You can't reuse a recent password. Choose a
  new one."
- TOTP code invalid -> "That code didn't match. Try again with the
  next code from your authenticator."

**24-hour delayed-removal posture:** factor revocation always
schedules a removal request 24 hours into the future per the
`team.users.reset_mfa` posture. The row flips to a `Removal pending`
chip plus a `Cancel removal` action while the window is open;
clicking Cancel removal sends `/v1/auth/mfa/factors/removal/cancel`
and the row flips back to active.

**Login history posture:** the screen reads the last 90 days of
`/v1/auth/audit-log` rows and projects them down to the
Security-relevant set (`auth.session.*` plus `auth.password.*` plus
`auth.mfa.*`). A small filter strip narrows the displayed window to
the last 7 / 30 / 90 days locally; the gateway always reads the
full 90-day window so the strip works without a re-fetch.

## What changed

### `lib/operator_web/services/demo_team_fixtures.dart`

Extended additively with two new fixture sets the parity contract
§ Demo-mode fixtures calls for:

- `kDemoTeamMfaFactorsFixture` — one active TOTP factor on the demo
  owner so the walkthrough can exercise the revoke -> 24-hour
  delayed-removal -> cancel flow without first running enrollment.
- `kDemoTeamLoginHistoryFixture` — six rows spanning the last 7 /
  30 / 90 days (sign-in events, MFA enroll, password change,
  session revoke) so the walkthrough's "filter to last 7 days" step
  has rows on both sides of the cutoff.

### `lib/operator_web/services/web_security_gateway.dart` (new)

Narrow `WebSecurityGateway` interface plus the live
`WebSecurityGatewayLive` impl built on `package:http`. Hits the
existing Phase 9 routes (paths verified against
`tool/advisor_proxy/advisor_proxy.dart` route registrations):

- `POST /v1/auth/mfa/factors/list`            — list own factors.
- `POST /v1/auth/mfa/totp/begin`              — begin enroll
  (body must include `user_email`).
- `POST /v1/auth/mfa/totp/confirm`            — confirm enroll.
- `POST /v1/auth/mfa/factors/revoke`          — schedule removal.
- `POST /v1/auth/mfa/factors/removal/cancel`  — cancel removal.
- `POST /v1/auth/mfa/recovery/request`        — queue MFA recovery
  (no bearer token; the operator may have lost access to all
  enrolled factors).
- `POST /v1/auth/password/change`             — change password.
- `GET  /v1/auth/audit-log`                   — login-history
  source.

Every authenticated write accepts a caller-minted
`Idempotency-Key` and threads it through as the request header.
The gateway never mints keys internally so the proxy
`proxy_requests` UNIQUE-key replay surfaces the original write on
retry. Login-history reads project the audit log down to the
Security-relevant subset: the contract's `auth.session.*` plus
`auth.password.*` plus `auth.mfa.*` prefixes are accepted in both
the dot-separated form and the underscore-separated row form
actually emitted by the codebase (`auth.signed_in`,
`auth.password_changed`, `auth.mfa_totp_enrolled`,
`auth.session_revoked`, `auth.all_sessions_revoked`,
`auth.login_failed`), plus the
`mfa_factor_revocation_*` lifecycle events written by
`mfa_operations_gateway.dart`. The 90-day window is enforced
gateway-side via the `from=` query parameter. No `dart:io`, no
`sqflite`.

### `lib/operator_web/services/demo_security_gateway.dart` (new)

In-memory `DemoWebSecurityGateway` reading the shared fixture file.
- `listFactors()` projects the fixture set; pending removals live
  on the gateway instance so a walkthrough's revoke + cancel cycle
  is reproducible across page loads.
- `beginTotpEnrollment` returns a deterministic otpauth URL +
  shared secret so the demo flow stays stable across runs.
- `confirmTotpEnrollment` accepts any non-`000000` code; `000000`
  triggers the locked invalid-code copy so the walkthrough can
  exercise the negative path.
- `revokeFactor` always schedules a 24-hour delayed removal
  request; idempotency replays return the original outcome.
- `cancelFactorRemoval` flips the matching request to
  `cancelled` status.
- `changePassword` enforces the demo policy rules (>=12 chars, one
  digit, one symbol) and reuse-rejection against an 8-slot password
  history; failures surface the locked validation codes
  (`wrong_current_password`, `password_policy_failed`,
  `password_reuse_rejected`).
- `listLoginHistory` filters the fixture set to the last 90 days
  and the Security-relevant event prefixes.

### `lib/operator_web/screens/security_screen.dart` (new)

Operator Web Console Security screen. Renders three stacked
sections:

- `Two-factor sign-in`
  (`operator_web_security_mfa_section`) — factor inventory with
  per-factor enroll / revoke / cancel-pending-removal actions.
  Revoking a factor schedules a 24-hour removal; the row flips to
  a `Removal pending` chip plus `Cancel removal` action while the
  window is open. A
  `Lost access to your authenticator?` link
  (`operator_web_security_mfa_recovery_request`) at the bottom of
  the section pops a confirm dialog and queues an MFA recovery
  request via `/v1/auth/mfa/recovery/request`; the proxy emails
  the operator a reset link out of band.
- `Password`
  (`operator_web_security_password_section`) — opens the change
  password dialog. A success toast surfaces inside the section
  after the dialog closes.
- `Recent sign-in activity`
  (`operator_web_security_login_history_section`) — login history
  table with a 7 / 30 / 90 day filter strip
  (`operator_web_security_login_history_filter_last_7` and
  siblings).

### `lib/operator_web/screens/mfa_factor_dialog.dart` (new)

Post-onboarding MFA enroll dialog. Two-step:

1. `Generate code` -> gateway returns the otpauth URL plus shared
   secret rendered in a copy-friendly panel.
2. `Verify and add` -> gateway returns the new factor; the dialog
   pops `true` and the Security screen reloads.

Validation copy locked verbatim per the parity contract — the
dialog surfaces "That code didn't match. Try again with the next
code from your authenticator." on `mfa_totp_invalid_code`.
Idempotency keys mint per begin + per confirm so a retry on confirm
hits a fresh idempotency slot rather than replaying the prior
failure.

### `lib/operator_web/screens/change_password_dialog.dart` (new)

Post-onboarding change-password dialog. Three fields (current /
new / confirm). Validation copy locked verbatim per the parity
contract:

- `wrong_current_password` -> "Current password is incorrect."
- `password_policy_failed` / `too_short_or_weak` ->
  "Password must be at least 12 characters with one number and one
  symbol."
- `password_reuse_rejected` -> "You can't reuse a recent password.
  Choose a new one."
- Mismatched confirmation -> "New password and confirmation must
  match. Re-type both fields and try again."

The dialog also pre-checks the new-password policy locally so the
operator sees the error without a round-trip; the proxy still
reverifies on submit.

## Click path (numbered steps)

### Step 1 — Sign in on web

Open `app.forgeflow.app` in a browser tab with
`OPERATOR_WEB_DEMO_AUTH=true`. Sign in via the demo magic link.

**Expected:** the web shell renders the side nav with a `Security`
entry between Sessions and Vendor connections.

### Step 2 — Click Security in the side nav

**User action:** click `Key('operator_web_nav_item_security')`.

**Expected:**

- Body swaps to `Key('operator_web_security_screen')`.
- `Key('operator_web_security_mfa_section')` lists one TOTP factor
  (the demo owner's existing fixture row) with a `Remove` action.
- `Key('operator_web_security_password_section')` shows a
  `Change password` button.
- `Key('operator_web_security_login_history_section')` lists six
  rows ranging from 2026-03-18 to 2026-05-05.

### Step 3 — Enroll a new authenticator

**User action:** click `Key('operator_web_security_mfa_add')`.
The MFA factor dialog opens. Click
`Key('operator_web_security_mfa_factor_begin')` to generate the
otpauth URL. Type any 6-digit code (e.g. `123456`) into
`Key('operator_web_security_mfa_factor_code_field')` and click
`Key('operator_web_security_mfa_factor_confirm')`.

**Expected:**

- Dialog closes.
- A snackbar `Authenticator app added.` surfaces.
- The MFA section now lists two factors.

### Step 4 — Schedule + cancel a removal

**User action:** click the existing factor's
`Key('operator_web_security_mfa_factor_revoke_demo-security-totp-existing')`
button. The confirm dialog opens. Click
`Key('operator_web_security_confirm_dialog_confirm')`.

**Expected:**

- Snackbar surfaces:
  `Authenticator removal scheduled. It will be removed in 24 hours
  unless you cancel.`
- The row flips to show a
  `Key('operator_web_security_mfa_factor_pending_chip_demo-security-totp-existing')`
  chip plus a
  `Key('operator_web_security_mfa_factor_cancel_removal_demo-security-totp-existing')`
  action.

**User action:** click the cancel-removal button.

**Expected:**

- Snackbar `Authenticator removal cancelled.` surfaces.
- The pending chip disappears; the row is back to active state
  with the `Remove` action restored.

### Step 5 — Change password

**User action:** click
`Key('operator_web_security_password_change')`. The dialog opens.
Type `demo-pass-1!` into the current field, `rotate-pass-2026!`
into both new + confirm. Click
`Key('operator_web_security_change_password_submit')`.

**Expected:**

- Dialog closes.
- A success toast surfaces in the password section
  (`Key('operator_web_security_password_toast')`):
  `Password updated.`

### Step 6 — Request authenticator recovery (negative path)

**User action:** click
`Key('operator_web_security_mfa_recovery_request')` at the bottom
of the MFA section. The confirm dialog opens. Click
`Key('operator_web_security_confirm_dialog_confirm')`.

**Expected:**

- Snackbar surfaces:
  `Recovery link sent to sam.owner@demobistro.test. Check your
  inbox in a few minutes.`
- The demo gateway records an `auth.mfa_recovery_requested` event
  in the login-history projection, visible in the next section.

### Step 7 — Filter login history to last 7 days

**User action:** click
`Key('operator_web_security_login_history_filter_last_7')`.

**Expected:**

- The 2026-05-05 web sign-in row stays visible.
- The 2026-04-12 MFA enrolment row, the 2026-04-10 password change
  row, the 2026-03-22 sign-in row, and the 2026-03-18 session
  revoked row disappear.

## Permission gating evidence

The Phase 9 proxy routes already enforce permission gates server-
side. Security is a per-actor surface; every authenticated user
sees their own data without a permission key check.

| Role                  | MFA inventory | Password change | Login history |
| --------------------- | ------------- | --------------- | ------------- |
| `operator_owner`      | own           | own             | own           |
| `operator_admin`      | own           | own             | own           |
| `operator_manager`    | own           | own             | own           |
| `operator_supervisor` | own           | own             | own           |
| `operator_staff`      | own           | own             | own           |
| `location_manager`    | own           | own             | own           |

Cross-team MFA reset (resetting another member's factors) is on
`11W.1` Members (`team.users.reset_mfa`) or via support escalation
through `11A.14` (`admin.users.reset_mfa_factors`). The `11W.6`
surface intentionally does not expose that path.
